## 1.3 いちばん大事な考え方（3つだけ覚えて帰る）

**① 同じ C コードを、リンクするファイルを変えるだけで2種類にビルドする**  
描画のソースをリンクしなければ「判定だけの実行体」になる。ロジックの二重実装がゼロになる。

**② サーバだけが本当の状態を持つ（サーバ権威）**  
ブラウザは受け取った状態を描くだけ。だからチートも、プレイヤー間のズレも原理的に起きない。

**③ プレイヤーも NPC も同じ「戦闘員」で、違うのは入力源だけ**  
`AI` か `EXTERNAL`（外から与えられる入力）かの 1 フラグ。  
これで「多人数」「リモート対戦」「AI 対戦」が同時に成立する。

# 2. 設計思想 ― なぜこの形か

**この章で分かること**: 用語の定義、cub3D が何だったか、Web 化の難問と採用案、3つの柱の根拠。

## 2.1 先に用語を固定する

本文で繰り返し使う語は、ここで定義する（付録Bにも再掲）。

| 用語 | 意味 |
|---|---|
| **戦闘員 (combatant)** | 人間・AI を問わずマップ上で戦う1体。実装型は `t_enemy` |
| **入力源 (input source)** | 戦闘員の操作を誰が決めるか。`AI` か `EXTERNAL` |
| **スロット (slot)** | 試合の参加枠。API 引数名は `slot`。RSP は4スロット、FPS は2スロット。定数名に `SEATS` が残る箇所あり（`SIM_FPS_SEATS` 等） |
| **ハザード** | マップ由来の敵（文字 `M`）。スロットではなく障害物。id は 8 番から |
| **サーバ権威** | サーバの状態だけが正しく、クライアントは表示するだけ、という方式 |
| **スナップショット** | ある時点の試合状態一式（位置・向き・スコア・手など） |
| **ゲート** | 「ここで判定して、ダメなら別案へ退避する」と事前に決めた関門 |

> 旧文面の「席」はすべて **スロット** に統一した。コード内の `slot` と揃えるため。

## 2.2 出発点 ― cub3D とは何だったか

42 の課題で作った **C 言語のレイキャスタ**。`Wolfenstein 3D` 風の疑似3Dで、
MiniLibX（X11）を使って Linux のウィンドウへ直接ピクセルを書いていた。

### FPS モード ― 一人称の探索

- マップに散らばる**収集アイテム**（`k`〜`o`）を全部集めると、**扉**（`D`）が開いて先へ進める
- **敵**（`M`）は巡回し、視界に入ると追跡してくる。接触すると死亡ペナルティ
- ピストルで撃てば倒せる（既定 5 ヒット）。懐中電灯・素手（走れる）に持ち替えられる
- **ゴール**（`G`）へ到達するとクリア

### RSP モード ― じゃんけん鬼ごっこ

- **プレイヤー1人 + NPC 3体**が**赤チーム / 青チーム**に 2 人ずつ分かれる
- 全員がグー・チョキ・パーのどれかを頭上に掲げて歩き回る
- **異なるチームの2人が接触すると、その場でじゃんけん判定**。勝った側のチームに 1 点、
  負けた側は即リスポーン（味方どうし・あいこは何も起きない）
- 自陣のスポーンマスに踏み込むと手がランダムに変わる。先に **10 点**取ったチームの勝ち

> **この「1人の人間 + 3体の NPC が同じマップで戦う」構造が、あとから見て最大の資産だった。**
> 4人が同じルールで動く器が、すでに完成していたということだから。

### `.cub` マップとプログラム構造（要約）

- マップはテキスト1枚（設定ヘッダ + 文字配列）。サーバが**本文をそのまま配れる**（後の E-09）
- `common` / `fps` / `rsp`。`mode_ops`（関数テーブル）でモード差を吸収
- 改造前は毎フレーム「入力→移動→AI→接触→描画」が1関数に同居 → **判定だけをサーバへ切れない**
- `t_game` の中心は `camera`（プレイヤー正本）と `world.enemies`（NPC だけ）→ **2人目の人間を置く場所がない**

レイキャスタの数学（DDA・魚眼補正など）は **付録A**。Cub3D 既習なら飛ばしてよい。  
解像度ノブ（E-13）の根拠だけは付録A末尾の計算量の節を見れば足りる。

## 2.3 何が問題だったか ― 世界が違う

> プロジェクトは **Web アプリケーション**であり、フロントエンド、バックエンド、**データベース**が必要である

一方 cub3D は **Linux の X11 ネイティブアプリ**。

| | cub3D | ft_transcendence の要求 |
|---|---|---|
| 実行環境 | Linux のウィンドウ | ブラウザ |
| 描画 | MiniLibX（X11） | Canvas / WebGL |
| 入力 | X11 のキーイベント | KeyboardEvent |
| プレイ人数 | 1人 | 複数人がネットワーク越しに |
| 状態の持ち主 | プロセス1つ | サーバが正本、DB に永続化 |

**ブラウザでは動かない。世界が違う。**

## 2.4 3つの案を比較した（`02_設計書/0-全体アーキテクチャ設計.md` §2.1）

| 案 | 内容 | 判定 |
|---|---|---|
| **A. C を WASM へ移植（採用）** | MiniLibX を薄い層に置換し、Emscripten で WASM 化。同じ C を Node でもヘッドレス実行 | **◎** ロジックの二重実装がゼロ |
| B. TypeScript でフルリライト | レイキャスタもルールも TS で書き直す | **×** 検証済み C を捨てる。品質リスク |
| C. サーバで描画して映像を配信 | サーバがレンダリングしてストリーム | **×** 帯域・遅延・スケールが非現実的 |

**結論は案A。** 「Day 2 のスパイクで検証し、ダメなら案B へ退避する」関門（ゲート1）を先に置いた。

## 2.5 案A の隠れたご褒美 ― 同じコードから2種類

「MiniLibX 依存を剥がす」＝「描画層が独立する」。描画ソースをリンクしなければ、**判定だけの実行体**が手に入る。

| 成果物 | 中身 | どこで動く | 役割 |
|---|---|---|---|
| `render.wasm` | レイキャスタ・スプライト・UI描画・判定 | ブラウザ | 絵を描く |
| `sim.wasm` | 判定だけ（移動・衝突・AI・じゃんけん・スコア）。**描画コードを含まない** | Node サーバ | 勝敗を決める |

これが**サーバ権威モデル**の土台になる。

```
サーバだけが本当の状態を持つ  →  ブラウザは受け取った状態を描くだけ
                              →  チートも、プレイヤー間のズレも原理的に消える
```

# 3. アーキテクチャ ― どう切って、どうビルドするか

**この章で分かること**: 3層分離、`pf_*`、`game_step`、3ターゲット、入力抽象化、公開口、snapshot／補間、ゲート1。

対応する作業痕跡: **E-01〜E-12**（および説明用の説1〜説4）。

## 3.1 目標の形（3層）

```
┌─────────────────────────────────────────────────────┐
│ pf_* 層（プラットフォーム層・新規）                  │
│   フレームバッファ / 入力 / 時間 / テクスチャの供給   │
│   ← 環境ごとに差し替える薄い層（X11 / Canvas / なし） │
├─────────────────────────────────────────────────────┤
│ game_step()    判定                                  │
│   入力を適用 → 移動 → 衝突 → AI → じゃんけん → スコア │
├─────────────────────────────────────────────────────┤
│ render_frame() 描画                                  │
│   状態を受けてピクセルを塗る                          │
└─────────────────────────────────────────────────────┘
```

**ルール**: 上の層は下を知らない。`game_step` は 1 ピクセルも触らないし、
時刻も取らないし、`sleep` もしない。**渡された `dt` を使って状態を進めるだけ。**

## 3.2 `pf_*` インタフェース（`includes/platform/platform.h`）

> **何を示すか**: MiniLibX 呼び出しを、環境差し替え可能な 10 関数に閉じ込めた境界。

```c
int     pf_init(t_window*, int w, int h, const char* title);
int     pf_create_framebuffer(t_window*);
void    pf_present(t_window*);
int64_t pf_now_ms(void);
int     pf_load_texture(t_window*, t_tex*);
void    pf_destroy_texture(t_window*, t_tex*);
void    pf_poll_events(t_input*);
void    pf_setup_hooks(t_game*);
void    pf_loop(t_window*);
void    pf_shutdown(t_window*);
```

| 実装 | ファイル | 中身 |
|---|---|---|
| native | `platform/native/platform_native.c` | MiniLibX を呼ぶ（従来の動作） |
| web | `platform/web/platform_web.c` | Canvas 用。ループは JS の `requestAnimationFrame` が回す |
| headless | `platform/headless/platform_headless.c` | **何もしない**。テクスチャは 1x1 ダミーで成功させる |

> **headless の「ダミーで成功させる」は地味に重要。**  
> サーバでも native と**同じ初期化経路**を通せる。「サーバのときだけ飛ばす」分岐を書かずに済み、分岐が生む状態ズレを未然に潰す。

## 3.3 判定ループ `game_step`（`core/loop.c`）

> **何を示すか**: サーバ・ブラウザ・native の全員が呼ぶ唯一の判定関数。1回呼ぶと `dt` 秒ぶん状態が進む。

```c
#ifndef SIM_BUILD   // ← native だけが使う駆動部。sim ビルドは丸ごと除外
int game_frame(t_game* game, double dt) {
    game_step(game, dt);                // 判定
    render_frame(game);                 // 描画
    pf_present(&game->window);          // 転送
    return 1;
}
#endif

int game_step(t_game* game, double dt) {
    double time_mult;

    if (game->cleared) return 1;
    time_mult = calc_time_mult(dt);
    update_death(game, dt);
    if (game->player && !is_player_dead(game))
        apply_input(game, time_mult);             // ローカルスロットの入力
    step_external_combatants(game, time_mult);    // ネットワーク越しのスロット
    update_enemies(game, dt);                     // AI
    game->mode_ops.combat(game);
    if (!game->cleared) check_quest(game);
    return game->cleared;
}
```

### フレームレート非依存 ― `time_mult`

`game_step` は毎秒何回呼ばれるか分からない（native は 60fps、サーバは 30Hz）。  
移動量を経過時間でスケールする:

```
time_mult = min(dt × 60.0, 3.0)
```

上限 `3.0`（`MAX_TIME_MULT`）は、デバッガ停止後などに `dt` が巨大になり**壁をすり抜けて瞬間移動する**のを防ぐため。

「いつ呼ぶか」はプラットフォームの責任。ビジーウェイトは廃止（ブラウザではタブが固まる）。

## 3.4 3つのビルドターゲット（Makefile）

> **何を示すか**: 同じソースから、リンクするファイル集合を変えるだけで3種を作る。

```make
# native: 全部 + MiniLibX
# render.wasm: main.c を除き、web プラットフォームを足す
# sim.wasm: 描画系ソースを丸ごと非リンク（★肝）
SIM_RENDER_EXCLUDES = main.c core/bmp.c engine/render/draw*.c \
    engine/render/screen.c engine/render/sprite.c \
    engine/render/cast_columns.c engine/raycast/raycast.c \
    engine/input/input.c ui/font.c ui/ui.c ui/crosshair.c
```

> **「描画しない」ではなく「描画コードが存在しない」**。  
> フラグ分岐ではなくリンク単位で消す。だから `sim.wasm` は構造的に画面を持てない。  
> サイズも `sim.wasm` 39KB に対し `render.js` 60KB と実測で差が出る。

## 3.5 付随した置き換え（入力・アセット）

キーコードの知識はプラットフォーム層の外に出さない。エンジンが受け取るのは論理入力 `t_input` だけ。

- native: X11 キーコード → `t_input`
- web: `KeyboardEvent.code` → `web_set_input(...)`
- サーバ: WebSocket の `{mv, yaw}` → `sim_set_input(...)`

XPM はブラウザにファイルシステムが無いので、**ビルド時に RGBA へ変換**（`make web-assets`）。実行時 XPM パースは廃止。

## 3.6 マップをメモリ上のテキストから読む（E-09）

> **何を示すか**: パース経路を1本にし、サーバがマップ本文をそのまま配れるようにした。

```c
int parse_config_text(t_config* config, const char* text);  // ★ 新設
int load_config(t_config* config, const char* path);        // 全読み → 上を呼ぶ
```

native も「ファイルを全部読んでから同じメモリリーダへ渡す」形に統一。  
全13マップで改造前後の dump がバイト一致することを確認済み。

## 3.7 サーバ向けの公開口（E-10 / E-11）― 設計意図

サーバから見えるエンジンは、公開 API **6関数 + `game_step`** に絞った。  
シグネチャとスナップショット配列のバイトレイアウトは **付録C**。

設計意図だけここに書く:

| 意図 | 内容 |
|---|---|
| プロセスを落とさない | `game_create` 失敗は `NULL`。`exit()` しない |
| スロットは後付け | `game_create` 時点ではスロット無し。`game_add_combatant` で埋める |
| AI スロットは入力無視 | `game_set_input` は AI へ書いても無視 |
| 切断＝入力源切替 | `game_set_input_source` で AI ⇔ EXTERNAL |
| JSON 化は Node | `game_snapshot` は `double` の平坦配列のみ。tick 付与も Node |
| 再現性 | `t_match_rules.seed` を固定すると同じ入力列で試合が再現する |

`make sim` → `web/build/sim.js` + `sim.wasm`（39KB）。  
検証: ASan/LSan、長時間ティック、**3モジュールインスタンス併走**（複数 GameRoom の前提）。

## 3.8 受信側 ― カメラの反転と補間（E-12）

> **何を示すか**: クライアントは自分の位置すら自分で決めない。過去2枚の snapshot の間を補って描く。

```
ローカルプレイ（従来）:  カメラが正本 → 戦闘員ノードへ同期
スナップショット駆動  :  戦闘員が正本 → カメラを完全導出   ★反転
```

サーバは 30Hz、ブラウザは 60fps 以上。そのまま描くとカクつくので補間する。

```
位置: 線形補間
向き: 最短弧（wrap 無しだと 179°→−179° が「ほぼ一周」に見える）
離散値（state / score / hand / alive / team）: 古い側の値をそのまま使う
```

**離散値を補間しないのが要点。** スコアの 3 と 4 の間に 3.5 は存在しない。

一方通行デモ: `sim.wasm` → JSON → ファイル → 補間 → `render.wasm`（`record.mjs` / `replay.html`）。  
W-10 では「JSON → ファイル」が「JSON → WebSocket」に置き換わるだけ。両端は完成済み。

# 4. ゲームロジック ― 戦闘員とルールの一般化

**この章で分かること**: なぜ `camera` 単独では足りなかったか、スロット統合、移動・死亡、オンライン向けルール、マップ。

対応する作業痕跡: **G-01〜G-10**。

## 4.1 問題 ― プレイヤーが特別すぎた

```
t_game
 ├ camera        ← これがプレイヤー。位置・向きの正本
 └ world.enemies ← NPC だけのリスト
```

この形では、(1) 2人目の人間を置く場所がない、(2)「この NPC を人間が操作する」ができない、(3) ゴール・追跡・接触が全部 `camera` を見ている。

## 4.2 やったこと ― プレイヤーを戦闘員リストへ（G-01〜G-04）

```
戦闘員リスト（world.enemies）
  スロット0  入力源 = EXTERNAL   ← ネットワーク越しの人間（または手元のプレイヤー）
  スロット1  入力源 = AI
  スロット2  入力源 = EXTERNAL   ← 別の人間
  スロット3  入力源 = AI
  （＋ マップ由来の敵ハザードも同じリスト。id は 8 番から）
```

全員が同じ型 `t_enemy`（＝戦闘員）。**違いは入力源だけ。**

```c
typedef enum e_input_source {
    INPUT_SRC_AI = 0,
    INPUT_SRC_EXTERNAL
} t_input_source;
```

| フィールド | 役割 |
|---|---|
| `input_source` / `input` | AI か EXTERNAL か。スロットが保持する入力（毎ティック上書き） |
| `radius` | 当たり半径。人間 0.5 / NPC 0.8（統合前の非対称を維持） |
| `death_timer` / `spawn` | 復帰待ち秒（**スロットごと**）と復帰地点（生成時に確定） |
| `dir_angle` | 向き（ラジアン。カメラを持たないスロットのため） |
| `combatant_id` / `is_player` | スロット番号（snapshot の識別子）／ローカル自スロットかの暫定フラグ |

## 4.3 移動と衝突の一本化（G-03）

> **何を示すか**: プレイヤー用／NPC 用だった移動を `combatant_walk_axis` 1本に統一。軸分割で壁ずりが起きる。

```c
void combatant_walk_axis(t_game* game, t_sprite* self, t_pos* pos, t_pos mv)
{
    next  = pos + mv;
    probe = next + WALL_MARGIN × sign(mv);
    if (next がマップ内 && 壁でない
     && probe がマップ内 && 壁でない
     && 他の戦闘員の当たり円に阻まれない)
        pos = next;
}
```

斜め移動は x / y を分けて2回呼ぶ。円衝突は「離れる移動は許す」でスタックを防ぐ（詳細定数は付録B）。

## 4.4 死亡と復帰をスロットごとに（G-04）

以前は `t_game.death_timer` が1個（プレイヤー専用）。戦闘員ノードへ移し、`t_game` 側は削除。  
**1vs1 ではスロットごとに死亡と復帰が独立する。**

## 4.5 この1変更で課題モジュールが3つ同時に成立する

| 課題モジュール | 実現方法 |
|---|---|
| **Multiplayer (3人以上)** | スロットを4つ埋めるだけ |
| **Remote players** | スロットの入力がネットワークから来るだけ |
| **AI opponent** | 空スロット・切断スロットの入力源を `AI` に切り替えるだけ |

> 「**NPC の入力を、ネットワーク越しの人間入力に差し替える**」――設計の中核。

## 4.6 ルールをオンライン対戦向けに一般化（G-05〜G-10）

### 先取点の引数化（G-05）

`match_rules.target_score`。0以下なら既定10。製品レンジ 3〜21 の検証は WS 層の責務（エンジンに製品ポリシーを二重化しない）。

### カメラ依存の除去（G-06〜G-08）― 最も厄介だった箇所

## 6.4 よくある疑問（FAQ）

### Q. `sim.wasm` と `render.wasm` の違いは？

**A.** 同じ C ソースから、リンクするファイルを変えて作る。`sim` は判定だけ（描画コード無し）。`render` はブラウザで絵を描く。正本の状態はサーバの `sim` 側。

### Q. 戦闘員とハザードの違いは？

**A.** 戦闘員はスロットに乗る参加者（人間または AI）。ハザードはマップ由来の敵でスロットではなく障害物（id は 8 から）。

### Q. なぜクライアントで勝敗を決めないのか？

**A.** サーバ権威。クライアントが判定するとチートとプレイヤー間のズレが構造的に起きる。クライアントは snapshot を描くだけ。

### Q. Issue の E / G / W / F は何か？

**A.** バックログのレーン接頭辞。E=Engine、G=Gameplay（本書の範囲で完了）、W=Backend/DevOps、F=Frontend。正本は `02_設計書/5-バックログ.md`。

# 付録A. レイキャスタの原理

> Cub3D で学習済みならこの付録は不要。  
> 改造の話には直接関係しないが、**第5章の解像度ノブ**はここの計算量から出る。

## A.1 基本の発想

3Dモデルは使わない。マップは2次元の文字配列のまま。  
**画面の横1列につき光線を1本飛ばし**、壁までの距離で縦線の高さを決め、横幅ぶん繰り返すと疑似3Dになる。

## A.2 カメラモデル

| 変数 | 意味 |
|---|---|
| `pos` | 位置（マス単位の小数） |
| `dir` | 視線方向の単位ベクトル |
| `plane` | カメラ平面。`dir` に直交し、長さが FOV（既定 0.66） |

```
ray_dir = dir + plane · camera_x[i]
camera_x[i] = 2·i / W − 1
```

`camera_x[]` は起動時に一度だけ計算（ホットループから割り算を追い出す）。

## A.3 DDA

素朴な微小ステップは遅い／すり抜けが起きる。  
**マス境界との交点だけを辿る**（縦線と横線の近い方へ1マスずつ）。  
`delta_dist = |1 / ray_dir|`。ループは比較1回＋加算2回程度。すり抜けしない。

## A.4 魚眼補正と壁描画

ユークリッド距離だと画面端が樽型に歪む。**カメラ平面に垂直な距離**を使う。  
壁の高さ `h = H / d`。テクスチャ座標は `wall_x` から求め、縦は加算のみの内側ループで書く。

## A.5 床・天井・スプライト

床天井の距離比は画面高だけで決まるので起動時テーブル化。  
スプライトはカメラ空間へ変換し、列ごとの depth バッファで壁の裏を隠す（1次元 Z バッファ）。遠い順に描画。

## A.6 計算量 ― 解像度ノブの根拠

```
コスト ≒ 画面幅 W × (DDA のマス数) + W × H × (テクスチャ書き込み)
       ≒ ピクセル数に比例
```

実測でも 1280×720 → 960×540（ピクセル数 0.56 倍）で 15.80ms → 8.93ms（0.57 倍）とほぼ比例。
