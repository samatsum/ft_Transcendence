Concept · Server-Authoritative Model

本当のゲームは、
サーバの中だけで進む。

ブラウザは勝敗を一切決めません。サーバが計算した状態の「写真」を受け取って、 すきまを補間しながら描くだけです。そしてこの「写真」に写る出演者は、 人間もAIも区別しない、たった1種類の「戦闘員」です。 この2つの決めごとが、Multiplayer・Remote players・AI opponent・切断復帰という 4つの要件を1つの仕組みで成立させています。

01 · Why server authority

なぜ「サーバだけが正しい」必要があるのか

4人でオンライン対戦をするとき、素朴に作ると「各プレイヤーのブラウザが、 それぞれ自分でゲームを計算する」形になります。これは必ず破綻します。 理由は2つです。

理由1

チート

ブラウザのコードは利用者が書き換えられます。「自分は無敵」「相手に勝った」と 自分のPCが言い張れてしまう。評価で必ず突かれる弱点です。

理由2

ズレ

通信には遅延があり、各自の計算が少しずつズレます。「Aの画面では勝ち、 Bの画面では負け」が起き、どちらが本当か決められません。

サーバ権威（server-authoritative）: ゲームの本当の状態はサーバの中だけに存在し、勝敗・スコア・位置は サーバが決める。ブラウザはそれを表示するだけ。この方式にすると、 チートは「サーバが認めないので無効」、ズレは「全員が同じサーバの状態を見るので 起きない」と、両方が原理的に消えます。

最重要の帰結: ブラウザ側（クライアント）に勝敗を決めるコードは1行も無い。 これは設計の建前ではなく、実際に game_apply_snapshot のコメントにも 「勝敗・スコアの正本はサーバであり、ここでは一切判定しない」と明記して守っています。

誰のCPUが計算するのか — 判定は集中、描画は分散

Webページを開くと、そのJavaScript / WASMは「あなたのPC」で動きます。 サーバのCPUは使いません。サーバからはデータ（スナップショット）を受け取るだけで、 描画はあなた自身のPCのCPUがやります。ブラウザは計算をサーバに 肩代わりさせる仕組みではありません。

計算どのCPUが実行するか
ゲームの判定（sim.wasm / game_step）サーバマシン1台（全員ぶんを1回だけ計算）
画面の描画（render.wasm）各プレイヤーのPC（各自が自分の画面を描く）

判定は1か所に集中（サーバ）→ チートもズレも消える。 描画は各自に分散（各ブラウザ）→ サーバは絵を描かないので軽い。 4人対戦なら描画は4台のPCが1画面ずつ分担し、サーバは判定だけです。

評価時だけの注意: この課題の評価は docker compose up で1台のマシン上で 行うため、Nodeサーバも確認用ブラウザも同じ物理マシンに同居します （ローカル評価の特殊ケース）。役割としては別で、2人が別々のPCで対戦すれば Aの描画はAのPC、Bの描画はBのPC、判定はサーバのPCと物理的に分かれます。

02 · Data flow

データの流れ（1往復）

全体像を先に1枚で。ブラウザは入力を送り、サーバは状態を返し、 ブラウザが描く、の1往復です。 

[ブラウザ] キー / マウス
      │  input を送信（30Hz）        ← mv（前後左右の押下ビット）と yaw（視点の絶対角）
      ▼
[サーバ] game_step で世界の状態を計算（30Hz）
        └ 位置・当たり判定・スコア・勝敗を決める（★絵は描かない）
      │  snapshot を送信（15〜20Hz）  ← 全戦闘員の位置・向き・スコア・生死…
      ▼
[ブラウザ] snapshot を貯めて now−100ms で補間
        └ render.wasm が「自分の画面」を描く（★描画はブラウザの仕事）

混同しやすい2点（実際によくある勘違い）

勘違い正しくは
ブラウザは「スナップショット」を送る ブラウザが送るのはinput。snapshotはサーバ→ブラウザの向きの言葉
サーバが「画面をどう描くか」を決める サーバが決めるのは世界の状態（位置・勝敗）だけ。描き方は各ブラウザが決めて自分で描く（サーバはheadlessで絵を持たない）

つまり、送る/返るデータは input と snapshot で別物、 そして「描く」のはサーバではなくブラウザ。サーバは「ボールはここ、 得点は2-1」と言うだけの審判で、各プレイヤーの画面映像そのものは 作りません。

例外は視点回転（yaw）だけ。 自分の見回しは、サーバの返事を待たずブラウザが即座に反映します（手応えを保つための 唯一の予測）。移動や勝敗は予測せず snapshot を待ちます。

03 · Snapshot

スナップショット＝ゲームの「写真」

サーバは1秒間に30回（30Hz）ゲームを進めます（game_step）。 その途中の状態を、定期的に写真に撮ってブラウザへ送ります。 これがスナップショットです。写真に写っているのは、表示に必要な最小限だけです。

中身例
試合の状態playing / finished、勝者、スコア
各戦闘員id・チーム・手・位置(x,y)・向き・生存・AIか・復帰までの秒

1回分で1KB未満に収まります（4人+数体なのでJSONで十分。実測で確認済み）。 正本のレイアウトは codes/includes/platform/sim.h です。

誰が何を担当するか（ここがW-10とF-06の境界）

サーバ（Node）                            ブラウザ
─────────────                            ─────────
game_snapshot()                          受信
  → フラットな数値の配列 ──JSON化──▶ WS ──▶ JSON
                                            → 補間（§04）
                                            → game_apply_snapshot()
                                            → 画面に描画

数値をJSONの文字列にするのはNodeの仕事（sim.wasmはしない）。 tick番号（何枚目の写真か）を振るのもNode。simは番号を持ちません。 この2点は「サーバ側の責務」として設計で切ってあります。

04 · Interpolation

補間（interpolation）＝ 写真と写真の「あいだ」を作る

ここで問題が起きます。サーバは1秒に30回進むが、配信はもっと粗い（例: 15〜20回/秒）。 一方ブラウザは1秒に60回描きます。つまり写真の枚数より、描く回数のほうが多い。 写真をそのまま出すと、キャラクターがカクカク（写真が届いた瞬間だけワープする）動きます。

「描画FPS」と「更新tick」は別物

FPS（1秒に何回"描く"か）は、絵を描く側だけの指標です。 サーバは絵を描かないのでFPSを持たず、代わりに「1秒に何回"世界を更新"するか」＝ tickレートを持ちます。この2つは別物で、値も目的も違います。

どこ持っているレート値なぜその値か
native（./cub3D）描画FPS60fps固定frame_delta（TARGET_FPS=60）が早すぎるフレームをスキップして抑える
ブラウザ描画FPSモニタのリフレッシュ（通常60。高リフレッシュ機はそれ以上）requestAnimationFrameがモニタに同期する
サーバ（sim）更新tick30Hz（配信は15〜20Hzに間引く）判定は30回/秒で充分。60に上げても通信量が倍になるだけ

描画FPSの上限は「人の目とモニタ」。60Hzモニタなら60fps以上描いても見えません。 更新tickの上限は「判定の精度と通信量」。だからあえて描画より遅く（30Hz）回します。

30Hzはengine固定値ではなく、サーバ層の「ノブ」です。 game_step(game, dt) はdtを引数で受けるので、tickレートは呼ぶ側 （NodeのsetInterval。デモはTICK_HZ=30）が決めます。 30→60と書き換えれば上げられ、移動量はdt比例なので ゲームの速さは変わりません。ただし①サーバCPUが増える（×ルーム数） ②このゲームでは精度の見返りが小さい③seed固定のデモ・テストのbyte一致再現が崩れる、 というトレードオフがあります。tick（判定）・配信・描画FPSは独立に調整可能 （例: tick 60だが配信は20のまま、も可）。

そして、まさにこの「描く60回 vs 届く15〜20回」のズレを埋めるのが、補間です。 2枚の写真の「あいだ」を計算で埋めます。

よくある誤解: 「2枚の写真から1枚の絵を作る」ではありません。 そう読むと「15回しか届かないなら7.5fpsしか描けないのでは？」となりますが、違います。 補間が作るのは「2枚のあいだの、好きな時刻の状態」です。 「どこまで進んだか」を表すalphaは0.0〜1.0の連続値なので、 同じ2枚を使い回して何フレームでも描けます。 
写真A ●───────────────────────● 写真B      ← 66.7ms 離れている（15Hz）
      ↑      ↑      ↑      ↑
   α=0.0  α=0.25  α=0.5  α=0.75            ← 60fps なら 4 フレーム分

つまり届く回数は、描く滑らかさを決めていません。では配信を増やすと 何が良くなるのか。軌跡の正確さです。補間は2点を直線で 結ぶので、その間に実際のシムが曲がっていると、ショートカットして少しズレます。 15Hzなら66.7msぶんのズレで、歩く速さでは数センチ相当。目では分かりません。 その代わり通信量は30Hzの半分で済みます。

なぜ15なのかは「100ms過去を描く」（後述）と関係します。補間するには 「描きたい時刻を挟む2枚」が常に手元に要るので、100msの遅らせ分は 写真1枚ぶんの間隔＋通信のゆらぎを吸収する予算です。

配信写真の間隔100msの予算に対して
30Hz33.3ms余りすぎ（通信量を倍払う意味がない）
15Hz（採用）66.7ms余り33ms。1枚遅れても耐えられる
10Hz100ms余りゼロ。1枚落ちると位置が飛ぶ

補間のしくみ（数値例つき）

名前は難しそうですが、やっているのは割り算とかけ算だけです。式は1本。 

描く値 = A + (B - A) × alpha

alpha（アルファ）は「AとBの、どのへんか」を0〜1で表した割合です。 alpha=0ならちょうどA、0.5ならまんなか、1ならちょうどB。

具体例。写真A（時刻0.00秒・位置10）と写真B（時刻0.10秒・位置20）があり、 いま0.07秒の絵を描きたいとします。

手順1 — alpha（どのへんか）を出す

alpha = (描きたい時刻 - Aの時刻) / (Bの時刻 - Aの時刻)
      = (0.07 - 0.00)  / (0.10 - 0.00)
      = 0.7                          ← A と B の 70% の地点

手順2 — その割合で混ぜる

位置 = 10 + (20 - 10) × 0.7 = 17     ← 位置 17 に描く

これを毎フレーム（1秒60回）やります。時間が進むとalphaが 0 → 0.2 → 0.5 …と増えるので、キャラはAの位置からBの位置へすーっと滑って いきます。アニメの「中割り」と同じ発想です。 

0.00秒 alpha=0.0 → 位置10
0.05秒 alpha=0.5 → 位置15
0.07秒 alpha=0.7 → 位置17
0.10秒 alpha=1.0 → 位置20   ← ここで次の写真Cに切り替え、また alpha=0 から

実際のコード（web/sim_demo/replay.js）も、この2手順そのものです。 

alpha = (playT - timeOf(cur)) / (timeOf(next) - timeOf(cur));  // 手順1
alpha = Math.min(1, Math.max(0, alpha));                       // 0〜1 に収める
const flat = window.Cub3DSnapshotInterp.interpolate(cur, next, alpha);  // 手順2
補間は「予測」ではありません。 AもBもすでに手元にある確定データです。やっているのは 「既知の2点のあいだを埋める」ことで、未来を当ててはいません。 だから外れようがない。これが「100ms過去を描く」理由（後述）とつながります。

「同じ物体」はどう対応づけるのか — idで照合

「Aの物体aとBの物体aを、どうやって同じものだと判定しているのか」。答えは、 戦闘員が持つ変わらないid（席番号）で突き合わせている、です。

  1. 写真Bを早見表にする「id → 戦闘員」のMapに変換する
  2. 写真Aの戦闘員を1人ずつ見る同じidをBの早見表から引く
  3. 見つかった2つを補間するAのその席・Bのその席の位置・向きを補間する
const later = new Map(d1.combatants.map((c) => [c.id, c]));  // B を id で引ける表に
d0.combatants.forEach((c) => {
	const next = later.get(c.id);   // A の戦闘員 c と同じ id を B から探す
	if (!next) return;              // B に居なければ補間しない（A の値のまま）
	// c（A側）と next（B側）の位置・向きを補間する
});

リストの並び順では照合していません（並びが違っても平気）。 idという「背番号」で突き合わせるので、途中で順番が変わっても・誰かが消えても 正しく対応します（消えた席は受け口 game_apply_snapshot が画面外へ退避させます）。

ピクセルは混ぜていない。状態を混ぜて描き直す

ここが一番大事で、直感と違うところです。2枚の写真のピクセル（色）は、 一切混ぜていません。 

写真A・写真B（各戦闘員の位置・向き）
      │  id で照合して、位置と向きだけ補間
      ▼
「いまの瞬間の全戦闘員の位置・向き」という数値
      │  これを C の t_game に書き込む
      ▼
C がその位置から 3D シーンを丸ごと描き直す（レイキャスト）
      ▼
新品のピクセルが毎フレーム出来上がる

つまり「絵と絵を混ぜている」のではなく、「登場人物を正しい位置に置き直して、 毎フレーム3Dを一から描いている」。もしピクセルを混ぜたら、半透明の残像のような 気持ち悪い絵になります。実際は「敵は座標(17,8)・向き0.7」と数値を確定してから、 その敵を通常どおりくっきり描くので、いつも鮮明です。

補間の対象は「数十個の数値」だけです（4人×位置2＋向き1＝12個ほど）。 画面は約96万ピクセルありますが、そのどれも補間していません。 だから軽い——ここが直感に反する肝です。

実物（web/snapshot_interp.js）:

// 位置は線形（まっすぐ按分）
out[o + 3] = c.pos[0] + (next.pos[0] - c.pos[0]) * alpha;   // x
out[o + 4] = c.pos[1] + (next.pos[1] - c.pos[1]) * alpha;   // y
// 向きは「最短の回り方」で
out[o + 5] = lerpAngle(c.dir, next.dir, alpha);

向きだけ特別扱いしているのに注目してください。角度は360°＝0°で 一周するので、359°から1°へ動くとき、素直に按分すると逆回り（長いほう）に 358°ぐるっと回って見える。それを防ぐため lerpAngle が 「短いほうの弧」で回します。 

function lerpAngle(a, b, alpha) {
	let diff = b - a;
	while (diff > Math.PI)  diff -= 2 * Math.PI;   // 半周を超えたら
	while (diff < -Math.PI) diff += 2 * Math.PI;   // 逆側から回る
	return a + diff * alpha;
}

位置と向きは補間する。でも「勝敗」は補間しない

補間するのは位置・向きという連続的に動く値だけです。 スコア・生死・勝者・手（グー/チョキ/パー）は、古いほうのsnapshotの値を そのまま使います。これらは「7点」「死んでいる」のように飛び飛びの値で、 あいだを作る意味が無いし、勝手に作るとサーバの判定と 食い違うからです。ここでも「クライアントは判定しない」が徹底されています。

なぜ「100ms前」を描くのか

補間には「AとBの2枚」が必要なので、Bが届くまでAのあとを描けません。 そこで、ブラウザはわざと100ms過去の時刻を描きます。こうすると、 描こうとする時刻の前後の写真が必ず手元にある状態になり、常に補間できます。

代償は「見えている世界が100ms遅れる」ことですが、視点の回転だけは例外で、 自分のマウス操作は待たずに即座に反映します（回転はサーバの許可を 待たなくてもズレないため）。これで操作の手応えは保たれます。

05 · Client receiver & working demo

ブラウザ側の受け口と、これが動く実例

補間した数値を、Cの描画エンジンに渡すのが game_apply_snapshot です。 

// codes/srcs/platform/web/web_snapshot.c
int game_apply_snapshot(t_game* game, const double* snap, int len, int view_id)
{
	// snap（補間済みの写真）を、表示用の t_game に書き込むだけ。
	// 勝敗・スコアの正本はサーバであり、ここでは一切判定しない。
	// view_id の席＝自分はカメラになり、他の席は敵スプライトとして描く。
}

ポイントは、このモードでは game_step を呼ばないことです。 ローカルで計算するとサーバの正本とケンカするので、ブラウザは 「写真を貼り替えて描くだけ」に徹します。 view_id は「4人のうち自分がどの席か」です。自分の席はカメラ （一人称視点）になり、残り3席は敵スプライトとして描かれます。

これが動く実例

本番のNodeサーバ（W-10）はまだ未実装でも、一方通行の全経路が動くデモがあります。 

web/sim_demo/record.mjs    sim.wasm を回して写真を撮り、snapshots.json に保存
        │  （＝サーバ役）
        ▼
web/sim_demo/replay.html   snapshots.json を読み、補間して描画（＝ブラウザ役）
F-06は、この replay.html の「snapshots.json を読む」 ところを「WSで受信する」に差し替えるだけでGameViewになります。 補間（snapshot_interp.js）と受け口（game_apply_snapshot）は そのまま流用できます。

06 · Combatant unification

戦闘員統合 — 人もNPCも同じリスト

プレイヤーも敵も「戦闘員」という同じ1種類にまとめ、違いは 『誰が操作を決めるか』だけにした、という話です。これが 「Multiplayer 3+」「Remote players」「AI opponent」の3モジュールを 1つの仕組みで成立させる鍵になっています。

元のcub3Dの構造と、その限界

元のcub3Dは、はっきり2種類に分かれていました。

プレイヤー  = カメラ（画面の視点）。世界にただ1人
敵（NPC）   = t_enemy のリスト。複数いる

この作りだと、オンライン対戦にするとき困ります。

  • 対戦相手（人間）は「敵」なのか「プレイヤー」なのか？
  • 4人対戦なら、残り3人はプレイヤーであり、同時に自分から見れば敵でもある
  • 席が切断したら、そこをAIに差し替えたい。でもプレイヤーとNPCが 別構造だと、差し替えのたびに種類そのものを変換しなければならない

「プレイヤー」と「NPC」を別物として作ると、接触判定・描画・写真 （スナップショット）のすべてが2系統になり、永久に複雑さを抱えます。

統合後の考え方

そこで、全員を「戦闘員（combatant）」という1種類のノードにまとめました。 プレイヤーも、world.enemies という同じリストの中の1要素になります。 

world.enemies（戦闘員リスト）
  ├─ 戦闘員0  ← 自分（人間）
  ├─ 戦闘員1  ← リモートの人間
  ├─ 戦闘員2  ← AI
  └─ 戦闘員3  ← AI

違いはたった1つ、「入力源（input_source）」だけです。 

// codes/includes/enemy/enemy_types.h
typedef enum e_input_source
{
	INPUT_SRC_AI = 0,        // AI が操作を決める
	INPUT_SRC_EXTERNAL       // 外部（キーボード、将来は WS 経由の人間）が操作を供給
}	t_input_source;
  • AI席: その場でモード別AIが「前へ進む」「じゃんけんはグー」などを決める
  • EXTERNAL席: 外から届いた入力（t_input）をそのまま使う
移動も当たり判定も描画も、全員まったく同じコードを通ります。 入力を「AIが作る」か「外から来る」かだけが分岐点です。

07 · One structure, three modules

これが3モジュールを一度に解決する

この1つの構造が、課題の3モジュールを同じ仕組みで満たします。

モジュール統合構造でどう成立するか
Multiplayer 3+（4人対戦）戦闘員リストに人間のEXTERNAL席を4つ並べるだけ
Remote players（リモート対戦）EXTERNAL席の入力を「WS経由の人間入力」にするだけ
AI opponent（AI対戦相手）席の入力源をAIにするだけ

そして切断・再接続が、この設計の一番おいしいところです。 

人間がプレイ中          →  input_source = EXTERNAL
       │ 切断
その席を AI が代替       →  input_source = AI      （席はそのまま。中身は動き続ける）
       │ 再接続
人間が戻る               →  input_source = EXTERNAL

席の種類を変換する必要がありません。 input_source という値を EXTERNAL ⇄ AI で切り替えるだけ。だからW-12（切断・AI代替）は、 専用のAPI1つ（game_set_input_source）で済みます。

元のRSPが、すでにこの形に近かったのが大きな資産でした。 RSPは元から「プレイヤー1人＋NPC3体＝4戦闘員」で、じゃんけんの勝敗判定も 「全部の異チームペアを見る」作りだったので、統合の差分が最小で済みました。

08 · What a combatant holds

「戦闘員」が持つ主な情報と、唯一の例外

1つのノード（t_enemy）が、席として必要なものを全部持ちます。抜粋すると:

フィールド意味
input_sourceAIかEXTERNALか（唯一の本質的な違い）
inputその席が保持している操作（EXTERNAL席はここに外部入力が入る）
is_player自分の席か（自分の身体は描かない＝カメラになる）
combatant_id席の番号。スナップショット・APIが席を特定する鍵
is_hazardマップ由来の敵'M'か（下記参照）
death_timer / spawn死亡演出と復帰地点（席ごとに持つ）
rspRSPの状態（チーム・手・生死）

is_player の席だけは、身体のスプライトを描画リストに繋ぎません。 自分はカメラ（視点）になるので、自分の身体は画面に映らない——元のcub3Dと同じです。

例外: ハザード（マップの敵'M'）は「席」ではない

1つだけ、戦闘員リストに居るが席ではないものがあります。 FPSモードのマップに置かれる敵'M'（is_hazard = 1）です。 ハザードは「プレイヤーを邪魔する障害物」で、次の点で席と違います。

  • アイテムを拾わない
  • ゴールに入っても試合を終わらせない
  • 接触した席を死なせる側になる（G-08。当たると数秒リスポーン待ちのペナルティ）

同じリストに置きつつ is_hazard で見分けることで、描画（スプライトとして描く）は 共通化しつつ、ルール上の扱いだけ分けています。

スナップショットとの関係

スナップショットの節で「各戦闘員の位置・向き・手を送る」と 書きましたが、その『戦闘員』がまさにこの統合ノードです。送る側は、 リストを頭から舐めて1ノードずつ写真に写すだけ。「これはプレイヤー」「これはNPC」 という分岐が要りません。受け取るブラウザも区別せず、全員を同じスプライト 描画で描きます（自分の席だけカメラにする）。

統合していなかったら、写真も「プレイヤー欄」と「敵欄」の2系統になり、 補間も受け口も倍の複雑さになっていました。

09 · Summary

まとめ

サーバ権威 / スナップショット / 補間

  1. 本当のゲームはサーバの中だけで進む（サーバ権威）。チートとズレを原理的に消すため
  2. データの流れは1往復ブラウザが input（mv/yaw）を送る → サーバが状態を計算 → snapshot を返す → ブラウザが補間して描く。描くのはブラウザでサーバは絵を持たない
  3. クライアントに勝敗判定コードは無い徹底して守られている
  4. サーバは写真を定期配信する1KB未満・JSON
  5. 2枚のあいだを補間して滑らかに描く位置と向きだけ。スコア・生死は補間せず古い写真の値を使う。予測ではなく既知2点のあいだ埋め。物体の対応はidで照合し、数値を混ぜて毎フレーム描き直す
  6. 100ms過去を描くことで常に補間できるただし自分の視点回転だけは即時

戦闘員統合

  1. プレイヤーもNPCも「戦闘員」1種類にまとめるworld.enemiesの同じリストに置く
  2. 違いは input_source だけAIかEXTERNALか。移動・判定・描画は全員共通
  3. 3モジュールが1つの仕組みで成立Multiplayer 3+ / Remote players / AI opponent
  4. 切断→AI代替→復帰は input_source の切り替えだけ席の変換が要らない（W-12）
  5. 元のRSPが既にこの形に近く、統合の差分が最小例外はハザード（'M'）。is_hazard で見分ける

10 · FAQ

テクニカルリード自己確認 — サーバ権威と戦闘員統合の抜粋

コード想定Q&A から、このページのテーマ（サーバ権威・スナップショット・補間・戦闘員/席の統合）に 関わる項目だけを抜粋しています。他のテーマ（engine/pf_*構造、buildターゲット、 WASM、ディレクトリ構成、.cubマップ）の項目は他のページに分けています。

Q

プレイヤーとNPCはどう区別している？

A. 区別しない。両方 world.enemies の1ノード （t_enemy）で、違いは input_source（AI / EXTERNAL）だけ。自席は is_player。

確認: codes/includes/enemy/enemy_types.h（t_enemy / t_input_source）

Q

外部入力席（サーバの人間）はどこで動く？

A. step_external_combatants が input_source==EXTERNAL かつ非自席の生存席へ、保持中の t_input を適用。native/web単体では該当席が無くno-op。

確認: codes/srcs/common/core/combatant.c:22

Q

サーバから使うAPIは？ 呼び出し順は？

A. game_create → game_add_combatant ×定員 → 毎tick sim_set_input → game_step → game_snapshot → JSON化（Node）。game_set_input_source で席をAI⇔外部に切替。

確認: 正本 includes/platform/sim.h / 実装 platform/headless/sim_api.c

Q

スナップショットの形は？ tickは誰が付ける？

A. フラットなf64配列（ヘッダ5＋戦闘員1人9）。 tickはsimが持たずNodeが採番、JSON化もNodeの責務。 レイアウトはsim.hの#defineが正本。

確認: includes/platform/sim.h（SIM_SNAP_*）/ platform/headless/sim_api.c:261（game_snapshot）

Q

game_apply_snapshot は誰が使う？ どこにある？

A. クライアント専用（サーバは使わない）。 idで戦闘員を照合し、表示用 t_game に書く。勝敗は一切判定しない。

確認: platform/web/web_snapshot.c:42
