説明用ドキュメント · ビルドと実行

同じ C のゲームを、
3 つの環境で動かす。

ft_transcendence のゲームロジックは C のソース 1 つしかありません。 それでも make は Linux の実行ファイルを、 make web はブラウザ用の WASM を、 make sim は Node サーバ用の WASM を作ります。 このページでは「何を作り分けているか」「誰がゲームループを回しているか」 「なぜ TypeScript のサーバが C のコードを実行できるのか」を 1 本にまとめます。

● 対象 チームメンバー全員

3つのビルドターゲット 誰がループを回すか WASM入門 FAQ

01 · Build targets

同じ C のソースから、用途の違う 3 つの成果物を作り分ける

ゲームロジックのソース（codes/srcs/common, fps, rsp）は 3 ターゲットとも同じです。違うのは「どの pf_* 実装を混ぜるか」と 「描画のコードを入れるか外すか」だけ。1 つの脳みそを、3 つの体に載せ替えるイメージです。 

                共通のゲームロジック（移動・衝突・敵AI・じゃんけん・スコア）
                        codes/srcs/common, fps, rsp
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
    make                        make web                    make sim
        │                           │                           │
   platform/native            platform/web               platform/headless
   ＋描画すべて                ＋描画すべて                 描画は除外
        │                           │                           │
        ▼                           ▼                           ▼
   cub3D（ネイティブ）        render.wasm（ブラウザ）      sim.wasm（サーバ）
コマンド成果物何のためのものか
makecub3D（Linux 実行ファイル）開発・回帰確認用。従来の cub3D そのもの
make webweb/build/render.js + .wasmブラウザで描くためのもの。画面担当
make simweb/build/sim.js + .wasmサーバで判定するためのもの。頭脳担当
make testcodes/tests/sim_test（実行ファイル）受入テスト。85 検査を自動実行

（make test は成果物というより検証用ですが、ビルドの一種なので並べています。）

make · 開発の足場

native（cub3D）

MiniLibX を使い、X11 のウィンドウを開いて動く従来どおりの cub3D。 全期間を通じて「壊れていないこと」を確認する基準です。 3 つのうち唯一 MiniLibX を必要とするビルドです。

make web · 画面担当

web（render.wasm）

ブラウザの <canvas> に描くための WASM。 サーバから届いたスナップショットを描くだけで、 自分ではゲームを判定しません。

make sim · 頭脳担当

server（sim.wasm）

Node サーバの中で回す、画面を持たないゲーム本体。 唯一の正しい状態を計算します（サーバ権威）。30Hz で game_step を回し、 状態のスナップショットを返します。

それぞれ詳しく

make（native）

make          # → ./cub3D が出来る
./cub3D maps/rsp_map/rsp.cub

エンジンをいじったら、まず make して両モードが動くかを見ます。

make web（render.wasm）

make web      # → web/build/render.js + render.wasm

make web は最初に web-assets（XPM 画像を RGBA へ変換）も走らせます。 ブラウザは XPM を読めないので、事前変換が要ります。 動かすには HTTP サーバが要ります（file:// では wasm を fetch できません）。

make sim（sim.wasm）

make sim      # → web/build/sim.js + sim.wasm

ここが肝心な点です。sim.wasm には描画のコードが物理的に入っていません。 Makefile の SIM_RENDER_EXCLUDES が draw.c / raycast.c / sprite.c / font.c などをリンク対象から外しているので、 「描画シンボルが無い」状態で成立します。

make test（受入テスト）

make test     # → sim_test をビルドして即実行。85 検査

sim.wasm と同じソース構成（headless）を、emcc ではなく普通の gcc で ネイティブの実行ファイルにしたもの。ブラウザも Node も要らずに走ります。 G-05〜G-09 のルール（先取点・ゴール・スポーン・ハザード・マップ）が仕様どおり動くかを 自動検証する、エンジンを壊す変更を検知する安全網です。

「描く担当」と「判定する担当」に分けた理由

render.wasmsim.wasm
どこで動くブラウザNode サーバ
描画するするしない
ゲームを判定するしないする（唯一の正）
何個動く各プレイヤーに 1 つ1 試合に 1 つ（複数試合なら複数）

判定を 1 か所（sim.wasm）に集めるからチートもズレも消える。 描画を各ブラウザ（render.wasm）に任せるから軽い。役割を割ったわけです。

CI が 3 つとも毎回ビルドする

GitHub Actions（.github/workflows/ci.yml）が、push のたびに 3 ターゲット全部をビルドし、make check（lint）・ make test・native の起動スモークまで走らせます。 これは単なる確認ではなく安全装置です。たとえば common/ に MLX を持ち込むと make web / make sim が落ちるので、 共通コードを壊す変更がすり抜けられません。 「3 つとも緑になった」＝「3 環境どれも壊していない」の保証になります。

02 · Loop inversion

誰がゲームを回しているか

ゲームを「回す人」を、環境ごとに差し替えられるようにした話です。 Linux ではライブラリが、ブラウザではブラウザが、サーバでは Node が回します。 この作りのおかげで、ゲームのロジックそのものは 3 か所で 1 つのままでいられます。

ループとは何のことか

ゲームは、ものすごく速いパラパラ漫画です。1 秒間に 30〜60 回、次のことを繰り返します。 

①入力を読む → ②状態を更新（移動・当たり判定・勝敗） → ③画面を描く → ①へ戻る

この「①へ戻る」をやり続ける仕組みがループです。 誰かがこのループを回し続けないと、ゲームは 1 枚目で止まったままになります。 問題は、この「回す人」が環境によって全然違うことです。

元の cub3D はどうだったか

元の cub3D は、回す人＝MiniLibX（MLX）でした。main() の最後はこうです。 

// codes/srcs/common/main.c
pf_setup_hooks(&game);   // 「毎フレーム main_loop を呼んで」と MLX に予約
pf_loop(&game.window);   // ← ここで MLX に制御を渡す。★もう return してこない★

pf_loop の native 実装は、たった 1 行です。

// platform_native.c
void pf_loop(t_window* window) { mlx_loop(window->ptr); }

mlx_loop（codes/minilibx-linux/mlx_loop.c）は、 42 から配布された MLX ライブラリの中にある無限ループです。中身を削ると: 

int mlx_loop(t_xvar *xvar)
{
	while (win_count(xvar) && !xvar->end_loop)   // ★これがループ本体
	{
		while (... XPending(xvar->display))       // 溜まった入力イベントを捌く
			mlx_int_param_event[ev.type](...);    //   → key_press など
		if (xvar->loop_hook)
			xvar->loop_hook(xvar->loop_param);    // ← やることが無いとき main_loop(game) を呼ぶ
	}
	return (0);
}

loop_hook に入っているのが、pf_setup_hooks で登録した main_loop です。 つまり MLX が、暇なたびに main_loop を延々と呼ぶ。これが元の構造でした。

ここが移植の壁だった

mlx_loop は Linux の X11 専用です。ブラウザにも Node にも存在しません。 そして「回す人」が MLX だと、ゲームを動かすには必ず MLX が要ることになります。

「反転」とは何をしたのか

やったことは一言でいうと、「回す人」と「1 フレーム分の処理」を切り離したことです。

Before（元の cub3D）

MLX（回す人） ──呼ぶ──▶ main_loop（1フレーム分の処理）
        ↑ この2つが癒着していて、引き剥がせない

main_loop は「MLX から呼ばれる」ことが前提の関数でした。 MLX が居ないと呼んでもらえない＝動かせません。

After（反転後）

      1フレーム分の処理を、引数付きの「ただの関数」として公開する
                    game_step(game, dt)
                          ▲
        ┌─────────────────┼─────────────────┐
   MLX が呼ぶ          ブラウザが呼ぶ        Node が呼ぶ
   （native）           （web）            （server）

「1 フレーム分の処理」を、誰からでも呼べる普通の関数にした。 すると「回す人」は誰でもよくなります。これをループ反転と呼んでいます （制御の向きが「ライブラリ→自分のコード」から「自分のコード←いろんな駆動元」に変わるので「反転」）。

3 つの「回す人」

同じ game_step を、3 者が別々の方法で呼びます。

環境回す人ループの正体1 フレームで呼ぶもの
native MLX mlx_loop の while（C・ライブラリ内） main_loop → game_frame → game_step + render_frame + pf_present
web ブラウザ requestAnimationFrame（JS） tick → web_render（= game_step + render_frame）→ JS が Canvas へ転送
server Node setInterval（JS。W-10 で実装予定） game_step のみ（描画しない）

3 つとも「回す人」が違うのに、game_step は 1 つ。これがこの設計の狙いです。

web の実物（web/engine_demo.js）

function tick(now) {
	const dt = Math.min((now - last) / 1000, 0.05);  // native の frame_delta に相当
	last = now;
	moduleRef._web_render(dt || (1 / 60));           // C を呼ぶ（game_step + render_frame）
	present(moduleRef);                              // JS が Canvas へ転送（後述）
	requestAnimationFrame(tick);                     // ★次のフレームで自分をまた呼ぶ
}

最後の requestAnimationFrame(tick) が、native の mlx_loop の while に相当します。 「次に画面を描くタイミングで、また tick を呼んで」とブラウザに予約する。 ブラウザはモニタのリフレッシュ（普通 60Hz）に合わせて呼び返すので、延々と回ります。

server の実物（現状は web/sim_demo/record.mjs）

本番の Node サーバ（W-10）はまだ未実装ですが、同じ構造の動く例がデモにあります。 

let tick = 0;
while (tick < MAX_SECONDS * TICK_HZ) {       // TICK_HZ = 30
	driveExternalSeat(tick);                 // 外部（人間）入力を入れる
	const finished = M._game_step(game, 1 / TICK_HZ);   // ★同じ game_step を呼ぶ
	tick++;
	if (tick % 2 === 0) snapshots.push(takeSnapshot(tick));  // 状態を記録して配信
	if (finished) break;
}

ここには render_frame も present もありません。サーバは描かないからです。 本番ではこの while が setInterval(..., 1000/30) に変わるだけで、中身は同じです。

「回す人」が違うと、描画の担当も変わる

native の game_frame は、1 フレームの中で pf_present（画面転送）まで C がやっていました。 web はここが違います。 C は「絵をメモリに書く」ところで止め、 Canvas に映すのは JS の仕事にしました。 

// web_main.c ― C 側。pf_present を呼ばない
int web_render(double delta_time)
{
	game_step(&g_game, delta_time);   // 状態を進める（3環境共通）
	render_frame(&g_game);            // フレームバッファ（メモリ）に絵を描く
	return (1);                       // ← ここで return。転送はしない
}
// engine_demo.js ― JS 側の present。これが web での「pf_present の中身」
function present(Module) {
	const ptr = Module._web_framebuffer_ptr();   // C が描いたバッファの場所を聞く
	const src = Module.HEAPU8;                    // WASM のメモリを直接読む
	for (...) {
		rgba[out]     = src[i + 2];   // B ┐ MLX は BGRA 並び、Canvas は RGBA なので
		rgba[out + 1] = src[i + 1];   // G │ ここで並び順を入れ替える
		rgba[out + 2] = src[i];       // R ┘
		rgba[out + 3] = 255;
	}
	ctx.putImageData(image, 0, 0);    // ← ここで初めて Canvas に絵が出る
}

C は「メモリに書く」、JS は「Canvas に映す」と役割が割れています。 だから web_framebuffer_ptr() のような「バッファの場所を教える関数」が要ります。

まとめ

ループ＝パラパラ漫画をめくり続ける仕組み。元の cub3D は MLX が回す人だったが、 MLX は Linux 専用なのでそのままでは移植できない。そこで「1 フレーム分の処理」を game_step という普通の関数に切り出した（ループ反転）。すると回す人は誰でもよくなる。 native=MLX / web=ブラウザ(rAF) / server=Node(setInterval)。 game_step は 3 環境で 1 つ。回す人と描く担当だけが環境ごとに違う。

03 · WebAssembly

なぜ Node で C を動かせるのか

C のコードを「ブラウザや Node が実行できる形」に翻訳した、それが WebAssembly（WASM）です。 「TypeScript のサーバが C のゲームを動かす」という、一見あべこべな構成が成り立つ理由を説明します。

何が不思議に見えるか

私たちの構成は、こう聞くと変に感じます。

Node（JavaScript の実行環境）の中で、C で書いたゲームエンジンが動いている。

普通、C はコンパイルして「その OS 専用の実行ファイル（Linux なら ELF）」になります。 JavaScript の世界とは別物のはずです。なぜ Node が C を動かせるのか。 答えは「C を、実行ファイルではなく WebAssembly という中間形式にコンパイルしたから」です。

WebAssembly（WASM）とは

WASM は、ブラウザや Node が直接実行できる、低レベルなバイナリ形式です。 

ふつうの C     →  Linux 実行ファイル（cub3D）   … Linux でしか動かない
WASM 向けの C  →  .wasm ファイル                … ブラウザでも Node でも動く

ポイントは、WASM が特定の OS ではなく「ブラウザ/Node の仮想マシン」向けであることです。 だから 1 つの .wasm が、ブラウザでも Node でも同じように動きます。 そして WASM はネイティブに近い速さで動くよう設計されています。JavaScript に 翻訳し直すのではなく、そのまま高速に実行されます。だからレイキャストのような重い計算も 現実的な速度で回ります。

なぜこれを使うのか

私たちはC のゲームロジックを 1 つに保ちたい。WASM なら、その C を ブラウザ（描画）でも Node（判定）でも動かせます。TypeScript に書き直す （＝ロジックの二重管理）を避けられるのが最大の理由です。

誰が翻訳するのか — Emscripten

C → WASM の翻訳をするのがEmscripten（emcc）というコンパイラです。 gcc の代わりだと思ってください。 

gcc  ...   →  cub3D          （Linux 実行ファイル。make）
emcc ...   →  sim.wasm ＋ sim.js  （WASM ＋ 橋渡しの JS。make sim）

注目してほしいのは、emcc が2 つのファイルを吐くことです。

ファイル中身役割
sim.wasm翻訳された C 本体実際に動くゲームロジック
sim.js（glue）Emscripten が自動生成する JavaScriptJS と WASM の橋渡し

.wasm は単体では使いにくい（メモリの確保や関数呼び出しの作法が生々しい）ので、 それを JS から扱いやすくする「glue（糊）コード」が一緒に生成されます。 私たちが Node から呼ぶのは、この sim.js です。

実際に Node から呼んでいるところ

web/sim_demo/record.mjs が、まさにこれをやっています。

// glue（sim.js）を読み込む
const createSim = require(here('../build/sim.js'));

// WASM を初期化して、モジュール M を得る
const M = await createSim();

// あとは C の関数を M._関数名(...) で呼べる
const game = M._sim_create(mapPtr, 1, TARGET_SCORE, SEED);   // C の sim_create
M._game_step(game, 1 / 30);                                  // C の game_step
M._game_snapshot(game, snapPtr, 256);                        // C の game_snapshot

C で書いた sim_create / game_step / game_snapshot が、 JS から M._sim_create のように普通の関数として呼べています。 これが「Node で C を動かす」の実体です。

_（アンダースコア）の意味

C の関数は WASM に入るとき名前の頭に _ が付く決まりになっています。 だから JS 側は M._game_step と書きます。

ひとつだけ知っておくべき癖 — メモリの受け渡し

JS と C はメモリの扱いが違うため、文字列や配列をやり取りするときだけ ひと手間かかります。数値（int / double）はそのまま渡せますが、 文字列やバッファは「WASM のメモリ上の住所（ポインタ）」で渡す必要があります。

record.mjs で .cub のテキスト（文字列）を渡す部分がそれです。

function writeCString(text) {
	const bytes = new TextEncoder().encode(text);
	const ptr = M._malloc(bytes.length + 1);   // WASM のメモリを確保して住所をもらう
	M.HEAPU8.set(bytes, ptr);                  // その住所へ文字列を書き込む
	M.HEAPU8[ptr + bytes.length] = 0;          // C の文字列は末尾 \0 が要る
	return ptr;                                // 住所（ポインタ）を返す
}

const mapPtr = writeCString(mapText);
const game = M._sim_create(mapPtr, 1, ...);    // 住所を渡す
M._free(mapPtr);                               // 使い終わったら解放

M.HEAPU8 はWASM のメモリを JS から覗く窓です。 C が書いた結果を JS がこの窓から読み取ります。

W-10 の実装では、この writeCString の作法がそのまま使えます。 難しいのは最初だけで、record.mjs にひな型が揃っています。

native / web / server との対応

同じ C から作った 3 つの成果物が、それぞれどう動くかを整理すると:

ビルド形式誰が実行する
nativegcc（make）Linux 実行ファイルOS が直接
webemcc（make web）render.wasm + glueブラウザが実行
serveremcc（make sim）sim.wasm + glueNode が実行

web と server は同じ WASM の仕組みで、実行する場所（ブラウザ / Node）が違うだけです。 だから片方（web/engine_demo.js）で分かったことは、もう片方（record.mjs）でも通用します。

まとめ

WebAssembly（WASM）= C を「ブラウザ/Node が実行できる形」に翻訳した中間形式。 OS 非依存で、1 つの .wasm がブラウザでも Node でもネイティブに近い速さで動く。 翻訳するのは Emscripten（emcc）。gcc の代わりに、.wasm と橋渡しの glue.js を吐く。Node は glue を読み込み、C の関数を M._関数名(...) で普通に呼ぶ。数値はそのまま、文字列/配列は WASM メモリの住所（ポインタ）で渡す。 これで C のロジックを 1 つに保ったまま、描画（ブラウザ）と判定（Node）に使える。

04 · FAQ

よくある質問

技術リード自己確認シート（コード想定 Q&A）から、ビルドターゲット・ゲームループ・ game_step・WASM に関わる項目だけを抜き出したものです。 エンジン構成や戦闘員統合、サーバ権威モデルに関する質問は他のテーマページにあります。

Q. プログラムはどこから始まり、1 フレームはどう回る？

A. main() → 引数/マップ検証でモード決定 → 初期化 → pf_setup_hooks（イベント登録）→ pf_loop（制御を MLX に渡す）。 以後 MLX が毎フレーム main_loop を呼ぶ。main_loop は時間を測って game_frame（= game_step + render_frame + pf_present）。

確認: common/main.c / common/core/loop.c:31

Q. game_step の中身と順序は？（順序に意味がある）

A. ①決着済みなら即 return ②update_death（全戦闘員の死亡タイマー） ③自席が生存なら apply_input ④step_external_combatants（外部入力席） ⑤update_enemies（AI 席）⑥mode_ops.combat（FPS=接触判定 / RSP=じゃんけん） ⑦check_quest（ゴール・収集）。

確認: common/core/loop.c:67（game_step）。 死亡判定を先にする理由は「死んだ席が同 tick でゴール/収集しないため」（レビュー P1 修正）。

Q. native / web / server で 1 フレームを「回す人」は誰？

A. native=MLX（mlx_loop）、web=ブラウザ（requestAnimationFrame）、 server=Node（setInterval。W-10 で実装）。 呼ばれる game_step は 3 つとも同一。

Q. make のターゲットは？ sim に描画が入らないのはなぜ？

A. make（native）/ web（render.wasm）/ sim（sim.wasm）/ test（受入 85 検査）。sim は SIM_RENDER_EXCLUDES で描画ソース （draw/raycast/sprite/font 等）をリンクから外す。

確認: Makefile

Q. コード品質はどう担保している？
