## 3. 事実に基づく弱点（優先度順）

### W1. 知識の一点集中（構造的）

- Engine / sim / snapshot / W-01 を **samatsum がほぼ単騎**で完了させている（履歴・⑥の記述）。  
- 3人は「標準 Web」前提で投入。これは並行の利点だが、**TL 不在日に技術が止まる**脆弱性でもある。  
- IRC でも知識差はあったが、層 API が先にありスタブで進められた。当プロジェクトは **snapshot 形と auth 共通化**がそれに相当する — ここを Day1 に紙合わせしないと IRC より脆い。

**打ち手（あなた）**: Day1 に (1) auth の Cookie 名/属性 (2) ②§5-C snapshot 形 を定例で確認。PM として議題化する。

### W2. 進捗チャネルが設計書中心で、稼働中の待ちが薄い

- Issue は意思決定が中心（#10/#11/#5 CLOSED。OPEN は #6 評価台本・#13 切り捨て順）。  
- PR は活発（W-08〜W-11/W-14・docs）。一方、**「誰が今日何で止まっているか」の日次1枚**はまだ弱い。  
- ⑤ゲート行は追従しているが、§1 Done 表への W-08〜 追記は遅れがち。

**打ち手**: 全 Issue 化はしない。ブロッカー3本だけ（**W-04**, **F-06×W-11結合**, **W-15**）を日次で⑤かメモに刻む。

### W3. 日程・ゲート定義の二重記載（一部解消）

- ⓪ §7 の14日表は無効と明記済み（良い）。  
- ゲート2 から W-12 除外は **Issue #5 で確定**し、⑤⑥は統一済み。  
- 残る食い違いは **⑥日割り（相対 Day）と実カレンダー**（サーバ側が先行、auth が遅延）。

**打ち手**: 定例で「計画 Day」ではなく **未完リスト**（auth / FE / W-15）を宣言する。

### W4. 契約パス表記と実装のズレ

- ③: `shared/api/`。設計の一部はルート直下 `backend/` 表記  
- 実装: `app/shared/src/`（`@ft/shared`）、`app/backend/`  
- ②が想定する `shared/ws/` 分割は **Issue #10 で配置済み**（`app/shared/src/ws/` に envelope・errors・game・lobby）  
- `.env.example` に `SESSION_SECRET` / `ALLOWED_ORIGIN` はコメント予約。`ALLOW_DEV_AUTH` は追記済み  
- 小さいが、FE/BE 初手で迷う。IRC なら interface 改訂で即修正していた類。

**打ち手**: ③冒頭に実装パスを1行追記。

### W5. 共有認証 API は入口だけあり、本実装が無い

- Issue #11 で `session.ts` のシグネチャ合意済み。  
- 現状は `ALLOW_DEV_AUTH` + `x-dev-user` の暫定実装。W-08〜W-11 はこれを呼んで先行完了。  
- **二重化リスクは下がった**（独自認証は作らず共通入口を使っている）。残るのは中身の置換。

**打ち手**: W-04/W-05 で Cookie/Origin 本実装に置換し、dev 分岐を消す（または production で絶対に開けないことを受入にする）。

### W6. 説明用が厚いが、torinoue の最短路は公式化した

- `説明用/` は TL 視点の教育資産として優秀（pf・ループ反転・snapshot）。  
- **担当別 reading guide は onboarding_docs に公式化**（#26）。`torinoue/` は深掘り。  
- 教育の完全消化より、**auth 着手の遅れ**が今の最大リスク。

**打ち手**: [reading_guide_torinoue.md](../onboarding_docs/reading_guide_torinoue.md) → 本 dir の PERT。手を動かすのは W-02。

### W7. AI 緩和の両刃

| 利点 | 弱点 |
|---|---|
| 設計理解・草案・PERT が速い | 境界を無視したコードが混入しやすい |
| 短期間の速度に必要 | 「動いたが説明できない」が評価で致命 |
| IRC より実験コストが低い | Co-author / 履歴に機械名義が残ると提出リスク |

チームルールは **Co-Authored-By 禁止**（⑥§7）。提出物に AI 記録は必須。  
IRC は「コード手書き」＋ **AI の git 操作禁止**で安全側に振っていた。当プロジェクトは緩和が強いので、代わりに **契約テスト（zod・受入）と git は人間実行**で安全側に振る。

**打ち手**: shared のスキーマと ③ の表が食い違ったらマージしない。AI 生成でも受入は人間が読む。コミット/push は本人が実行し、AI 名義が履歴に残る操作は都度確認。

### W8. ブランチ運用の宣言と観測のギャップ

- ⑥§7: Issue 単位ブランチ、直 push しない。  
- 現状は `feat/w-08-lobby` 等で PR 運用が回っている（改善）。  
- W-01 の `"type":"module"` 回帰は教訓として文書化済み — 同じ失敗を auth/docker で繰り返さない。
