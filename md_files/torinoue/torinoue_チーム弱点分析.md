## 3. 事実に基づく弱点（優先度順）

### W1. 知識の一点集中（構造的）

- Engine / sim / snapshot / W-01 を **samatsum がほぼ単騎**で完了させている（履歴・⑥の記述）。  
- 3人は「標準 Web」前提で投入。これは並行の利点だが、**TL 不在日に技術が止まる**脆弱性でもある。  
- IRC でも知識差はあったが、層 API が先にありスタブで進められた。当プロジェクトは **snapshot 形と auth 共通化**がそれに相当する — ここを Day1 に紙合わせしないと IRC より脆い。

**打ち手（あなた）**: Day1 に (1) auth の Cookie 名/属性 (2) ②§5-C snapshot 形 を定例で確認。PM として議題化する。

### W2. 進捗チャネルが設計書に閉じ、GitHub が空

- `gh issue list` は実質プレースホルダのみ。PR も空に近い観測。  
- ⑤が正本と書いてある一方、4人の「今止まっている」が Issue に出てこない。  
- IRC は MD で待ちを残していた。どちらか一方でよいが、**どちらも更新されない状態が最悪**。

**打ち手**: 全 Issue 化はしない。ブロッカー3本だけ（W-04, W-11×F-06, W-15）を日次で⑤かメモに刻む。

### W3. 日程・ゲート定義の二重記載

- ⓪ §7 の14日表は無効と明記済み（良い）。  
- それでも ⑤ゲート2 行は W-08〜**W-12**、⑥日割りは W-12 を Day4。  
- 「完了したか」で揉める典型パターン。

**打ち手**: [PERT §5](./torinoue_PERT依存図.md) の案α/βを Day1 に決め、⑤⑥を同じ一文に。

### W4. 契約パス表記と実装のズレ

- ③: `shared/api/`。設計の一部はルート直下 `backend/` 表記  
- 実装: `app/shared/src/`（`@ft/shared`）、`app/backend/`  
- ②が想定する `shared/ws/` 分割は **未作成**（WS zod の置き場が口頭待ち）  
- `.env.example` に `SESSION_SECRET` / `ALLOWED_ORIGIN` はコメント予約のみ  
- 小さいが、FE/BE 初手で迷う。IRC なら interface 改訂で即修正していた類。

**打ち手**: ③冒頭に実装パスを1行追記。WS 用 zod を `app/shared` のどこに置くかを TL と一文で決める。

### W5. 共有認証 API が「文書の文章」だけで、呼び方がない

- ②は「Cookie を検証」、③は Origin/Cookie 決定。  
- `authenticate` のモジュール境界がコードにも短い擬似 API にも無い。  
- samatsum が W-08 で独自実装すると二重化・穴が起きる。

**打ち手**: W-04/W-05 で `app/backend` 内に共通関数を置き、名前を ⑥§4 か ③ に1行で書く。

### W6. 説明用が厚いが、torinoue の最短路が公式に無い

- `説明用/` は TL 視点の教育資産として優秀（pf・ループ反転・snapshot）。  
- 一方、**REST 未習熟者が2時間でゲート2 ブロッカーを理解する導線**が地図に無かった。  
- 残り5日では教育の完全消化は不可能。優先誤ると Day2 の auth が死ぬ。

**打ち手**: 本 `torinoue/` 読む順を自分の正にする。地図にリンク済み想定。

### W7. AI 緩和の両刃

| 利点 | 弱点 |
|---|---|
| 設計理解・草案・PERT が速い | 境界を無視したコードが混入しやすい |
| 残り5日の速度に必要 | 「動いたが説明できない」が評価で致命 |
| IRC より実験コストが低い | Co-author / 履歴に機械名義が残ると提出リスク |

チームルールは **Co-Authored-By 禁止**（⑥§7）。提出物に AI 記録は必須。  
IRC は「コード手書き」＋ **AI の git 操作禁止**で安全側に振っていた。当プロジェクトは緩和が強いので、代わりに **契約テスト（zod・受入）と git は人間実行**で安全側に振る。

**打ち手**: shared のスキーマと ③ の表が食い違ったらマージしない。AI 生成でも受入は人間が読む。コミット/push は本人が実行し、AI 名義が履歴に残る操作は都度確認。

### W8. ブランチ運用の宣言と観測のギャップ

- ⑥§7: Issue 単位ブランチ、直 push しない。  
- 現状ブランチ `doc_Review`、直近は docs merge が中心。実装レーン開始前なら問題ではないが、**4人実装が始まると衝突コストが一気に出る**。  
- W-01 の `"type":"module"` 回帰は「検証範囲が骨格起動だけだった」教訓として既に文書化されている — これは強み。同じ失敗を auth/docker で繰り返さない。

## 4. 強み（弱点と対で見る）

1. **Engine/Gameplay 完了 + CI green** — IRC 初期より「動く核」がある  
2. **決定表（D-4〜）が REST/WS にある** — 議論の土台がある  
3. **切り捨て順が書いてある** — スコープ崩壊を防げる  
4. **説明用とコード想定Q&A** — TL が知識移転を意図している  
5. **W-01 が契約の型（shared zod + health）を示している** — 小さいが正しい方向  
6. **AI 緩和** — ドキュメントと分析の速度を正当に使える（本成果物自体がその例）
