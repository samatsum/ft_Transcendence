# ドラフト: docs/ 全体構造の見直し（Issue #141）

**位置づけ**: これは正本ではない。Issue [#141](https://github.com/samatsum/ft_Transcendence/issues/141)
の方針（草案を作り、わからない部分はHELPで残し、PRで埋めてもらう）に沿った作業用ドラフト。
論点ごとに方針が決まった時点で、その範囲だけ実ファイルに反映していく（論点A・B・Cは反映済み。
下の各節に実施状況を記録する）。まだ決まっていない論点（D一部）は、既存ファイルを動かさず
この場で議論を続ける。

**このドラフトの読み方**: 各節は「事実」「観察」「論点」の3種類に分けて書いている。
「事実」は今回grep・ls・ghコマンドで確認したもの、「観察」はそこから見える傾向、「論点」はまだ決めていない
選択肢の提示。論点には**決定済み／未決定**の状態を明記する
（HELP＝書いた人が知らない事実を教えてもらう付箋、TODO＝残作業チェックリストという、Issue #141本来の
意味とは別物なので、論点にはこの2語を使わない）。

## 1. なぜ今これをやるか

2026-08-30、チーム運用が実際に始まったことに伴い、`チーム体制.html`・レーンID運用・Git運用フローの
3点はすでに見直して`docs/141`ブランチにコミット済み（[このセッションの前半](#)）。
その過程で、docs/ 全体に共通する2つのパターンが見えてきた。

1. **1つの事実が何ヶ所にも書かれている。** 「samatsumが単独稼働している」という一文だけで、
   `README.md`・`docs/ai/`側6ファイル・`docs/human/`側8ファイルの、計15箇所以上に散らばっていた
   （実際に direct grep で確認し、全箇所を直した）。CLAUDE.md自身が「1箇所だけ直すのは修正ではなく
   矛盾の作成」と警告している通りの状態だった。
2. **「レーン」という概念がファイル構成そのものに埋め込まれている。** Issue IDの採番だけでなく、
   `docs/human/専門用語/`配下のファイル名（`E-専門用語.html`等）や`開発状況/`配下のページ分割
   （サーバー系 vs フロントエンド系）が、もともとの「4レーン=4人」という前提を引きずっている。
   レーンをラベルとしてのみ残す運用に変えた今、この構成が最適かは要検討。

このドラフトは、この2パターンを踏まえて docs/ 全体をどう整理し直すかの叩き台。

## 3. 論点（HELP: 要判断）

以下は結論を出さず、選択肢として提示する。PRコメントか、このファイルへの直接編集で答えてほしい。

### 論点A: 「進捗カウント」をdocs/から追い出すか — **決定済み（2026-08-30）**

**決定**: `開発状況/`の§02のような進捗カウント（xx件中yy件完了）は、docs/から完全に削除する。
定性表現への置き換えもしない。

**理由（ttsubo）**: 進捗管理はGitHub（Issues + 単一Project "all"）で行っているため。docs側に
数字を残すと、GitHub側の実態とのズレが今回の「samatsum単独稼働」と同じパターンで再発する。

**適用範囲**: `開発状況/サーバー開発工程.html` §02・`開発状況/フロントエンド開発工程.html` §02、
および他ページに同種の完了数カウントが見つかった場合は同様に削除する。§01・03・04・07・08のような
「なぜこの工程が必要か」を説明する読み物部分は対象外（残す）。

### 論点B: `docs/human/`の想定読者を「samatsum」から「チーム」に一括更新するか — **決定済み（2026-08-30）**

**事実**: `docs/ai/README.md`の冒頭など、複数箇所で「人間向けドキュメントはsamatsum向けに書かれている」
という前提が明記されている。実際には今6人チームなので、この前提そのものが古い。

**決定**: 想定読者はチーム全体を前提にする（samatsum個人向けという記述はすべて外す）。

**表現ルール（細部も決定済み）**: 全体を指す場合は「チーム」、個人に言及する場合は個人名ではなく
**役割名**（例: 「テクニカルリード」「PM」）で表現する。人が入れ替わってもドキュメントが腐らない
ことを優先する。

**適用範囲（確定）**: このルールは「誰かの行動・状態を説明する地の文」（例:
「テクニカルリードが単独稼働のなかで進める」）に適用する。`チーム体制.html`のロースター表や
`README.md`のTeam表のように、**「今この役割を誰が務めているか」を宣言すること自体が目的のページ**
は例外とし、実名の掲載を続ける（そうしないと表が意味を成さないため）。

### 論点C: `専門用語/`のレーン別ファイル名をどうするか — **決定済み（2026-08-30）**

**決定**: レーン接頭辞を落とし、分野名ベースのファイル名にする。分類軸（何と何をまとめるか）自体は
変えない。

| 旧ファイル名 | 新ファイル名 |
|---|---|
| `E-専門用語.html` | `エンジン用語.html` |
| `F-専門用語.html` | `フロントエンド用語.html` |
| `G-専門用語.html` | `ゲームルール用語.html` |
| `B・I-専門用語.html` | `サーバー用語.html` |
| `全体-専門用語.html` | `全体用語.html` |

**理由（ttsubo）**: レーンの分類自体（何をまとめるか）は用語集として自然だが、`E-`のような
接頭辞はIssue IDの見た目と同じで紛らわしい。読む側にとってはファイル名にIssue ID接頭辞が
付いているかどうかは重要ではない。

### 論点D: 変わりやすい事実は、そもそもdocs/に置くべきか — **決定済み（2026-08-30）**

**事実**: 今回「samatsum単独稼働」という1つの事実が15箇所以上に重複していたのを人力のgrepで
洗い出した。CLAUDE.mdは「grepして数える」ことをルール化しているが、洗い出す作業自体は毎回人力。

**決定（方針）**: 「1箇所にまとめてリンクする」のさらに手前として、**そもそもGitHubが持てる情報は
docs/に置かない**方向にする。

- **実装ステータス（何%終わったか）**: docs/から追い出し、GitHub Projects / Milestoneの進捗表示に
  一本化する。`backlog.md`が持ち続けるのは受入条件・依存関係・意思決定の理由であって、
  「今の進捗数値」ではない（論点Aの決定と同じ考え方——`開発状況/`の§02削除はこの一部）。
- **チーム状況**: 42課題書がREADME.mdへの役割明記（PO/PM/TL/開発者）を義務づけているため、
  この**役割の枠組みだけ**はREADME.md＋`チーム体制.html`に残さざるを得ない。一方「誰が今どの
  Issueに着手しているか」のような日々のタスクアサインはGitHubのIssue assigneeの仕事であり、
  docs/には置かない。

**経緯**: これは2026-08-27〜28に一度話していた「docs/human/からGitHubが持てる情報（Issueステータス・
Projects・Assignee）を削る」方針（フェーズ1: `残作業一覧.html`削除、PR #130）の続き。
単一Project（"all"）への統合が済んだことで、フェーズ2に進める状態になった。

**細部も決定済み（2026-08-30）**:
- ルート`README.md`の「Current status」テーブルも**削除**する。課題要件と照らし合わせても
  必須の情報ではないため、評価者向け例外は設けない。GitHub（Issues/Projects "all"）への
  リンクに置き換える。
- `評価対応/42モジュール対応表.html`の各行の完了タグ（status-done/partial/todo）も**削除**する。
  進捗管理はGitHubに任せる。「必須要件 → コード入口」の対応表としての価値（表の本体）は残す。

### 論点E: `開発状況/`ページの「Issueカードグリッド」をどうするか — **決定済み（2026-08-30）**

**事実**: `開発状況/サーバー開発工程.html`・`フロントエンド開発工程.html`の§02（進捗カウント）を
削除する作業中に見つけた。両ファイルとも「◯工程を「何のためか」で読む」というセクションに、
Issue 1件につき1枚のカード（サーバー側17枚）があり、各カードは「何のためのIssueか」という
説明文と、完了タグ（`status-done`等）・担当者（`samatsum`）・データ属性（`data-status`/`data-owner`）が
1枚に同居している。凡例・絞り込みボタン（完了/部分完了/未完/不採用/samatsum担当）も付いた、
作り込まれたUI。

**決定**: セクションごと丸ごと削除する。理由は、このカードの「何のためのIssueか」という説明文は
`docs/ai/backlog.md`の該当行（タイトル・受入条件・検証結果）とほぼ同じ内容をチーム説明向けに
短くしただけで、実質的な重複だから（ttsuboが該当セクションを実際に読んで確認）。「一目で進捗が
見える」という体験価値は完了タグ・絞り込みUIありきのもので、タグを抜いても純粋な読み物としての
独自価値は薄い。

**残すもの**: 同ページ§01の4分類カード（Foundation/Realtime/Product data/Delivery等、粗い粒度の
「なぜこの区分があるか」）と、末尾の「3分説明」セクションは、backlog.mdより粗く要約された読み物
として独自価値があるため対象外。
