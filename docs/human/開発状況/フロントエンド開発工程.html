Frontend · F系・GV系

動くサーバーを、
プレイヤーが触れる画面にする。

F系・GV系は、B系・I系と並行してブラウザ側の画面（app/frontend/）を作る10工程です。 ログイン画面、ロビー、対戦画面、HUD、観戦画面と、プレイヤーが実際にクリックする すべての面を担当します。web/（Cエンジンのwasm化）とは別レーンです。

● 現在の実装状況はGitHub Issues / Projectを参照（このページは狙いと依存関係の説明用） · モジュール構成は2026-08-08のD-19改訂

01 · Meaning

Fは「エンジンの見た目」ではなく、プレイヤーが操作する製品の顔

Issue接頭辞のFは、このプロジェクトではFrontendレーンを指します。サーバー側はB系・I系です。 Fは大きく4つの仕事に分かれます。

Foundation · F-01/02

土台と通信

Vite/React/TSの骨格と、REST APIを叩くための共通fetch・エラー処理を整えます。

Player-facing · F-03/04/05/09/10

ログイン前後の画面

認証画面、共通レイアウト、ロビーを担当します（プロフィール・フレンドUIは2026-08-08に不採用）。

Match · GV-06/07/08/12

対戦そのもの

render.wasmの表示、HUD、試合遷移、（条件付きで）観戦画面を担当します。

Quality · F-11

仕上げ

レスポンシブ対応とキーボード操作でのアクセシビリティを最後に整えます。

B系・I系との境界: B系・I系は「サーバーとして何を保証するか」を完成させます。F系・GV系は「その保証を、プレイヤーが 迷わず操作できる画面としてどう見せるか」を受け持ちます。詳細はB/Iとの境界参照。
重要: pages/LoginPage.tsx・LobbyPage.tsx・PrivacyPage.tsxなどの ファイルはすでに存在しますが、中身がstub（受け皿）のこともあります。 ファイルがあることと画面が完成していることは同じではありません——各stubのコード先頭コメントに 「これはF-0Xで実装する」と明記されている場合は未完成です。現在の実装状況はGitHub Issues / Projectを参照してください。

02 · Screen flow

ログインから試合結果まで、画面がどう繋がるか

F番号順に実装されるわけではありません。プレイヤー体験としては、次の順番で複数Issueが連携します。

STEP 1 ログイン

F-03がsignup/loginフォームとroute guardを担当（未実装）

STEP 2 共通レイアウト

F-04がヘッダー・フッター・Privacy/ToSを担当（未実装）

STEP 3 ロビー

F-05がQuick Match・カスタムルーム・ルームビューを担当（未実装）

STEP 4 試合開始遷移

GV-08がmatch_foundからカウントダウンへ自動遷移する（未実装）

STEP 5 対戦

GV-06がrender.wasmとCanvasを繋ぎ、GV-07がHUDを重ねる（完了）

STEP 6 結果

GV-08がmatch_endモーダルを出し、ロビーへ戻す（未実装）

観戦（GV-12）はこの6ステップの続きではなく、STEP 5と並行して走る別の流れです。対戦者以外が試合中にspectateで接続し、プレイヤーと同じsnapshotを受け取ってmatch_endまで見続けます——結果表示の後に始まるものではありません。サーバー側の受け口はB-17。
F-11（レスポンシブ/アクセシビリティ）は全画面を最後に横断して調整します。 GV-12は2026-08-08のモジュール改訂（D-19）で「予備枠」から「必須」へ変わりました——観戦モードを +5点枠に採用したためです。申告したモジュールが動かないとその分は0点なので、これは後回しにできる仕上げではありません。

03 · Dependencies

次に進む順番は、番号順ではない

GV-06/GV-07はF-05より先に完了しています。これは「Gate 2でデモできる状態を優先する」という 判断のもとで、計画（④設計書の依存順）とあえて順序を変えたものです。ロビーが無いため、 ただし/game/dev-roomは現在ブラウザから開けません（ルーム未生成で4002、開発用認証ヘッダを送れず4000）。再現には本認証B-04とロビー起点のルーム生成F-05＋B-09が要ります。

Player-facing（未着手・担当未定）

  1. F-03 → F-04B-04（本認証）が閉じ次第、ログイン画面とレイアウトを実装
  2. F-05B-08/B-09（ロビーWS・マッチ成立）を消費してロビー一式を実装
  3. GV-08 → GV-12試合遷移を閉じ、続けて観戦UIを載せる（GV-12はB-17待ち）
  4. F-11最後に全画面のレスポンシブ/アクセシビリティを横断調整

samatsum · すでに閉じた対戦画面

  1. F-01 完了骨格・ルーティング・ビルド警告ゼロを確立
  2. F-02 完了共通fetch・エラー処理・401リダイレクトを確立
  3. GV-06 コード完了B-11のsnapshotをrender.wasm経由でCanvasへ表示。ブラウザでの受入は未再現
  4. GV-07 完了B-12のgrace/AI状態をHUDへ可視化
合流点: B-04 → F-03 → F-04 → F-05 → GV-08。 ここが通ると「ログインした人がロビーから実試合へ入り、結果を見てロビーへ戻る」という プレイヤー体験が一本になります。現時点の最大のブロッカーはB-04（本認証）です。

05 · Boundary with B / I

F系・GV系が消費するのは「B系・I系の保証」、作るのは「体験」

Backendが完成すればFrontendは実装しやすくなりますが、F側にはWSの張り替え、 WASM描画、入力、cleanupという独自責務があります。境界を混ぜないことが重要です。 同じ対応表はサーバー開発工程.htmlのF側境界にもあります（正本は同一）。

B系・I系が保証するもの消費する側F系・GV系で残る仕事
B-04 auth REST + CookieF-03フォーム、route guard、401遷移
B-08/B-09 lobby WS + match_foundF-05/GV-08ロビー表示、再接続、試合画面への遷移
B-11 snapshot/eventGV-06/GV-07render.wasm、補間、Canvas、HUD、入力送信（コード完了・ブラウザ受入は未再現）
B-12 grace/AI状態GV-07切断猶予とAI切替の可視化（完了済み）
B-17 spectator接続 + snapshot配信GV-12観戦HUD、視点切替、観戦者向けの入力抑止

06 · Three-minute talk

このまま読める、F全体の3分説明

「B系・I系が作るのはサーバーの保証、F系・GV系が作るのはプレイヤーが実際に触る画面です。 F-01でVite/React/TSの骨格を作り、F-02で共通の通信処理（エラー表示・401リダイレクト）を整えました。

本来はF-03のログイン画面、F-04の共通レイアウト、F-05のロビーと順に作ってから対戦画面へ進む 計画でしたが、Gate 2でデモできることを優先し、先にGV-06（render.wasmをCanvasへ表示し、 snapshotを補間する対戦画面）とGV-07（スコア・切断猶予・AI代替を見せるHUD）を完成させました。

ただしブラウザからは今のところ実演できません——通常起動のサーバーはルームを1つも作らず（4002）、ブラウザのWebSocketは開発用認証のx-dev-userヘッダを送れない（4000）ためです。検証はws-check.tsというNode製の検査ハーネスで行いました。ブラウザで触れるようになるのは、本認証（B-04）とロビー起点のルーム生成（F-05＋B-09）が入ってからです。 一方でログイン画面・ロビー・プロフィールはまだstub（受け皿だけ）の状態です。

次に必要なのは、B系の本認証（B-04）が閉じ次第のF-03、そしてB-08/B-09を使うF-05のロビーです。 この2つが繋がると、プレイヤーはログインからロビー経由で実試合に入れるようになります。」
