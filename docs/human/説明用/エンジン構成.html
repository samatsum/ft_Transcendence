01 · pf_* boundary

MLXに触る処理だけを、10個の関数にくくり出す

cub3Dは42の課題として、MiniLibX（MLX）というライブラリで画面を出しています。 MLXはLinuxのX11（デスクトップの画面表示の仕組み）を前提にしたライブラリです。

どこで動かす画面MLXは使えるか
Linuxのデスクトップ（従来のcub3D）X11のウィンドウ使える
ブラウザHTMLの<canvas>使えない（X11が無い）
Nodeサーバ（対戦の判定役）画面そのものが無い使えない

つまり、ゲームのロジック（移動・当たり判定・じゃんけんの勝敗・スコア）は 3か所でまったく同じものを使いたいのに、画面まわりだけが3か所で全部違うわけです。 ここで何も工夫しないと、ロジックを3回書くことになります。ブラウザ用にTypeScriptで 書き直し、サーバ用にもう一度書き、元のCも残す。そうすると「サーバでは勝ちだった のにブラウザでは負けに見える」といった3つの実装がズレるバグが必ず 出ますし、直すときは3か所直す必要があります。

解決策: 「MLXに触る処理」だけを10個の関数に押し込め、名前をpf_ （platformの略）で統一しました。ゲームのロジックは 「pf_present()を呼べば画面に出る」としか知りません。その中身が MLXなのかCanvasなのか、何もしないのかは知らないし、知る必要もありません。

サーバ版（headless）は半分が「何もしない」ですが、これは手抜きではなく 設計どおりです。サーバは絵を描く必要がなく、画面もキーボードもありません。 でも移動・衝突・じゃんけんの勝敗判定は完全に同じものを使いたい。そこで 「描画まわりは全部空っぽの実装を用意する」ことで、ゲームのロジック側は 1行も分岐せずにサーバでも動くようになります。 

// ゲームのロジックはこう書いてある（3環境で共通、if文なし）
pf_present(&game->window);   // Linux: 画面に出る / ブラウザ: Canvasに出る / サーバ: 何も起きない

もしpf_が無ければ、ここにif(サーバなら描画しない)という分岐が コードのあちこちに入ることになります。

なぜ「headless」で「server」じゃないのか

headless（ヘッドレス）は「頭が無い」という意味の一般的な業界用語で、ここでのhead はディスプレイを指します。モニタもキーボードもマウスも繋がっていない コンピュータをheadless computerと呼ぶのが元で、headless browser（Chromeの画面 なしモード）やheadless CMSも同じ用法です。platform/serverにしなかった 理由は3つあります。

理由1

層の名前は「何であるか」を表すべき

platform/の3つは実行環境の性質で並んでいます。ここに serverを混ぜると2つが「環境」で1つだけ「役割」になり、軸がずれます。 native=OSのデスクトップ上、web=ブラウザの中、 headless=画面が無い、という性質の並びです。

理由2（決定的）

実際、サーバ以外でも使っている

make test（85検査の受入テスト）は、headless実装を含んだ ただのネイティブ実行ファイルをgccでビルドして走らせています。 サーバでもwasmでもありません。デモ記録用のweb/sim_demo/record.mjs も同じ層を使います。もしserverという名前だったら、「なぜテストが サーバ実装をリンクしているのか」という不要な疑問が毎回発生します。

理由3

サーバであることはこの層の関心事ではない

headless実装がやっているのは「描画しない・入力を拾わない・ループを持たない」 の3つだけで、誰がその上でtickを回すかを知りません。回すのが Fastifyでも、テストのforループでも、record.mjsでも 同じように動きます。

語指すもの
headlessプラットフォーム層の実装（platform_headless.c）。「画面が無い」という性質
sim.wasmheadless実装を含めてビルドした成果物
サーバ / GameRoomsim.wasmを30Hzで回すNode側のコード（B-10）

「headlessだからサーバ」ではなく、「headlessだからサーバでも動かせる」 という順序です。

実際どこにあるのか

MLXを使う実装は1ファイルだけに閉じ込めてあります。

ファイル行数中身
platform/native/platform_native.c160MLXを使う唯一のファイル
platform/web/platform_web.c280ブラウザ版（Canvas / RGBAテクスチャ登録）
platform/headless/platform_headless.c144サーバ版（ほぼ「何もしない」）

確認するには、リポジトリのルートで「mlx.hをincludeしている」か 「mlx_◯◯()を呼んでいる」ファイルを探します。 

grep -rln 'mlx\.h\|mlx_[a-z]' codes/srcs

codes/srcs/platform/native/platform_native.cの1行しか 出ません。つまりcodes/srcs/common/（ゲームのロジック本体）は、 MLXを一切呼んでいません。

呼ぶ側は、どうやってnative / headlessを指定しているのか

指定していません。3つのファイルは、まったく同じ10個の 関数名を定義しています。 

// platform_native.c
void pf_present(t_window* w) { mlx_put_image_to_window(...); }   // 画面に出す

// platform_web.c
void pf_present(t_window* w) { /* JSがHEAPU8を読んでCanvasへ */ }

// platform_headless.c
void pf_present(t_window* w) { (void)w; }                        // 何もしない

呼ぶ側（loop.c）は、ただこう書いてあるだけです。

pf_present(&game->window);

ifも#ifdefも関数ポインタもありません。 Makefileがターゲットごとに1つしかソースを渡していないので、リンカが 「その場にあるpf_present」に解決するだけです。選択の余地がありません。

コマンド生成物渡すpf_*実装Makefileの変数
makecub3D（Linuxアプリ）platform_native.cNATIVE_PLATFORM_SRCS
make webrender.wasm（ブラウザ）platform_web.cWEB_PLATFORM_SRCS
make simsim.wasm（サーバ用）platform_headless.cSIM_PLATFORM_SRCS
make testsim_test（受入テスト）platform_headless.c同上（SIM_SRCSを流用）

2つ混ぜればduplicate symbol、0個ならundefined referenceで リンクが落ちます。間違えようがないのが、この方式の一番の利点です。 Cで実装を差し替えるときの最も古典的なやり方で、特別な技術は使っていません。 ゲームロジックのソースは4つとも同じものを使っています。 違うのはpf_*の実装だけです。

もう一段の節約として、make simはさらに描画のソースコード自体を リンク対象から外しています（MakefileのSIM_RENDER_EXCLUDES）。 draw.c / raycast.c / sprite.c / font.c などはsim.wasmに含まれていません。だからheadlessの pf_create_framebufferは「メモリを確保しない」で済みます。 描く人がそもそも居ないからです。

正確を期すと: 「分岐は一切ない」と言い切ると少し不正確です。コードベース全体で条件コンパイルは 2箇所だけあります。engine/render/cast_columns.c （nativeはpthreadで並列描画、webは単一スレッド）とcore/loop.c （ブラウザでは計測用のprintfを出さない、「コンソール警告ゼロ」要件のため）。 どちらもpthreadと計測ログの都合であって、pf_*の選択とは無関係です。 pf_*に関しては、本当に分岐ゼロです。

壊さないために守ること

原則: codes/srcs/common/（とfps/ rsp/）にMLXを 持ち込まない。もしcommon/のどこかに#include "mlx.h"を 書いてしまうと、make webとmake simが コンパイルエラーで落ちます（ブラウザ用・サーバ用のビルドにはMLXの ヘッダが存在しないため）。これは事故ではなく、わざとそうなるように 作ってある安全装置です。CI（GitHub Actions）が毎回3つとも全部ビルドするので、 この退行は必ず検知されます。なおmake check（lint）にはこれを検査する 項目はありません。検知しているのはビルドそのものです。 「lintが通ったから大丈夫」ではなく「3ターゲットのビルドが通ったから大丈夫」と 考えてください。

Backend / Frontend担当への実務的な影響

結論から言うと、pf_*を直接呼ぶ機会はほぼありません。

samatsum（ゲームサーバ / B-10・B-11）

sim.wasmをNodeで動かすとき、中ではheadless版のpf_* が使われています。「描画しない・入力を拾わない・ループを持たない」実装なので、 tickを回すのはNodeの責務です（setIntervalで game_stepを呼ぶ）。呼ぶのはpf_*ではなく sim公開API（sim_create / sim_set_input / game_step / game_snapshot）です。

フロントゲーム / GV-06（完了済み・samatsum実装）

ブラウザではpf_presentが「JSがWASMメモリを読んで Canvasに描く」という形になっています。C側は絵をメモリに書くだけで、 Canvasに出すのはJSの仕事です。そのためweb_framebuffer_ptr() などでバッファの場所をJSから取得します。この配線は web/sim_demo/replay.htmlに動く実例があります。

02 · Where languages run

「書く言語」と「動く言語」は別物

意外かもしれませんが、TypeScriptというプログラムが動く場所は、ブラウザにも サーバにも存在しません。TypeScriptは書くための言語で、 動かす前に必ずJavaScriptに変換されます。型チェックという安全装置が 付いたJavaScript、と思ってください。走る前に型は外され、ただのJavaScriptになります。

例えるならTypeScriptは「補助輪付きのJavaScript」。走り出す前に補助輪（型） が外れて、実際に走るのはJavaScriptです。だから、ランタイム（ブラウザや Node）に渡せる形は3つだけです。機械語（nativeのCから。Linuxが 直接動かす）、JavaScript（ブラウザとNodeが受け取る）、 WASM（ブラウザとNodeが受け取る）。ブラウザもNodeも、TypeScriptは 受け取れません。JavaScriptとWASMだけです。

実は、全部いずれ機械語になる — 違いは「いつ」

「JavaScriptやWASMは機械語ではないの?」と思ったら、その勘は正しいです。 CPUは機械語しか実行できません。例外はありません。だから JavaScriptもWASMも、最後は必ず機械語になってCPUが走らせます。「実行される言語が 3種類ある」のではなく、機械語にするタイミングと配る形が違うだけです。

いつ機械語になるか配る（shipする）もの
C（native）ビルド時（gccで先に翻訳）機械語そのもの（cub3D）
JavaScript実行時（ブラウザ/Nodeの中で自動的に）ソースコード（文字のまま）
WASM実行時（同上。ただし高速・確実）バイトコード（機械語に近い中間形式）

Cは「先に全部機械語へ翻訳してから配る」＝AOT（Ahead-Of-Time、事前 コンパイル）。JavaScript / WASMは「そのまま配って、動かす瞬間に機械語へ翻訳する」＝ JIT（Just-In-Time、実行時コンパイル）。ブラウザやNodeの中には V8というエンジンが入っていて、こいつがJavaScriptを読みながら その場で機械語に変換して走らせています。「JSが動く」の実体は 「V8がJSを機械語にしてCPUに流している」ことです。

では、なぜWASMのほうが速いのか。「両方とも機械語になるなら速さは同じでは?」—— 同じ機械語でも"質"が違います。JavaScriptは型が実行時まで決まりません （xが数値か文字列か、動かすまで不明）。だからエンジンは「たぶん数値 だろう」と推測して機械語を作り、外れたら作り直すという保険とやり直しを抱えます。 これが遅さの元です。WASMはC由来で型がガチガチに決まっているので、 推測なしで素直に速い機械語を吐けます。だからCに近い速度が出ます。 レイキャストのような重い計算をC/WASMに任せる理由がこれです（→ §5でも触れる 「速度が足りていた」の裏付け）。

言語→いつ変換→どこで動く

書く言語いつ変換される何になる最終的に動く場所
C（エンジン）ビルド時（emcc）WASMブラウザとNodeの両方
C（エンジン・native用）ビルド時（gcc）機械語Linuxが直接
TypeScript（フロント）ビルド時（Vite）JavaScriptブラウザ
TypeScript（バック）起動時（tsx）JavaScriptNode（サーバ）

バックエンドはtsxというツールで動かします。tsxはTypeScriptを その場でJavaScriptに変換してからNodeに渡すので、体感は「TSをそのまま 実行」ですが、中身は「TS→JS→Node」です。フロントのViteも同じで、TSをJSへ変換して ブラウザに渡します。どちらも走るのはJavaScriptです。

TypeScriptは「3つ」ではなく「2か所で書く」

app/の中にTypeScriptが3つありますが、これは用途と行き先で 分かれているだけです。

同じTypeScriptでも、フロント用は最終的にブラウザ、バック用はNodeで動きます。 app/shared/（zodの型）は、フロントとバックの両方に取り込まれて、 それぞれのJavaScriptの一部になります。書く言語は同じでも、変換後に 置かれる場所が違うわけです。

よくある勘違い

Q. TypeScriptはブラウザで動くの?

動きません。ビルドでJavaScriptに変換され、ブラウザが動かすのは JavaScriptです。「TypeScriptが動いている」ように見えても、実体は 変換後のJavaScriptです。

Q. JavaScriptとWASMは、別々に動く別のプログラム?

いいえ、ペアで動きます。JavaScriptが主役（ホスト）で、WASMを 読み込んでその関数を呼びます。WASMは計算専門で、画面や通信にはJavaScriptを 通してしか触れません。

Q. ブラウザのJavaScriptとNodeのJavaScriptは同じもの?

言語としては同じJavaScriptです。違うのは居場所と権限。 ブラウザのJSはセキュリティの檻の中（ファイルは触れない）、NodeのJSは檻の外 （ファイルも通信もできる）です。

Q. Cはどこで動くの?

nativeでは機械語としてLinuxが直接。ブラウザとNodeではWASMに 変換されて動きます。同じCのソースが、3つの場所すべてで （形を変えて）動いているのがこの設計の肝です。

03 · Directory layout

切り分けの軸は「コードかどうか」ではない

「コードなら1か所に集めたほうが素直では?」と感じるかもしれません。でも実際の軸は 言語（ツールチェーン）と担当レーンの2つです。 

app/        TypeScript の Web アプリ一式（backend / frontend / shared + tsconfig.base）
codes/      C エンジン本体（srcs / includes / minilibx / tests）
web/        C を WASM 化した成果物＋それを動かす JS（build / engine_demo.js / sim_demo）
maps/       .cub マップ（ゲームの入力データ）
textures/   画像素材（.cub が参照）
infra/      nginx・証明書・Dockerfile（docker/）＝デプロイまわり
docs/       資料一式（この説明も含む）
screenshot/ 実行時のスクリーンショット出力先（中身は git 管理外）

Makefile              C のビルド入口
package.json /

このほかnode_modules/（npm生成物）、cub3D（ビルド出力）、 .gitignore等の隠しファイルがありますが、いずれも「自動生成」か 「隠し」なので数に入れません。

軸1・言語（＝ビルドの仕組み）

codes/はCプロジェクト、app/はTypeScriptプロジェクト

codes/は「コード全般」ではなくCプロジェクトです。 Makefile・MiniLibX・.c/.hの世界で、 ビルドはmake。いっぽうapp/はTypeScript プロジェクトで、ビルドはnpm。この2つはツールも 依存関係も完全に別です。同じフォルダに混ぜるとlintやビルドの設定が ぶつかります。言語で切ると、ツールチェーンが素直に分かれます。

軸2・担当レーン

フォルダを開けば「どのレーンか」が分かる

app/の中はレーン分担そのままです。app/backend/＝ Auth / REST / DB（未完成）、app/frontend/＝画面（F-01・F-02・GV-06は完了、 残りは未完成）、app/shared/＝全員が使うzod契約、codes/＝エンジン本体 （予定作業は完了。ただしG-11・G-12の修正は残る）。複数人で並行作業する体制になったときも、 この対応がそのまま効きます（現在はsamatsum単独稼働。チーム体制.html参照）。

なぜapp/にまとめたのか（ルートを減らす工夫）

もともとbackend/ frontend/ shared/ tsconfig.base.jsonはルート直下にバラけていました。 これらは「TypeScriptのWebアプリ」という1つの塊なので、app/配下へ まとめました。ルートから3ディレクトリ+1ファイルが消えてapp/ 1つに。担当レーンとの対応はapp/backendのように 1階層下で保たれるので、「フォルダ＝レーン」の見やすさは失っていません。

なぜ壊れないのか: 各パッケージは互いをパッケージ名（@ft/sharedなど）で 参照しているので、フォルダを動かしてもimportは無傷です。tsconfig.base.json も一緒にapp/へ下ろしたため、extends: "../tsconfig.base.json" の相対パスは変わらず解決します。実装コードは1行も変えていません。

なぜ「これはルートのまま」なのか

ルートに残っている物の多くは、ツールがそこにあることを要求する からです。動かすと壊れるか、規約と戦うことになります。

ルート固定の物理由
package.json / package-lock.jsonnpm workspacesのルート。ここでしか成立しない
Makefilemakeの既定入口。動かすとmake -f codes/Makefileになり不便

05 · Single-threaded rendering

なぜブラウザは並列描画しないのか

やれば遅くなる要素があり、しかも要らなかったから、です。 「ブラウザはCPUをうまく使えない」からではありません。

cub3Dの描画はレイキャストという方式です。画面を縦に細い列へ切り、 1列ずつ「壁までの距離」を計算して、その距離から壁の高さを決めて 描きます。960幅なら960本の列を毎フレーム計算します。列と列は互いに独立なので、 複数のCPUコアで分担すれば速くなるはずです。実際native版はそうしています。 

// codes/srcs/common/engine/render/cast_columns.c
jobs[i].start = (cols * i) / n;      // 各スレッドに担当する列の範囲を割り当て
jobs[i].end   = (cols * (i + 1)) / n;
pthread_create(&tid[i], NULL, &cast_worker, &jobs[i]);  // n 個のスレッドで並列

列ごとに書き込むピクセルが重ならないので、mutex（排他ロック）が1つも ありません。並列化に理想的な構造です。ところがweb版は、これを使わず 1スレッドで全列を描きます。なぜか、理由は2つあります。

理由その1 — ブラウザで並列化すると「代償」がつく

Emscriptenで Cのpthreadをブラウザ向けにビルドすると、こう変換されます。 

C の pthread      →  Web Worker（複数コアで動く。ここは問題ない）
スレッド間の共有メモリ →  SharedArrayBuffer   ← ★これが厄介

SharedArrayBuffer（SAB）が問題です。2018年の Spectre / Meltdown（CPUの投機実行の穴を突いて、本来読めない メモリを盗み見る攻撃）で、SABが超高精度なタイマーとして悪用でき、 攻撃の部品になることが分かりました。そのためブラウザ各社はSABを一度 全面無効化し、今は条件付きでしか使えません。その条件が cross-origin isolationです。サーバが全レスポンス に次の2つのヘッダを付ける必要があります。 

Cross-Origin-Opener-Policy:   same-origin
Cross-Origin-Embedder-Policy: require-corp

これを有効にすると、そのページが読み込む外部リソース全部 （画像・フォント・他オリジンの何か）にも、対応するヘッダが必要になります。 1つでも欠けると、そのリソースが読めなくなります。

私たちにとって、これが何を意味するか: nginx（I-15）の設定が、その分ややこしくなる。評価の拒否条件「コンソールに 警告・エラーゼロ」を、原因の分かりにくいヘッダ由来のエラーで落とすリスクを 抱える。I-15は残り日程で沼ると痛い。要するに、並列化の見返り（速度）に 対して、リスクとインフラの手間が見合わない。

理由その2 — そもそも速度が足りていた

E-13で、シングルスレッドのまま実測しました（開発機・Nodeヘッドレス・300フレーム）。

内部解像度fps（fps_map）fps（rsp_map）
960×540（既定）112.0106.8

60fps要件に対して約1.8倍の余裕があります。評価機が開発機の半分の 性能でも要件を満たす計算です。つまり「並列化しないと60fpsに届かない」という状況 ではありませんでした。面倒を持ち込んでまで速くする理由が、そもそも 無かったわけです。

参考までに、nativeは並列なので1920×1080でも1フレームを約8.5msで 描けます（＝秒110枚ぶんの"能力"）。実際の./cub3Dは frame_deltaが60fpsに制限しているので出力は60fps固定ですが、1080pでも 8.5msしかかからないため60fpsを楽に満たす余裕があります。この余裕が小さいのが シングルスレッドのwebで、解像度を下げるノブが要るのはwebだけです。

足りなくなったら、まず解像度を下げる

重い評価機に当たった場合の対処は、pthread有効化ではなく内部解像度 です。その口はもう実装済みです（E-13）。 

engine_demo.html?res=848x480      ← URL で内部解像度を指定できる

web_init(map, is_rsp, width, height)の後半2引数がこれです。 内部解像度を下げても、Canvas側はCSSで画面いっぱいに引き伸ばすので、 プレイヤーから見たウィンドウの大きさは変わりません（少し粗くなるだけ）。描画コストは ほぼピクセル数に比例するので、848×480は960×540の約78%の負荷です。

対処の優先順位1

内部解像度を848×480に下げる

設定変更だけ。無料。ノブは実装済み。

対処の優先順位2

COOP/COEPを入れてpthread有効化

必須要件を壊しかねない。1を先に試してから、それでも足りない場合のみ。

2を先にやってはいけません。1はコストゼロ、2は「コンソール警告ゼロ」 を危険にさらします。

まとめ: webが単一スレッドなのは、ブラウザが非力だからではありません（Web Workerで並列は 可能）。ブラウザで並列化＝SharedArrayBuffer＝COOP/COEPヘッダが必須＝nginxが複雑化し、 コンソール警告ゼロ要件を脅かします。しかもE-13で960×540＝112fps、60fpsの約1.8倍 あり、そもそも要らなかった。描画のコード自体は並列化しやすい構造（列分割・mutex なし）なので、やろうと思えばいつでも有効化できます。ただし動機がありません。

06 · FAQ

テクニカルリード自己確認シートより — エンジン構造編

samatsumが評価・チーム説明で即答できるように用意した自己確認シートから、 エンジン構造・pf_*境界に関する項目だけをここに集めました （サーバ権威モデル・ビルドターゲット・スナップショット・戦闘員などの項目は他の テーマページに分類しています）。

Q. native / web / serverで1フレームを「回す人」は誰?

A. native=MLX（mlx_loop）、web=ブラウザ （requestAnimationFrame）、server=Node（setInterval。 B-10で実装）。呼ばれるgame_stepは3つとも同一。

Q. MLXに依存しているのはどこ? 何ファイル?

A. pf_*のnative実装1ファイルだけ （platform/native/platform_native.c）。sim層・render層はMLXを 呼ばない。確認はgrep -rln 'mlx\.h\|mlx_[a-z]' codes/srcs。

Q. どうやってnative / web / headlessを切り替えている?

A. 切り替えていない。3実装が同じ関数名を持ち、Makefileが ターゲットごとに1つだけリンクする（NATIVE_/WEB_/SIM_PLATFORM_SRCS）。 リンカが解決するだけ。

Q. headless（サーバ）が「何もしない」pf関数だらけなのはなぜ?

A. サーバは描画も入力もループも持たないから。空実装にすることで、ロジック側に if(サーバ)を書かずに済む。確認は platform/headless/platform_headless.c。
