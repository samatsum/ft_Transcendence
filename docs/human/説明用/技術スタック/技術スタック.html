技術スタック — 採用済み

「なぜその技術を選んだか」への回答用。エンジン層（C・minilibx・Emscripten）は対象外で、 Web アプリ側のうち実際にコードが入っている技術だけを載せる。 設計は決まっているが実装がまだゼロの技術（SQLite・Prisma・argon2id・nginx）は 使用予定技術スタック.html に分けてある。

1実行形式
技術どのようなものかなぜ選んだか（比較対象）
WebAssembly C/C++ 等のコードを、ブラウザ・Node.js がほぼネイティブ速度で実行できるバイナリ形式へ変換する技術。 比較対象は「TS/JS でレンダラーを一から書き直す」案。それだと完成済みの C エンジンを捨て、 当たり判定・AI・衝突を2言語で二重にメンテすることになる。WebAssembly なら 同じ C ソースからネイティブ・ブラウザ用（render.wasm）・ サーバー用（sim.wasm）の3種を作り分けられ、ロジックの正本は C 側1つで済む。 このプロジェクトで最もリスクが高い選定だったため、Gate 1 として最初に検証した。
2Backend
技術どのようなものかなぜ選んだか（比較対象）
Node.js JavaScript / TypeScript をサーバー上で動かす実行環境。 比較対象は Python・Go・Java。決定打はsim.wasm を直接実行できること。 WebAssembly はブラウザ発の技術なので JS 系ランタイムと相性がよく、 判定エンジンを動かすための橋渡し層が要らない。
Fastify Node 上で HTTP・WebSocket サーバーを組み立てる土台。ルーティング・検証・エラー処理を提供する。 比較対象は Express（定番だが低機能・低速）と NestJS（DI コンテナ等を備えた重量級）。 公式 WS プラグインがあり REST とリアルタイムを1つのサーバーに同居させやすい。 NestJS はこの規模・期間には過剰投資と判断した。
3FE / BE 共有
技術どのようなものかなぜ選んだか（比較対象）
TypeScript JavaScript に型（変数の種類のチェック）を足した言語。ビルドで JS へ変換してから配る。 比較対象は素の JavaScript。FE/BE を同じ言語にすることで 型定義を1箇所に書いて両方で使い回せる。 42 が要求する「入力検証を FE/BE 両方で行う」を、二重実装ではなく1つの定義で満たす。
zod データの形をスキーマとして定義し、実行時にも検証できるライブラリ。 比較対象は Joi・Yup。zod はスキーマから型を自動導出できるのが決め手で、 1つ書けば型と検証の両方が手に入る。app/shared/ に1箇所だけ置き、 FE/BE が同じ定義を import する。
npm workspaces 1つのリポジトリで複数パッケージ（shared / backend / frontend）を管理する仕組み。 比較対象はリポジトリ分割と、Turborepo・Nx といった専用ツール。 共有 zod スキーマをパッケージ公開なしで直接 import したいので 単一リポジトリが前提。その上で、追加ツールを入れずに npm 標準機能だけで足りる規模だった。
4リアルタイム通信
技術どのようなものかなぜ選んだか（比較対象）
WebSocket 一度繋いだら接続を維持し、双方向に小さいメッセージを送り合える通信方式。@fastify/websocket を使用。 比較対象は Socket.IO。独自プロトコル層を挟むぶんオーバーヘッドがあり、 素の WebSocket クライアントと直接話せなくなる。対戦の入力送信とスナップショット配信という 単純な用途では、その抽象化が不要な複雑さになると判断した。
5Frontend
技術どのようなものかなぜ選んだか（比較対象）
React 画面を部品（コンポーネント）の組み合わせとして作る UI ライブラリ。 比較対象は Next.js・SvelteKit。SSR モジュールを採用しないので SSR は不要で、 Next.js の機能の大半が過剰になる。SPA が最も単純で、 かつ React は課題書の言う「フレームワーク」の要件を満たす。 AI によるコード生成の品質が最も高い部類なのも採用理由として記録されている。
Vite TS/React のコードを JS へ変換し、開発中はブラウザへ即座に反映するビルドツール。 比較対象は Webpack ベースの旧来構成。ネイティブ ES モジュールを活用するため 開発サーバーの起動と変更反映が桁違いに速い。 現在の React エコシステムでの標準的な選択でもある。
Tailwind CSS 用意されたクラス名（text-sm・flex など）を HTML に直接並べて見た目を作る手法。 比較対象は Bootstrap（既製 UI 部品が強い代わりに見た目を変えにくい）。 課題書が「CSS フレームワークを使うこと」自体を要求しており、それを満たしつつ コンポーネント志向の React と相性がよい。
Vitest フロントエンド用のテストランナー。apiFetch・補間・HUD 状態のテストで使用中。 比較対象は Jest（定番だが設定が重め）。Vite と同じビルド基盤を共有するため 設定がほぼ要らない。Vite を採用している以上、自然な組み合わせ。

正確を期すための注記。 Vitest はローカルでは動くが、CI では実行していない。 CI の web-app ジョブがやっているのは npm ci・型検査・ビルド・ /api/health の起動確認まで。テスト実行の追加は I-16 の範囲。
