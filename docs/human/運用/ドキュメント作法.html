01 · Which track

新しいページはai/とhuman/どちらか

docs/ai/docs/human/
言語英語日本語
形式Markdown（.md）HTML（.html）
読者AIコーディングアシスタントsamatsum
ファイル名英語kebab-case（ws-protocol.md）内容が分かる日本語（直訳・ローマ字は不可。例: チーム体制.htmlであってteam-plan.htmlではない）

実装時にAIが参照する事実（プロトコル仕様・バックログ・コーディング規約・Git運用）は ai/へ。samatsumが読んで理解・学習するもの（オンボーディング・専門用語・ 「なぜこう作ったか」の解説・プロジェクト概要）はhuman/へ。迷ったら 両方作る——コマンドや正確なパスなど機械的な事実は片方だけに正本を置き、 もう片方はそこへリンクするだけにします（二重管理で内容がズレるのを防ぐため）。 architecture.mdとプロジェクト概要.html、 git-workflow.mdとGit運用フロー.htmlの対がその実例です。

01.5 · Category directories

docs/human/の中はカテゴリ別ディレクトリ

docs/human/はフラットではありません。内容の種類が違うファイルは ディレクトリを共有しません。「その他」的な寄せ集めディレクトリも作りません—— 既存のどれにも当てはまらなければ、新しいカテゴリディレクトリを作ります （samatsum本人の明示的な指示、2026-08-07。もともとは8本の無関係なファイルが docs/human/直下にフラットに並んでいて見通せなくなっていた）。

ディレクトリ内容の種類
はじめに/初めて読む人向けの全体像（プロジェクト概要・チーム体制・オンボーディング）
運用/作業する上でのルール（Git運用フロー、このページ）——製品そのものの話ではない
開発状況/更新され続ける進捗ドキュメント（B系・I系とF系・GV系の2ページ）
説明用/「なぜこう作ったか」の深掘り解説＋TL自己確認Q&A
専門用語/レーン別の専門用語集
プレイヤー向け/作る人向けではなく、遊ぶ人（プレイヤー・評価者）向けの製品ドキュメント

docs/human/index.html自体だけはルート直下に残します（README.mdが リポジトリルートに残るのと同じ、入口ファイルの慣習）。新しいページを作る前に、 既存カテゴリに当てはまらないか確認してください。当てはまらなければ新設して構いません （1ファイルだけのカテゴリでもOK——プレイヤー向け/も最初は1ファイルからでした。 それはまだ仲間が増えていないだけです）。

02 · HTML template

HTMLページのテンプレート

ゼロから書かず、既存ページ（短い例としてはじめに/チーム体制.html）をコピーしてください。 骨格は共通です。 

<!doctype html>
<html lang="ja">
<head>
	<meta charset="utf-8">
	<meta name="viewport" content="width=device-width, initial-scale=1">
	<meta name="color-scheme" content="dark">
	<title>ページ名 — ft_transcendence</title>
	<link rel="stylesheet" href="../assets/style.css">  <!-- カテゴリディレクトリはどれも1階層なので既定はこれ。docs/human/index.html自身は ./assets/style.css -->
</head>
<body>
	<header class="hero">…</header>
	<nav class="topnav">…</nav>   <!-- 短いページなら省略可 -->
	<main class="shell">
		<section id="...">…</section>
	</main>
	<footer class="shell">…</footer>
</body>
</html>

nav.topnav（アンカーリンク＋印刷ボタン）は、ページ内目次が要るくらい長い ページだけに付けます。短いページ（セクションが数個だけ）は省略して構いません （はじめに/チーム体制.htmlが省略例）。

03 · Shared stylesheet

共通スタイル（docs/human/assets/style.css）

docs/human/配下の全カテゴリディレクトリのHTMLページが同じ1枚のCSSを参照します。ページ固有の <style>は書かない——必要なクラスが無ければ共通CSS側に足します。

唯一の例外: 印刷前提のページ。 説明用/技術スタック/の2ページだけは、共通CSSではなく同階層の 印刷用.cssを使います（samatsumの指定、2026-08-08）。 カラー印刷を前提に「白地・白/黒/赤の3色のみ・角丸なし・グラデーションと影は禁止・ ウェイトは900/700/500のみ」という別のデザイン体系で作る必要があり、 画面用のダーク配色と両立しないためです。ページ固有スタイルを許す前例ではありません—— 例外の範囲はこの2ページだけで、印刷用ページを増やす場合も新しいCSSを書かず 印刷用.cssを使い回します。
用途クラス
ページ構造.shell・.hero・.topnav/.nav-inner
セクション見出し.section-kicker（h2の上の小さいラベル）・.section-intro
カード・グリッド.card・.card-label・.grid.grid-2/3/4
コールアウト.callout（水色・情報）・.callout.warning（黄色・注意）

04 · Diagrams

図：Mermaid か、プレーンテキストか

box-drawing文字（┌│└▼→等）と日本語を同じ行に混ぜて手描きしない。 CJK文字は「monospace」フォントでもASCII文字の約2倍の幅で描画されるため、 box-drawingの桁合わせ計算が実際のブラウザ表示ではズレます。samatsum本人から 指摘が入り、実際に4ページで確認されました。

Mermaidを使う

多段組み・分岐・二者間のやり取り

箱が横に並ぶ図、1つのノードから複数の矢印が分岐する図は必ずMermaid。 ブラウザ⇄サーバのような二者間のやり取りはsequenceDiagramが 手描き矢印より圧倒的に読みやすい。

プレーンテキストのままで良い

単純な縦一直線・実際のコード

A → B → Cのような横並びの無い単純な流れは、ズレのリスクが 低いのでそのままで構わない（機械的に全部変換しない）。ファイル形式の例・ ディレクトリ一覧・実際のコード/ターミナル出力は図ではないのでMermaid化しない。

埋め込み方

静的ファイルなのでMermaid本体をCDNから読み込み、assets/style.cssの配色に 合わせて初期化します。既存ページ（サーバ権威モデル.htmlなど）から コピーしてください（配色を都度打ち直すとページ間でズレます）。 

<pre class="mermaid">
flowchart TD
    a["ノードA"] --> b["ノードB"]
</pre>

<script type="module">
	import mermaid from "https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs";
	mermaid.initialize({
		startOnLoad: true,
		theme: "base",
		themeVariables: {
			darkMode: true,
			background: "#07111f",
			primaryColor: "#12243a",
			primaryTextColor: "#edf6ff",
			primaryBorderColor: "#29415d",
			lineColor: "#5de4d6",
			/* 以下省略。既存ページからそのままコピーする */
		}
	});
</script>

CDNへの到達性に依存します（オフラインでは図が生のテキストとして表示される）。 評価対象のアプリ本体ではなく開発用ドキュメントなので許容していますが、 図が描けなくても文章だけで意味が伝わるように書いてください。

ルート直下のREADME.mdなど、GitHub上で見るプレーンMarkdownでは ```mermaidフェンスを使います（GitHubがネイティブ描画するのでスクリプト不要）。

コミット前に構文検証する

目視だけに頼らないこと。括弧の閉じ忘れ・ラベル内の引用符の衝突などは mermaid.parse()で機械的に検出できます。使い捨てで構いません。

05 · Navigation

ナビゲーションへの組み込み

新しいページはどこかからリンクされて初めて見つかります。最低限：

  1. index.htmlのファイル一覧表に行を追加#files セクション
  2. 初見の人が読むべきなら「読む順」にも追加末尾とは限らない——専門用語集は「これを前提に他ページを読む」ため先頭に挿入した
  3. 内容が重なる既存ページから相互リンクする孤立したページを作らない

docs/ai/*.mdを追加した場合はdocs/ai/README.mdのDocuments表に行を足します。

05.5 · Pitfalls

編集を始める前に — 実際に何度も踏んだ5つの落とし穴

2026-08-09、外部監査（Codex）がドキュメントの不整合を13件、再監査でさらに10件、 その後さらに1件見つけました。そのうち大半が、同じ1つの失敗パターンから生まれています。 4回連続で同じことをやりました。docs/を触る前にここを読んでください。 実行するコマンドの一覧は doc-style-guide.md（英語・AI向け）にあります。

最大の落とし穴: 1つの事実が何箇所に書かれているか数えずに直すこと。 このリポジトリは同じ事実を docs/ai/（英語）＋docs/human/（日本語） ＋README 3種＋コードのコメントに持っています。 1箇所だけ直すのは「修正」ではなく矛盾の作成です。

Pitfall 1 · 波及漏れ

同じ事実が何箇所にあるか数える

実例:「F-05は5領域」をbacklog.mdで直し、frontend.mdと 日本語2ページを放置。「エンジンは完成」を1ファイルで直し、他6ファイルを放置。 「GV-06は完了」を1箇所で限定し、ステータス表6箇所を放置。
対策: 直す前に grep して件数を数える。2件以上なら同じコミットで全部直すか、 直さない理由をコミット本文に書く。

Pitfall 2 · 走査漏れ

検索パターンは思っているより狭い

2回、「残り0件」と報告した後に監査が5件見つけました。原因は 表記ゆれ（W-はE/G/W/F・W-series・ 「Wの保証」とも書かれる）、本文以外（フッタ・<title>・ ナビ・card-label）の見落とし。
対策: 3〜4通りの表記で検索する。編集後に再走査し、件数をコミット本文に書く。

Pitfall 3 · 依存の切断

不採用にしたIssueには、まだ生きた依存元がある

モジュールを取り下げると、それを消費していたIssueが静かに実装不能になります。 F-05はB-07とB-13を落とした後も5領域のままで、フレンド領域にはAPIが無く、 試合フィードにはmatch_resultの供給源が無い状態でした。
対策: 何かを落としたら、そのIDでgrepして消費側を全部読む。

Pitfall 4 · 根拠なき完了宣言

「検証済み」は、証拠となる成果物を名指しする

この期間で最悪の欠陥は、修正そのものが作った新しい嘘でした。 GV-06/GV-07を「ws-check.tsで検証済み」と書きましたが、 ws-check.tsはB-11/B-12/B-14を検査するバックエンド用で、 Frontendも Canvas もrender.wasmも読み込みません。
対策:「完了」「検証済み」「実測」と書くときは、 根拠となるテスト・スクリプト・実行を名指しし、実際に開いて 主張範囲をカバーしているか確認する。証拠が無いならそう書く。 「コードはマージ済み、受入は未再現」は正当なステータスです。

Pitfall 5 · 自分の過去の編集が古くなる: backlog.mdはB-17新設の根拠として「ws/game.tsはいまだに 『実装は余力時』と書いている」と述べていました。書いた時点では正しく、 1つ後のPRでそのコメントを直した瞬間に嘘になりました。 ドキュメントが他ファイルの現在の状態を引用しているときは、 引用先を触るたびに引用元も確認してください。

06 · Dead links

コミット前にリンク切れを確認する

これまで複数のdocs PRで実際にリンク切れを検出してきたチェック方法です。 リンクに触れる変更・ファイルのリネーム・新規ページ追加のあとは必ず実行してください。 

python3 - <<'EOF'
import re, os, html
repo = os.path.abspath('.')
targets = ['README.md', 'infra/README.md', 'web/README.md']
for dirpath, dirs, files in os.walk('docs'):
    for fn in files:
        if fn.endswith('.html') or fn.endswith('.md'):
            targets.append(os.path.join(dirpath, fn))
def check(path):
    text = open(path, encoding='utf-8').read()
    d = os.path.dirname(os.path.abspath(path))
    for pat in [r'href="([^"]+)"', r'\]\(([^)]+)\)', r'src="([^"]+)"']:
        for m in re.finditer(pat, text):
            target = html.unescape(m.group(1))
            if target.startswith(('http', 'mailto:', '#')) or not target:
                continue
            resolved = os.path.normpath(os.path.join(d, target.split('#')[0]))
            if not os.path.exists(resolved):
                print(f"BROKEN in {os.path.relpath(path, repo)}: {target}")
for t in targets:
    check(t)
EOF

ファイルが存在するかしか見ていません。存在する別ファイルを 間違って指している場合は検出できないので、diffの読み込みは省略しないこと。

07 · Status wording

担当・進捗表記のルール

正本はチーム体制.html。何度も出てくる判断なのでここにも要約します。

  • 離脱済み・過去の期間のメンバー（mamiyaza / hminemur、および2026-08-05〜2026-08-30の 期間に限ってtorinoue——2026-08-30にPMとして復帰済み）を、その期間より後の未完成タスクの 現在の担当者として書かない。名前の代わりに完了 / 未完成 / 担当未定を使うか、 チーム体制.htmlとGitHub Issueのアサインで現在の担当を確認する。
  • 過去の経緯（実際に誰が作ったか、いつ決まったか）としての言及は問題ない ——「過去の事実」か「現在進行中に見えるか」を見分ける。誤読されそうなら 削除ではなく注記を足す（architecture.md §6/§9のパターン: 元の表は残しつつ、 「これは過去の計画で現在は無効」という注記を上に足す）。
  • 進捗を書く前にdocs/ai/backlog.md、疑わしければ git log origin/mainで裏取りする。記憶だけで書かない ——このリポジトリは過去に何度も「ドキュメントが未実装と書いていたのに originでは実装済みだった（逆もあり）」を踏んでいる。
