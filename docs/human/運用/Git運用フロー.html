Operating Rule · Git / GitHub

ローカルでマージして
終わり、にしない。

origin/main（GitHub側）が唯一の正本。統合はそこで行い、ローカルの main は pull で追従させるだけにする。 これがこのリポジトリのGit運用ルールです。チームの誰にも、Claude Codeなどの AIエージェントにも、同じルールを適用します。

01 · The flow

標準の8ステップ

すべての変更（1行のdocs修正でも）はこの流れに乗せます。main へ直接 コミットすることはありません。ローカルとorigin（GitHub側）を並べて表示するので、 どの時点でどちらが進んでいるかが分かります。←→ボタンかキーボードの矢印キーで ステップを送れます。

1 / 8

🖥 ローカル

☁ origin（GitHub）

ステップ⑦は省略しない。 今回、ローカル main が origin/main より31コミットも 遅れていた原因はまさにこれで、しばらくgit pullしていなかったせいで 古いmainを土台にした作業ブランチが1本まるごと発生し、後から手作業で origin/mainと突き合わせる羽目になりました。
ステップ⑧も省略しない。 放置するとどうなるか——実際にこのリポジトリでは、マージ済みのブランチが7本放置され、 どれが安全に消せるか（git branch --merged・git diff --stat・ gh pr listでのPR状態確認）を後から1本ずつ手作業で調べる羽目になりました。 マージした直後に消せば、この調査は不要です。

まとめてコピペする場合はこちら。番号は上のインタラクティブな図と揃えています。 

# ① 出発点：作業前に最新化
git checkout main
git pull

# ② ブランチを切る
git checkout -b feat/xxx

# ③ 作業してコミット
# ...実装...
git add .
git commit -m "..."

# ④ push
git push -u origin feat/xxx

# ⑤ PRを作る（CIはここから実行される）
gh pr create --fill

# ⑥ CIが緑になったらマージ（squash）
gh pr merge --squash    # お好みで --merge や --rebase も選べる

# ⑦ ローカルのmainを追従させる
git checkout main
git pull

# ⑧ 役目を終えたブランチを消す
git branch -d feat/xxx                  # ローカル
git push origin --delete feat/xxx       # リモート（gh pr merge --delete-branch なら両方まとめて）

02 · Naming

ブランチ名・コミットメッセージの規約

このリポジトリの過去35件以上のPRですでに使われている規約に揃えます。新規に決めるものではありません。

ブランチ名: <種別>/<issue番号>-<短い説明>

2026-08-30に規約変更。 2026-08-08〜2026-08-29は <種別>/<短い説明>（Issue番号なし。例: docs/141のように番号のみのブランチも存在した）でしたが、 どのIssueの作業か名前から分からないため、Issue番号を先頭に入れる形に変更しました。 既存ブランチの改名は行いません。
接頭辞用途例
feat/新機能feat/133-put-delete-user-api
fix/バグ修正・レビュー指摘対応fix/135-auth-display-name
docs/docs/ディレクトリ・README.mdのみの変更docs/141-team-lane-restructure
chore/製品挙動を変えないツール・依存関係の変更chore/deps-bump
ci/CIワークフローの変更ci/add-lint-job

<issue番号>はそのブランチが対応するGitHubのIssue番号そのもの （後述のとおりレーンIDではない）。claude/... や samatsum/... のような個人名プレフィックスの新規作成は今後も避けます。 AIが作るブランチも<種別>/<issue番号>-<説明>に揃えてください。

コミットメッセージ: Conventional Commits

feat: / fix: / docs: / chore: / ci: / build: / lint:。 2026-08-30以降、スコープにはレーンIDではなくGitHub Issue番号そのものを入れます （fix(133): address CodeRabbit review feedback）。それ以前のコミット （fix(F-01): ...のようなレーンIDスコープ）はそのまま残し、書き換えません。 1行目の要約は日本語・英語どちらでも構いませんが、同じブランチ内で言語を混ぜないこと。

03 · Merge strategy

マージ方式の選び方

既定

--squash

1 PR = 1 コミットに畳む。作業中の修正コミット・CodeRabbit指摘対応コミットなどが ブランチ内でどれだけ雑に積まれていても、mainのログは 「出荷単位の一覧」として綺麗に保たれる。迷ったらこれ。

例外1

--merge

ブランチ内の個々のコミットにそれぞれ独立した意味があり、後から個別に参照したい 場合のみ。頻度は低い。

例外2

--rebase

短く・すでに綺麗で・単一目的のブランチで、マージコミット自体がノイズになる場合のみ。

禁止

mainへの直接プッシュ全般

直接コミット・ローカルでマージしてpush・force-push、いずれも禁止。下の 「なぜPR経由か」の理由により、必ずブランチ→PR→CI→GitHub上でマージ、を通す。 履歴を書き換える必要があるなら、それはマージ前のブランチ単位で行う話であって、 共有履歴に対して事後にやることではない。 GitHubのruleset（ブランチ保護）でmainへの直接push・force-pushは 実際にブロックされている——人の注意力だけに頼らず、仕組みでも守られている。

04 · Why

ローカルマージではなく、PR経由が良い理由

このルールを制定した2026-08-07時点はチームが解散し、samatsum単独稼働でした。 いまは複数人がブランチをpushしています（現在の体制は チーム体制.html）。単独稼働だった当時は レビュアーが不在という理由でPRを経由していましたが、複数人になった今も理由は 変わらずCIがいつ走るかです。

やり方CIが走るタイミング失敗したときどうなるか
ローカルで main にマージ →
git push origin main		 pushした後 main に壊れたコミットが乗った状態になる。その間に git clone した人（評価者含む）は壊れたビルドを引く
ブランチをpush → PR作成 →
CI緑を確認してからGitHub上でマージ		 マージする前（PR上） main には触れない。revertする必要すら発生しない
PR＝レビューゲートではなく、CIゲート。 CIが緑になった自分のPRを自分でマージ（self-merge）するのは正常な運用です。 大事なのは「mainに触れる前に、そのコミットに対してCIを走らせているか」 だけです。

05 · Lane prefixes

レーン接頭辞と、2026-08-08の改名

この節がレーン定義の正本です。 以前は⑥ チーム体制§03と オンボーディングにも別の語彙でレーンの定義が置かれ、 3つの語彙が並立していました。2026-08-08にここへ一本化し、他の2ページからはこの節を参照する形にしています。 レーンを増やす・境界を動かす場合は、まずここを直してください。
2026-08-30、上の表は「そのIssueが属するレーン」の定義としては維持しつつ、 ID接頭辞としての新規採番は廃止しました。 チーム運用が実際に始まり、新規Issueにレーン付きIDを振る運用が回らなくなったため （新しいIssueはGitHubの生番号のみで作られています）、レーンは lane:engine / lane:backend / lane:infra / lane:frontend / lane:gameview ラベルだけで表すことにしました。 レーンごとに分かれていたGitHub Projectsも単一の"all" Projectへ統合済みです。 既存のbacklog.mdの行・過去のコミット・クローズ済みIssueに残るレーン付きID はそのまま残り、読み方は下の「旧IDとの対応」節と同じです。

Issue番号の頭文字はレーンを表します。レーンは「どこで動くか」ではなく 「何のコードで、誰が保守するか」で分けています。 render.wasmはブラウザで動きますがEngineレーンなのはこのためです—— 同じraycast.cがnativeバイナリとrender.wasmの両方にコンパイルされるので、 実行場所で線を引くと1つのソースファイルが2レーンに割れてしまい、担当境界として機能しません。

接頭辞レーン範囲
E- / G-Enginecodes/とweb/のCエンジン。接頭辞は2つだがレーンは1つ（E-は移植・基盤、G-はゲームルール）。完了済みの作業を振り直す利益が無いため分けたまま
B-BackendFastify・認証・REST・WS・GameRoom・DB（Prisma/SQLite）
I-Infra / DevOpsリポジトリ骨格とツーリング、Docker/nginx/TLS、CI
F-Frontend一般Web画面: 認証・レイアウト・ロビー・レスポンシブ
GV-GameViewゲーム画面: Canvasとrender.wasm統合・HUD・試合遷移・観戦UI

Bレーンの中には、性質の違う仕事が2種類ある

B-は1レーンですが、中身は「普通のWebアプリ」と「リアルタイム対戦サーバー」に分かれます。 必要な経験がかなり違うため、着手先を選ぶときはこの区別が効きます。 これはレーンではなく、Bレーン内部の読み分けです——Issue番号の接頭辞はどちらもB-のままです。

区分Issue中身性質
基盤 B-02〜B-05 Fastify共通処理、Prisma+SQLite、認証（argon2id・Cookie）、Origin検証 一般的なWebアプリのCRUDと認証。教材や記事が豊富で、Web開発の経験がそのまま効く
ゲームサーバー B-08〜B-12・B-17 ロビーWS、マッチ成立、GameRoom、ゲームWS、切断/AI代替、観戦配信 30Hz tick・15Hz snapshot・状態機械・再接続。sim.wasmの挙動を理解している必要があり、既存実装を読むところから入る
（どちらでもない） B-14 GET /api/mapsとマップ本文の配布 完了済み。基盤とゲームサーバーの両方から使われる

F-とGV-も同じ理由で分かれています——一般Web画面（F-）と、 render.wasmやWebSocketに触るゲーム画面（GV-）。 こちらは性質の差が大きいので、内部区分ではなく別レーンにしてあります。

旧IDとの対応

2026-08-08まで、バックエンド・DB・インフラは全てW-（Web）1つに詰め込まれており、 接頭辞が中身を何も表していませんでした。フロントエンドも一般画面とwasm/WS依存のゲーム画面が同居していました。 改名では番号を保持したので対応は機械的ですが、 約85件のコミットメッセージと過去のGitHub Issueは書き換え不可能なため、 新旧の語彙は履歴上ずっと共存します。

旧新
W-01I-01
W-02〜W-14B-02〜B-14（番号そのまま）
W-15・W-16I-15・I-16
F-06・F-07・F-08・F-12GV-06・GV-07・GV-08・GV-12
他のF-変更なし
E-・G-変更なし
古いコミットの読み方: 接頭辞だけ置き換え、番号はそのまま。 2026年7月のコミットにあるW-12は今のB-12、 PR #35のF-07は今のGV-07です。

06 · Issue tracking

backlog.md＋GitHub Issueの併用（2026-08-08〜）

各E-/G-/B-/I-/F-/GV-/H-番号の受入条件・依存・進捗の正本は、引き続きdocs/ai/backlog.mdです。 2026-08-08から、新しく見つかった課題はGitHub Issueにも同時に記録するようにしました ——「何が問題で、今解決しているか否か」をIssueタブでopen/closedとして視覚的に一目で見られるようにするためです。 当初は2026-08-08より前のbacklog.mdの行は遡及登録しない方針でした（最初の例が Issue #46（G-11）・ Issue #47（G-12））が、 2026-08-09にこの方針は上書きされました——Kanban（GitHub Projects）での管理のため、 残っている未着手の行を全てIssue化しています（B-03〜B-05・B-17、F-03〜F-05・F-11、GV-08・GV-12、 I-15・I-16、H-01 → #77〜#89）。 部分完了（B-08等）や完了済みの行は対象外です。 この一覧はIssue化した時点の記録で、B-03（#77）はその後完了しました——未着手として残っているのは#78以降です。

項目ルール
タイトルプレフィックス無しの短い説明のみ（例:「GET, POST, PUT, DELETEのエンドポイント」）。GitHub自体のIssue番号が識別子。2026-08-30より前は<Issue番号>: <短い説明>（例:「G-11: FPSの射撃機構がプレイヤー同士を排除できてしまう」）でしたが、既存Issueのタイトルは書き換えません
ラベル対象領域に対応するレーンラベルを1つ——E-/G-→lane:engine（上の「レーン接頭辞」表の通り1レーン）、B-→lane:backend、I-→lane:infra、F-→lane:frontend、GV-→lane:gameview（接頭辞6つに対しラベル5つ。H-は特定レーンの作業ではない最終ゲートなのでラベル無し）。＋backlog-tracked＋bugかenhancement。2026-08-09に修正: Issue #46〜#48がこの表と矛盾するlane:gameplayを誤って付けられていた（このラベルは廃止し、lane:engineへ付け替え済み）
本文中のコード引用絶対URL（https://github.com/samatsum/ft_Transcendence/blob/main/...）を使う。../../のような相対パスは、Issue本文がリポジトリのファイルツリーの外にあるため静かに解決しません（docs/内では同じ書き方が問題なく動くので特に注意）
相互リンクbacklog.mdの行からIssue番号へ、Issue本文からbacklog.mdの節へ、両方向にリンクする
クローズのタイミング対応するbacklog.mdの行がマージ済みPRで完了マークされた時だけ閉じる（両者がズレないように）

07 · Anti-patterns

やってはいけないこと

  1. ブランチをローカルmainにマージして終わりにする origin/mainに乗り、ローカルmainがそれを pullで追従するまでは「完了」ではない。
  2. ローカルmainを放置する 新しいブランチを切る前は毎回git checkout main && git pull。 不安ならgit fetch && git rev-parse main origin/mainで 一致を確認してから始める。
  3. 他のfeatureブランチから枝分かれする 意図的にPRを積み重ねる場合を除き、必ずmainから切る。 積む場合はPRの説明にその旨を明記する （PR #35の 「積む形」のように）。
