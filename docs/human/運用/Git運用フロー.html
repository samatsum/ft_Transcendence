Operating Rule · Git / GitHub

ローカルでマージして
終わり、にしない。

origin/main（GitHub側）が唯一の正本。統合はそこで行い、ローカルの main は pull で追従させるだけにする。 これがこのリポジトリのGit運用ルールです。samatsum本人にも、Claude Codeなどの AIエージェントにも、同じルールを適用します。

2026-08-07 制定 ローカルmainが31コミット遅れていた事故を受けて明文化
なぜPR経由か 5ステップ 命名規約 マージ戦略 後片付け レーン接頭辞 Issue併用 やってはいけないこと

01 · Why

ローカルマージではなく、PR経由が良い理由

チームが解散し、いまはsamatsum単独稼働です（詳細は チーム体制.html）。レビュアーはもういません。 それでもPRを経由する意味は残っています。理由はレビューではなく CIがいつ走るかです。

やり方CIが走るタイミング失敗したときどうなるか
ローカルで main にマージ →
git push origin main		 pushした後 main に壊れたコミットが乗った状態になる。その間に git clone した人（評価者含む）は壊れたビルドを引く
ブランチをpush → PR作成 →
CI緑を確認してからGitHub上でマージ		 マージする前（PR上） main には触れない。revertする必要すら発生しない
PR＝レビューゲートではなく、CIゲート。 CIが緑になった自分のPRを自分でマージ（self-merge）するのは正常な運用です。 大事なのは「mainに触れる前に、そのコミットに対してCIを走らせているか」 だけです。

02 · The flow

標準の5ステップ

すべての変更（1行のdocs修正でも）はこの流れに乗せます。main へ直接 コミットすることはありません。 

# 1. 作業前に最新化
git checkout main
git pull

# 2. ブランチを切って作業
git checkout -b feat/xxx
# ...実装・コミット...

# 3. ブランチをpushしてPRを作る
git push -u origin feat/xxx
gh pr create --fill

# 4. CIが緑になったらGitHub上でマージ（gh pr merge でも、Web UIでも可）
gh pr merge --squash    # お好みで --merge や --rebase も選べる

# 5. ローカルのmainを追従させる
git checkout main
git pull
ステップ5は省略しない。 今回、ローカル main が origin/main より31コミットも 遅れていた原因はまさにこれで、しばらくgit pullしていなかったせいで 古いmainを土台にした作業ブランチが1本まるごと発生し、後から手作業で origin/mainと突き合わせる羽目になりました。

03 · Naming

ブランチ名・コミットメッセージの規約

このリポジトリの過去35件以上のPRですでに使われている規約に揃えます。新規に決めるものではありません。

ブランチ名: <種別>/<短い説明>

接頭辞用途例
feat/新機能feat/f-01-scaffold
fix/バグ修正・レビュー指摘対応fix/design-gaps-3-6
docs/docs/ディレクトリ・README.mdのみの変更docs/w-08-design-complete
chore/製品挙動を変えないツール・依存関係の変更chore/deps-bump
ci/CIワークフローの変更ci/add-lint-job

claude/... や samatsum/... のような個人名プレフィックスの新規作成は今後避けます。何を含むブランチかが 名前から分からず、関連する作業の隣にソートもされないため。AIが作るブランチも <種別>/<説明>に揃えてください。

コミットメッセージ: Conventional Commits

feat: / fix: / docs: / chore: / ci: / build: / lint:。 スコープ付きも可（fix(F-01): address CodeRabbit review feedback）。 1行目の要約は日本語・英語どちらでも構いませんが、同じブランチ内で言語を混ぜないこと。

04 · Merge strategy

マージ方式の選び方

既定

--squash

1 PR = 1 コミットに畳む。作業中の修正コミット・CodeRabbit指摘対応コミットなどが ブランチ内でどれだけ雑に積まれていても、mainのログは 「出荷単位の一覧」として綺麗に保たれる。迷ったらこれ。

例外1

--merge

ブランチ内の個々のコミットにそれぞれ独立した意味があり、後から個別に参照したい 場合のみ。頻度は低い。

例外2

--rebase

短く・すでに綺麗で・単一目的のブランチで、マージコミット自体がノイズになる場合のみ。

禁止

ローカルで--ff-onlyしてpush

上の「01 なぜPR経由か」の理由により、必ずGitHub側でマージし、CIをその マージ結果に対して走らせること。

05 · Cleanup

マージ後は、ブランチを消す

マージされたブランチはもう役目を終えています。ローカルとリモート両方から削除します。 

git branch -d feat/xxx                  # ローカル
git push origin --delete feat/xxx       # リモート（gh pr merge --delete-branch なら両方まとめて）
放置するとどうなるか — 実際にこのリポジトリでは、マージ済みの ブランチが7本放置され、どれが安全に消せるか （git branch --merged・git diff --stat・ gh pr listでのPR状態確認）を後から1本ずつ手作業で調べる羽目になりました。 マージした直後に消せば、この調査は不要です。

05.5 · Lane prefixes

レーン接頭辞と、2026-08-08の改名

この節がレーン定義の正本です。 以前は⑥ チーム体制§03と オンボーディングにも別の語彙でレーンの定義が置かれ、 3つの語彙が並立していました。2026-08-08にここへ一本化し、他の2ページからはこの節を参照する形にしています。 レーンを増やす・境界を動かす場合は、まずここを直してください。

Issue番号の頭文字はレーンを表します。レーンは「どこで動くか」ではなく 「何のコードで、誰が保守するか」で分けています。 render.wasmはブラウザで動きますがEngineレーンなのはこのためです—— 同じraycast.cがnativeバイナリとrender.wasmの両方にコンパイルされるので、 実行場所で線を引くと1つのソースファイルが2レーンに割れてしまい、担当境界として機能しません。

接頭辞レーン範囲
E- / G-Enginecodes/とweb/のCエンジン。接頭辞は2つだがレーンは1つ（E-は移植・基盤、G-はゲームルール）。完了済みの作業を振り直す利益が無いため分けたまま
B-BackendFastify・認証・REST・WS・GameRoom・DB（Prisma/SQLite）
I-Infra / DevOpsリポジトリ骨格とツーリング、Docker/nginx/TLS、CI
F-Frontend一般Web画面: 認証・レイアウト・ロビー・レスポンシブ
GV-GameViewゲーム画面: Canvasとrender.wasm統合・HUD・試合遷移・観戦UI

Bレーンの中には、性質の違う仕事が2種類ある

B-は1レーンですが、中身は「普通のWebアプリ」と「リアルタイム対戦サーバー」に分かれます。 必要な経験がかなり違うため、着手先を選ぶときはこの区別が効きます。 これはレーンではなく、Bレーン内部の読み分けです——Issue番号の接頭辞はどちらもB-のままです。

区分Issue中身性質
基盤 B-02〜B-05 Fastify共通処理、Prisma+SQLite、認証（argon2id・Cookie）、Origin検証 一般的なWebアプリのCRUDと認証。教材や記事が豊富で、Web開発の経験がそのまま効く
ゲームサーバー B-08〜B-12・B-17 ロビーWS、マッチ成立、GameRoom、ゲームWS、切断/AI代替、観戦配信 30Hz tick・15Hz snapshot・状態機械・再接続。sim.wasmの挙動を理解している必要があり、既存実装を読むところから入る
（どちらでもない） B-14 GET /api/mapsとマップ本文の配布 完了済み。基盤とゲームサーバーの両方から使われる

F-とGV-も同じ理由で分かれています——一般Web画面（F-）と、 render.wasmやWebSocketに触るゲーム画面（GV-）。 こちらは性質の差が大きいので、内部区分ではなく別レーンにしてあります。

旧IDとの対応

2026-08-08まで、バックエンド・DB・インフラは全てW-（Web）1つに詰め込まれており、 接頭辞が中身を何も表していませんでした。フロントエンドも一般画面とwasm/WS依存のゲーム画面が同居していました。 改名では番号を保持したので対応は機械的ですが、 約85件のコミットメッセージと過去のGitHub Issueは書き換え不可能なため、 新旧の語彙は履歴上ずっと共存します。

旧新
W-01I-01
W-02〜W-14B-02〜B-14（番号そのまま）
W-15・W-16I-15・I-16
F-06・F-07・F-08・F-12GV-06・GV-07・GV-08・GV-12
他のF-変更なし

古いコミットの読み方: 接頭辞だけ置き換え、番号はそのまま。 2026年7月のコミットにあるW-12は今のB-12、 PR #35のF-07は今のGV-07です。

06 · Issue tracking

backlog.md＋GitHub Issueの併用（2026-08-08〜）

各E-/G-/B-/I-/F-/GV-/H-番号の受入条件・依存・進捗の正本は、引き続きdocs/ai/backlog.mdです。 2026-08-08から、新しく見つかった課題はGitHub Issueにも同時に記録するようにしました ——「何が問題で、今解決しているか否か」をIssueタブでopen/closedとして視覚的に一目で見られるようにするためです。 当初は2026-08-08より前のbacklog.mdの行は遡及登録しない方針でした（最初の例が Issue #46（G-11）・ Issue #47（G-12））が、 2026-08-09にこの方針は上書きされました——Kanban（GitHub Projects）での管理のため、 残っている未着手の行を全てIssue化しています（B-04・B-05・B-17、F-03〜F-05・F-11、GV-08・GV-12、 I-15・I-16、H-01 → #77〜#89）。 部分完了（B-08等）や完了済みの行は対象外です。

項目ルール
タイトル<Issue番号>: <短い説明>（例:「G-11: FPSの射撃機構がプレイヤー同士を排除できてしまう」）
ラベル接頭辞に対応するレーンラベルを1つ——E-/G-→lane:engine（上の「レーン接頭辞」表の通り1レーン）、B-→lane:backend、I-→lane:infra、F-→lane:frontend、GV-→lane:gameview（接頭辞6つに対しラベル5つ。H-は特定レーンの作業ではない最終ゲートなのでラベル無し）。＋backlog-tracked＋bugかenhancement。2026-08-09に修正: Issue #46〜#48がこの表と矛盾するlane:gameplayを誤って付けられていた（このラベルは廃止し、lane:engineへ付け替え済み）
本文中のコード引用絶対URL（https://github.com/samatsum/ft_Transcendence/blob/main/...）を使う。../../のような相対パスは、Issue本文がリポジトリのファイルツリーの外にあるため静かに解決しません（docs/内では同じ書き方が問題なく動くので特に注意）
相互リンクbacklog.mdの行からIssue番号へ、Issue本文からbacklog.mdの節へ、両方向にリンクする
クローズのタイミング対応するbacklog.mdの行がマージ済みPRで完了マークされた時だけ閉じる（両者がズレないように）

07 · Anti-patterns

やってはいけないこと

  1. mainへの直接コミット ローカルでもpush後でも禁止。1行のdocs修正でも必ずブランチを切る。
  2. ブランチをローカルmainにマージして終わりにする origin/mainに乗り、ローカルmainがそれを pullで追従するまでは「完了」ではない。
  3. mainのforce-push いかなる理由でも行わない。履歴を書き換える必要があるなら、それは マージ前のブランチ単位で行う話であって、共有履歴に対して事後にやることではない。
  4. ローカルmainを放置する 新しいブランチを切る前は毎回git checkout main && git pull。 不安ならgit fetch && git rev-parse main origin/mainで 一致を確認してから始める。
  5. 他のfeatureブランチから枝分かれする 意図的にPRを積み重ねる場合を除き、必ずmainから切る。 積む場合はPRの説明にその旨を明記する （PR #35の 「積む形」のように）。

2026-08-07 制定。AI向けの同内容は docs/ai/git-workflow.md。samatsumとの会話で 「ローカルmainへのマージだけで終える運用は事故のもと」と確認した内容を明文化したもので、旧資料からの翻訳ではない。
