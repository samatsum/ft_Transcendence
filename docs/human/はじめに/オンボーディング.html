01 · Now

いま何を作っているか

42の課題 ft_transcendence: ブラウザで遊べるオンライン対戦（cub3D由来のエンジンをWeb化）。 Cエンジンはすでに完成しており、これからTypeScriptのBackend / Frontendを積み上げる段階。

状態内容
完了 Cエンジン（codes/ / web/）。判定を担う sim.wasm と、描画を担う render.wasm。
これから TypeScriptのBackend / Frontend（app/）。次の関門はゲート2。
ゲート2の定義: 複数ブラウザでRSP（じゃんけん鬼ごっこ）対戦が最後まで成立すること。 これが結合デモのgo/no-go関門であり、連番の課題番号ではない。 日程の正本は⑤ バックログ §6（Gate/schedule mapping）。

要件の一次情報: ai/requirements.md（旧 01_課題/ft_トランセンデンス.md）

02 · Lanes & roles

開発レーンと管理役割

このプロジェクトの実装は4つの開発レーンに分かれる。誰が何を担当するかは体制によって変わるが、 レーンの境界そのものは変わらない共通の地図として使える。詳細の正本は ⑥ チーム体制 §03（開発レーン構成）。

Lane · Game server

ゲームサーバーレーン

sim.wasm駆動・WS・GameRoom。対戦の心臓部を動かす。

Lane · Backend foundation

Auth / REST / DB / Dockerレーン

身元確認、REST API、DB、起動基盤を担う。

Lane · Non-game UI

非ゲームUIレーン

認証画面・ロビーなど、対戦そのものではない画面を担う。

Lane · GameView

GameViewレーン

GameView / HUD / マッチ遷移。対戦画面の体験を担う。

管理役割（課題書 II.1.1）: テクニカルリード（TL）、プロジェクトマネージャー / スクラムマスター（PM/SM）、 プロダクトオーナー（PO）、開発者（専任）の4種。 全員が開発者であり、管理役割は開発と兼任できる。 評価では「自分の役割と貢献」を説明できる必要がある。

04 · Boundaries

モジュール境界（ここだけ合意すれば並行できる）

正本はこのページ（旧「⑥チーム分担計画」§4の内容を移設）。 担当者が誰であっても、この契約の境界自体は変わらない。

契約所有レーン主な消費レーン
app/shared/のzod（型の単一情報源） Auth/REST/DBレーン（非ゲームUIレーンが必須レビュアー） 全レーン
REST API Auth/REST/DBレーン 非ゲームUIレーン
WSプロトコル（メッセージ形・GameRoom） ゲームサーバーレーン GameViewレーン（＋ロビーは非ゲームUIレーン）
sim公開API / snapshot受信・補間（C側） 完了・原則不変 ゲームサーバーレーン / GameViewレーン
最優先の同期: ゲームサーバーレーン ⇄ GameViewレーンのsnapshot JSON形（②WSプロトコル設計のsnapshot節）。
次点: Auth/REST/DBレーン ⇄ 非ゲームUIレーンのエラーエンベロープとCookie。

契約を変えるときは設計書を先に直してから実装する （②WSプロトコル設計自身が「実装が本書と食い違ったら、まず本書を直してから実装せよ」と明記している通り）。 元は「所有レーンの担当者に相談してから」というルールだったが、samatsum単独稼働の現状では 相談する相手が別にいないため、この原則だけが残っている。

05 · FAQ

よくある混乱

Q. Cub3D / レイキャスタの数学まで読むか？

A. ゲート2前は、ゲームサーバーレーン（エンジン駆動）以外は不要。 説明用の深いエンジン資料や、印刷用全記録のレイキャスタ章は後回しでよい。

Q. codes/（C）を直してよいか？

A. 原則凍結。変更が必要な場合は、上の「モジュール境界」にある契約表を先に更新し、 設計書を直してから実装する（②WSプロトコル設計の原則に従う）。

Q. 進捗の正本はどれか？

A. Issue受入・ゲート定義・日程（Gate/schedule mapping） → ⑤ バックログ §6。 0-全体アーキテクチャ設計.mdの14日表は日程としては無効。

Q. 説明用資料はすべて読む必要があるか？

A. いいえ。自分が今取り組んでいる分野に関係する資料から読めば十分。 説明用（説1〜説12）を通読する必要はない。
