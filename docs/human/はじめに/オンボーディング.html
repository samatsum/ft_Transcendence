02 · Boundaries

モジュール境界（ここだけ合意すれば並行できる）

正本はこのページ。レーンは2026-08-30以降Issueに貼るラベルとしてのみ使う運用になったが （詳細はGit運用フロー §05）、 「このコード領域が何を保証し、誰が消費するか」という契約の境界自体は、 誰が今そこを担当していても変わらない共通の地図として使える。

契約所有領域主な消費領域
app/shared/のzod（型の単一情報源） Backend（Frontendが必須レビュアー） 全領域
REST API Backend（基盤側） Frontend
WSプロトコル（メッセージ形・GameRoom） Backend（ゲームサーバー側） GameView（＋ロビーWSはFrontend）
sim公開API / snapshot受信・補間（C側） Engine（完了・原則不変） Backend / GameView
最優先の同期: Backend（ゲームサーバー側） ⇄ GameView のsnapshot JSON形（②WSプロトコル設計のsnapshot節）。
次点: Backend（基盤側） ⇄ Frontend のエラーエンベロープとCookie。

契約を変えるときは設計書を先に直してから実装する （②WSプロトコル設計自身が「実装が本書と食い違ったら、まず本書を直してから実装せよ」と明記している通り）。 2026-08-30更新: チーム運用が始まったので、変える前に チーム体制.htmlとGitHub Issueのアサインで 「今そこを担当している人」を確認してから相談すること——固定の担当者がいない領域は PM/TL（チーム体制.html参照）に確認する。

03 · FAQ

よくある混乱

Q. Cub3D / レイキャスタの数学まで読むか？

A. ゲート2前は、Backendのゲームサーバー側（エンジン駆動）以外は不要。 説明用の深いエンジン資料や、印刷用全記録のレイキャスタ章は後回しでよい。

Q. codes/（C）を直してよいか？

A. 原則凍結。変更が必要な場合は、上の「モジュール境界」にある契約表を先に更新し、 設計書を直してから実装する（②WSプロトコル設計の原則に従う）。

Q. 進捗の正本はどれか？

A. GitHub Issuesと Projectが現在の実装状況の正本。 受入条件・依存関係・意思決定の理由は⑤ バックログ。 0-全体アーキテクチャ設計.mdの14日表は日程としては無効。

Q. 説明用資料はすべて読む必要があるか？

A. いいえ。自分が今取り組んでいる分野に関係する資料から読めば十分。 説明用/配下を通読する必要はない。
