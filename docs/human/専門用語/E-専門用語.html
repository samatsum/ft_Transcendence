01 · Platform layer

pf_* 層 — 画面まわりだけを差し替え可能にする継ぎ目

用語意味
pf_*（platform層）MLXに触る処理だけを10個の関数（pf_init・pf_presentなど）にくくり出したもの。ゲームロジックはこの関数名だけを呼び、中身がMLXなのかCanvasなのか何もしないのかを知らない。正本: codes/includes/platform/platform.h
native元のcub3Dどおり、MLX/X11でLinuxデスクトップに描く実装（platform_native.c）
webブラウザのCanvasに描くための実装（platform_web.c）。pf_presentは「何もしない」代わりに、JS側がWASMメモリを読んでCanvasに転送する
headless（ヘッドレス）「画面が無い」実装（platform_headless.c）。描画・入力デバイス・ループを一切持たない。サーバ用のsim.wasmやmake testの受入テストがこれを使う
framebuffer（t_framebuffer）「ピクセルへのポインタ・幅・高さ」だけを持つ構造体。MLXのt_imageの代わりに、draw_pixelが直接参照する
ループ反転元のcub3Dは「MLXが暇なたびにmain_loopを呼ぶ」構造だったのを、「1フレーム分の処理＝game_stepという普通の関数」に切り出し、呼ぶ側（MLX/ブラウザ/Node）をどれでも良くした設計変更。詳細はビルドと実行.html

02 · 3 build targets

3つのビルドターゲット

コマンド成果物用途
makecub3D（Linux実行ファイル）開発・回帰確認用。従来のcub3Dそのもの
make webrender.wasmブラウザで描くだけ。判定はしない
make simsim.wasmNodeサーバで判定だけ。描画コードは物理的にリンクされていない（SIM_RENDER_EXCLUDES）
make testsim_testheadless実装をネイティブビルドした受入テスト（85検査）
覚え方： render.wasm＝目（見た目だけ担当）、sim.wasm＝脳（勝敗の判定だけ担当）。 どちらも同じCソースから作るが、リンクするpf_*実装と含めるソースが違うだけ。

03 · sim public API

sim公開API — サーバが呼ぶ関数群

関数役割
game_create.cubのテキストからゲームを1つ作る（対戦1試合＝1インスタンス）
sim_set_inputある戦闘員の入力（移動・視点）をサーバから渡す
game_step1tick分だけゲームを進める。native/web/serverの3環境で呼ばれ方が違うだけで中身は共通
game_snapshot今の状態をフラットな数値配列として取り出す。JSON化はNode側の仕事（simはしない）
game_apply_snapshotクライアント専用。受け取ったスナップショットを表示用に書き込むだけで、判定はしない
game_set_input_sourceある席の入力元をAI⇔外部（人間）で切り替える。切断時のAI代替・復帰の要

正本: codes/includes/platform/sim.h

04 · Combatant

戦闘員統合 — 人もNPCも同じ1種類

用語意味
戦闘員（combatant）プレイヤーもAIも同じt_enemy構造体の1要素として扱う、という統合設計。違いはinput_sourceだけ
input_sourceAIかEXTERNAL（外部入力＝人間）かのフラグ。これを切り替えるだけで人間⇔AI代替が実現する
ハザード（is_hazard）マップ上の敵'M'のうち、席（プレイヤー枠）ではなく純粋な障害物として振る舞うもの
スポーン（spawn）戦闘員の初期・復帰位置。席ごとに固定で持つ

詳細はサーバ権威モデル.htmlの「戦闘員統合」章、 ゲームルール寄りの用語はG-専門用語.htmlへ。
