01 · Repository

リポジトリ構成 — 何がどこにあるか

トップレベルの各ディレクトリが「何の言語で書かれた、何を担当する部分か」を表にしました。 codes/だけ知っている状態から見ると、これが一番効きます。

ディレクトリ言語これは何か
codes/Cゲームエンジン本体。あなたが知っている部分。native / web / sim の3ターゲットに化ける元になるソース
web/C由来のWASM + 少量のJScodes/をブラウザ/Node向けに翻訳した成果物（render.wasm・sim.wasm）と、それを動かすための最小限のJS（engine_demo.jsなど）。フロント画面（React）とは別物 — 詳しくは下の「よくある勘違い」参照
app/backend/TypeScriptNode上で動くサーバー。認証・DB・WebSocket・sim.wasmの実行を担当。詳細はB・I用語集
app/frontend/TypeScript（React）ブラウザで動く画面。ロビー・対戦画面・プロフィールなど。詳細はF用語集
app/shared/TypeScriptbackendとfrontendが同じ型定義を使うための共有コード（zodスキーマなど）
infra/設定ファイルnginx・TLS証明書・Dockerfile。本番起動まわり
maps/ / textures/データゲームのステージ定義（.cubファイル）と画像素材
docs/Markdown / HTMLこの用語集を含む、プロジェクトの全ドキュメント。docs/ai/=AI向け英語、docs/human/=人間向け日本語（このページ）
archive/—更新されなくなった過去の文書置き場。読む必要は基本ない
よくある勘違い：web/ ＝ フロントエンド、ではない。 web/は「Cのエンジンをブラウザで動かすためのWASM変換結果」を置く場所で、 エンジンのレーン（E）の一部です。プレイヤーが実際に見るReact画面は app/frontend/で、こちらは完全に別のレーン（F）です。あなたが「web/は 何をしているか分かる」と言うとき、それは正しくエンジン側の話をしています—— app/frontend/はまた別に理解する必要があります。

02 · Architecture

アーキテクチャの基本用語

用語意味
クライアント / サーバクライアント＝各プレイヤーのブラウザ。サーバ＝app/backendが動くNodeプロセス1つ。全員のクライアントが同じサーバに繋がる
サーバ権威（server-authoritative）「本当のゲーム状態」はサーバだけが持ち、クライアントは表示するだけという設計方針。チートとズレを防ぐための一番重要な決定。詳細はサーバ権威モデル.html
プロトコル通信の「言葉の決まり」。このプロジェクトにはREST APIとWebSocketの2種類がある
REST APIブラウザが「GET /api/users/1」のようにHTTPでサーバへ1回ずつ要求を送る方式。ログイン・プロフィール取得などに使う（解説: AWS「RESTful API とは」）
WebSocket（WS）一度繋いだら繋ぎっぱなしで、双方向に小さいメッセージを送り合える通信方式。対戦中の入力・状態配信に使う（RESTだと繋ぎ直しのコストが高すぎる）（公式: MDN WebSocket API）
スナップショット（snapshot）サーバが今の試合状態を「写真」のように切り出してクライアントへ送るデータ。詳細はB・I用語集・サーバ権威モデル.html
tickサーバがゲームを1コマ進める単位（このプロジェクトは30Hz＝1秒に30回）。フレーム（描画の1コマ）とは別の概念

03 · Build & Run

ビルド・実行系の用語

用語意味
WASM（WebAssembly）Cのコードを、ブラウザやNodeがそのまま高速に実行できる形式へ翻訳したもの。詳細はビルドと実行.html（公式: MDN WebAssembly）
Emscripten（emcc）C → WASMへ翻訳するコンパイラ。gccの代わりに使う（解説: Weblio辞書「Emscriptenとは」）
コンテナ / Docker「アプリと、それが動くのに必要な環境一式」を1つの箱に詰めて配れるようにする技術。評価はdocker compose upという単一コマンドで動く必要がある（解説: AWS「Docker とは」）
Docker Compose複数のコンテナ（nginx・Node・DBなど）をまとめて起動する仕組み。docker-compose.ymlに定義されている（解説: Docker ドキュメント日本語化プロジェクト「Docker Compose 概要」）
CI（継続的インテグレーション）コードをpushするたびに自動でビルド・テストを走らせる仕組み（解説: GitHub「CI/CDとは」）。このリポジトリでは.github/workflows/ci.yml1本の中に3つのジョブが定義されていて、毎push・毎PRで並行して走る
起動スモーク（smoke test）「詳しく動作確認する」のではなく、起動してすぐ落ちないか（クラッシュしないか）だけを確認する、最も基本的な健全性チェック。語源は電子機器の試作品の電源を入れて発煙しないか調べる試験（公式: MDN用語集「Smoke Test」）。このリポジトリではnativeジョブが実マップ5枚を実際に起動し、5秒間クラッシュせず動き続けたら成功と判定する
sim（sim.wasm）Cエンジンを、判定専用（描画コードを含まない）としてビルドしたWebAssembly。サーバー（Node）がこれを実行し、衝突・勝敗・スコアだけを計算する。対になるのが描画専用のrender.wasm。詳細はE用語集の「3つのビルドターゲット」
モノレポ（monorepo）複数の独立したパッケージ（プロジェクト）を、1つのリポジトリにまとめて入れる構成（対義語はマルチレポ）。app/配下のshared・backend・frontendがnpm workspacesでこの構成になっており、sharedのzodスキーマを他2つが直接importできるのはこのおかげ（解説: GitLab「モノレポとは？」）
このリポジトリのCIは3ジョブ構成（2026-08-07時点、3つとも green）：
  • native — CエンジンをmakeでLinux実行ファイルとしてビルドし、make check（lint）・make test（sim受入テスト85件）・5枚のマップでの起動スモークまで通す
  • wasm — make web simでrender.wasmとsim.wasmをビルドし、Node上でrecord.mjsによるsim通し実行まで確認する
  • web-app — app/のTSモノレポ（shared/backend/frontend）をnpm ci・型検査・ビルドし、backendを実際に起動して/api/healthが返るか確認する
3つとも独立したジョブなので、どれか1つが赤くても他は影響を受けない（例: web-appだけ落ちていてもnativeとwasmは個別に緑になる）。 PRを出すと3つ全部が自動で走り、全部緑にならないとマージしてはいけない、というのがCIゲートのルール。

04 · Git / GitHub

Git・GitHub運用の用語

詳しい手順とルールはGit運用フロー.htmlにまとまっています。ここでは単語だけ先に。

用語意味
ブランチ（branch）作業内容をmainから分岐させた、独立した作業スペース（公式: Pro Git 日本語版 3章）
コミット（commit）変更内容に付ける「セーブポイント」（公式: Pro Git 日本語版 2章）
PR（プルリクエスト）「このブランチの変更をmainに取り込んでください」というGitHub上の提案。CIがここで走る（公式: GitHub Docs「プルリクエストについて」）
マージ（merge）ブランチの内容をmainに取り込むこと（公式: GitHub Docs「プル要求のマージ」）
squashブランチ内の複数コミットを1個にまとめてからマージする方式。このリポジトリの既定（公式: GitHub Docs「プル要求のマージ」の同ページ内）
CIゲート「CIが緑（成功）にならないとマージできない・してはいけない」という運用上の関所
