01 · What is "the server"

「サーバー」とは具体的に何か

app/backend/にあるTypeScriptプログラムが、Node.js上で1個のプロセスとして 動き続けているもの。全プレイヤーのブラウザが、この1つのサーバーに接続します。 入口はapp/backend/src/index.ts。

用語意味
Node.jsJavaScript/TypeScriptをブラウザの外（サーバー上）で動かすための実行環境。sim.wasmもこの中で動く（公式: Node.js公式サイト（日本語））
FastifyNode上でHTTP・WebSocketサーバーを組み立てるための土台（フレームワーク）。ルーティング・バリデーション・エラー処理を提供する。Express等の同系統ツールの中でも軽量・高速な選択肢（解説: Zenn「fastifyに入門してみた」、公式ドキュメントは英語のみ）
ミドルウェアすべてのリクエストに共通で挟まる処理（ログ出力、認証チェックなど）

02 · REST / Auth

REST APIと認証

用語意味
REST APIGET /api/users/1のように、URLとHTTPメソッド（GET/POST/PATCH/DELETE）の組み合わせでサーバー機能を呼ぶ設計方式（解説: AWS「RESTful API とは」）
エンドポイント個々のURL＋メソッドの組（例:POST /api/auth/login）
認証（Authentication）「あなたは誰か」を確認すること。ログイン処理がこれ
認可（Authorization）「あなたはこの操作をして良いか」を確認すること。認証の後に行う
argon2idパスワードのハッシュ化アルゴリズム。生パスワードは保存せず、これで不可逆変換した値だけをDBに置く（漏洩しても元のパスワードは分からない）（解説: Zenn「現代標準のパスワードハッシュ - Argon2とは」）
ソルト（salt）ハッシュ化前にパスワードへ混ぜるランダムな値。同じパスワードでも毎回違うハッシュ値になるようにし、辞書攻撃を防ぐ。argon2idには組み込み済み（公式: MDN用語集「Salt」）
Session（セッション）ログイン状態そのもの。サーバーのDBに「このユーザーはログイン中」という行として記録される
Cookieブラウザに保存される小さなデータ。ここにはセッションを指す不透明なトークンだけを入れ、リクエストのたびに自動送信させることでログイン状態を維持する（httpOnly＝JSからは読めない設定）（公式: MDN用語集「Cookie」）
Origin検証リクエストが「自分のサイトから」来たものかをチェックする仕組み。異なるサイトからの不正な変更リクエストを弾く（CSRF対策の一種）（公式: MDN用語集「CSRF」）
エラーエンベロープ失敗レスポンスの形式を全エンドポイントで統一するルール（{"error":{"code":...,"msg":...}}）
zodTypeScriptでデータの形をチェックする（バリデーションする）ためのライブラリ。フロントとバックが同じ定義を共有し「二重に検証する」要件を1つの定義で満たす（解説: Zenn「Zod 入門」、公式ドキュメントは英語のみ）
レート制限（rate limit）短時間に大量アクセスされたら拒否する仕組み。ログイン試行の総当たり攻撃などを防ぐ（公式: MDN用語集「Rate limit」）

03 · Database

データベースとORM

用語意味
DB（データベース）ユーザー・試合結果などを永続的に保存する場所。ファイルが消えない限りデータが残る（メモリ上の変数と違う）
SQLiteこのプロジェクトが使うDBの種類。サーバー独立プロセスを別途立てず、1個のファイルとして動くのが特徴。評価環境（単一マシン）に向いている（解説: JavaDrive「SQLite入門」、公式ドキュメントは英語のみ）
ORM（Object-Relational Mapping）DBのテーブルをTypeScriptのオブジェクトのように扱えるようにする層。生のSQL文を書かずに済む（解説: Wikipedia「オブジェクト関係マッピング」）
Prismaこのプロジェクトが使うORM。schema.prismaでテーブル定義を書き、TypeScriptの型を自動生成する（解説: Qiita「Prisma 入門」、公式ドキュメントは英語のみ）
マイグレーション（migration）「DBの構造をこう変えてください」という手順書。prisma migrateで適用する。初回起動時に自動で走る設計
スキーマ（schema）テーブルの構造定義（どんな列があるか、型は何か）

04 · WebSocket

WebSocketまわり — 対戦の心臓部

ここが「オンライン対戦」を実際に動かしている部分です。REST APIとは別の通信経路として、 ゲーム中はずっと繋ぎっぱなしにします。

用語意味
WS Gateway（WSゲートウェイ）WebSocket接続を受け付ける入口。ロビー用とゲーム用の2種類がある
GameRoom1試合＝1インスタンス。中でsim.wasmを30Hzで回し続け、参加者へsnapshotを配信する。複数の試合が同時に走るとGameRoomも複数存在する
tickサーバーがゲームを1コマ進める周期。このプロジェクトは30Hz（1秒に30回）
snapshot配信tickより粗い頻度（15Hz）で、全戦闘員の位置・向き・スコアなどをクライアントへ送ること。通信量を抑えるための間引き
入力（input）クライアント→サーバへ送る、プレイヤーの操作（移動方向・視点）。seqという連番を付けて、古い入力が新しい入力を上書きしないようにする
join / welcomeゲームWSに繋いだ直後のやり取り。joinで入室を要求し、welcomeでサーバーが初期状態（マップ本文など）を返す
切断猶予（grace period）接続が切れてもすぐ負けにせず、一定時間（30秒）は再接続を待つ仕組み。その間は席がAIに自動で代替される
再接続（reconnect）猶予時間内にブラウザが繋ぎ直すこと。サーバーはその席をAIから人間へ戻す

05 · Lobby / Matchmaking

ロビーとマッチメイキング

用語意味
ロビー（Lobby）対戦が始まる前に、プレイヤーが待機・マッチング相手を探す場所（画面としてもWSの状態管理としても存在する）
マッチメイキング複数プレイヤーを1つの試合に組み合わせる処理
キュー（queue）「対戦相手待ち」の列。FIFO（先入れ先出し）で処理される
カスタムルーム招待コードで友達だけを集めて始める部屋（自動マッチングと別経路）
MatchPlanロビー側が「この参加者たちで試合を始める」と確定させた計画データ。これを元にGameRoomが作られる
presence（プレゼンス）「オンライン中」「マッチング中」「対戦中」などのユーザーの状態。フレンドのオンライン表示に使う

06 · Infra

インフラ（配布・起動まわり）

用語意味
DevOps開発手法ではない。開発（Dev）と運用（Ops）を別チームに分けず、作った人が動かすところまで持つ、という考え方と、そのための実践（自動ビルド・自動テスト・自動デプロイ・監視）の総称。ScrumやXPのような「進め方の型」ではなく、文化・体制の名前（解説: AWS「DevOps とは」）。このレポで担当するのはI-レーンの2件だが、どちらも未着手——I-15（Docker/nginx/TLSで1コマンド起動。現状のdocker-compose.ymlにはwasmを生成するengine-buildしか無く、nginx.confも存在しない）とI-16（CIにフロントエンドのlint/typecheckを足す拡張）。ただしCIそのものは動いている——E-14で実装済みで全ジョブgreen。I-を「Infra / DevOps」と呼ぶのは、Infraだけだと名前からCIが漏れるため。なお課題書 IV.7 にも同名のモジュール分類があり、ボーナスで採用したヘルスチェック/ステータスページ（1pt）はそちら
nginxWebサーバー/リバースプロキシ。TLS（HTTPS化）と、リクエストをFastifyへ橋渡しする役目（解説: Zenn「NGINXのリバースプロキシ機能を使う」、公式ドキュメントは英語のみ）
リバースプロキシ外部からのアクセスを一旦受け取り、内部の別サーバーへ転送する仕組み
TLS / HTTPS通信を暗号化する仕組み。評価要件で全接続がHTTPSであることが必須（公式: MDN用語集「HTTPS」）
自己署名証明書（mkcert等）正式な認証局を通さず自分で作るTLS証明書。ローカル評価環境ではこれで済ませる
Docker Composenginx・Node（backend）・DB用ボリュームなど複数コンテナを1コマンドでまとめて起動する定義（docker-compose.yml）（解説: Docker ドキュメント日本語化プロジェクト「Docker Compose 概要」）
env / .envパスワードやポート番号など、環境ごとに変える設定値。Gitには含めず（.gitignore）、.env.exampleにひな形だけ置く
