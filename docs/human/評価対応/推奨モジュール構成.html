42評価 · D-19（2026-08-08 採用）

残作業を最小にして
14pt＋5ptを取る構成。

全55モジュールの洗い出しで見つかった候補を踏まえて、 「同じ14ptなら、残っている作業が一番少ない組み合わせはどれか」という観点で組み直した構成。 現行計画（42モジュール対応表.html）との違いは、 高価なモジュールを、すでに完成しているもの・ほぼ完成しているものへ差し替える点にある。 この構成は2026-08-08に正式採用されたため、 42モジュール対応表.htmlと architecture.md §4も、すでにこの内容へ更新済み。

2026-08-08に正式採用された（D-19） 正本の architecture.md §4 は更新済み。このページは「なぜそう変えたか」の記録
考え方 推奨・必須14pt 推奨・追加5pt 現行計画との差分 削れる作業 リスクと次善策

01 · Principle

2つの原則で組み直した

原則1

必須14ptには、却下されにくいものだけを置く

14ptは合格ライン。ここに解釈の余地があるモジュールを置くと、 当日却下された瞬間に不合格になる。実演すれば誰が見ても明らかなものだけで14ptを組む。 解釈が割れうるものは、落ちても影響しないボーナス側へ回す。

原則2

同じptなら、残作業が少ない方を採る

モジュールのptは難易度と無関係。2ptのために新しいサブシステムを作るより、 すでに動いているものを2ptとして申告する方が合理的。 エンジン側は完成済みなので、この判断で浮く工数が大きい。

前提として動かせないもの: 課題書 第III章の必須要件（FE+BE+DBのWebアプリ、メール+パスワード認証のハッシュ化、 単一コマンド起動、全接続HTTPS、Privacy/ToS、レスポンシブ）はモジュールとは無関係に必須。 つまり W-02〜W-05・W-15・F-03・F-04・F-11 は、どの構成を選んでも必ずやる。この改訂はその「必ずやる分」の外側だけを組み替えている。

02 · Recommended core

採用した必須14pt

8モジュールで14pt。4モジュール（8pt）がすでに完成またはエンジン側完成で、 残り4モジュールも「必ずやる認証・ロビー作業」が終われば自動的に成立する。 新規サブシステムの追加はゼロ。

#モジュール区分pt今の状態成立に必要な残作業
1完全なWebベースのゲーム（RSP）Gaming Major2エンジン完成ログイン→ロビー導線（必須作業に含まれる）
2リモートプレイヤーGaming Major2実証済み同上。W-12の30秒切断復帰は実装済みで、むしろ強い実演材料
3マルチプレイヤー（3人以上）Gaming Major2エンジン完成同上（RSP 2v2＝4人）
4FE/BE双方でフレームワークWeb Major2完了なし
5WebSocketsのリアルタイム機能Web Major2ゲームWSは完了W-08のロビーWS結合（必須作業に含まれる）
6AI対戦相手AI Major2完了なし（現行計画ではボーナス扱いだったものを必須へ昇格）
7ORMの使用（Prisma）Web Minor1未着手W-03のみ。DBは第III章で必須なので、どのみち作る＝実質タダ
8ゲームカスタマイズオプションGaming Minor1エンジン側完成マップ選択と先取点の選択UI（ロビー画面の一部）
ポイント: 「AI対戦相手」を必須側へ動かした。 すでに完成していて実演も容易な2ptを、合格ラインの内側に置く。 現行計画ではここがボーナス扱いで、代わりに未着手の「標準的なユーザー管理」2ptが 必須側に入っていた——完成品を保険に回し、未着手のものを命綱にしていた形になる。

03 · Recommended bonus

採用した追加5pt

ボーナスは上限+5pt。ここには「安い」か「落ちても構わない」ものを置く。 4モジュールで5pt、いずれも新規サブシステムを必要としない。

#モジュール区分pt今の状態成立に必要な残作業
9高度な3DグラフィックスGaming Major2実装は完成コードはゼロ。READMEに正当化を書くのみ。
ただし却下リスクあり（→§06）
10カスタムデザインシステムWeb Minor1部品9個が存在再利用可能部品をあと1個＋パレット/タイポグラフィの文書化
11観戦モードGaming Minor1土台のみWSのspectateアクション実装＋視点切替UI（F-12）
12ヘルスチェック/ステータスページDevOps Minor1/api/health済ステータスページ＋自動バックアップ・復旧手順
ボーナスは必須14ptが全て揃って初めて加算される（課題書 第VII章）。 先にボーナスへ手を出さないこと。実装順は必ず「必須14pt → 完成 → ボーナス」。

05 · What this saves

この改訂で、着手しなくてよくなったIssue

下のIssueは、上の構成を採る限りモジュール獲得のためには不要になる。 （製品として作りたいなら別の理由で作ればよいが、点数のためには要らない。）

Backend

W-06 / W-07 / W-13

W-06 アバターアップロード（2MB制限・MIME/マジックバイト検査・nginx静的配信）、 W-07 フレンドAPI（申請・承認・削除・presence合成）、 W-13 試合永続化と統計API。 いずれも「標準的なユーザー管理」「ゲーム統計」を外したことで不要になる。

Frontend

F-09 / F-10

F-09 プロフィール/統計/履歴画面＋自己編集＋アバター、 F-10 フレンドUI（presenceバッジのリアルタイム更新）。 どちらも上記バックエンドに依存していたもの。

5つのIssueが不要になる。 一方で、増える作業は「観戦のspectateアクション＋F-12」「部品1個＋文書化」 「ステータスページ＋バックアップ手順」の3つで、いずれも上記5つより明らかに軽い。 3Dグラフィックスに至っては追加作業ゼロ。

06 · Risks

リスクと、その次善策

リスク影響対策
3Dグラフィックスが却下される
（評価者が「Three.js等のライブラリ必須」と読む）		 ボーナス5pt→3pt。合格ラインには影響しない そもそも必須側に置いていないのが対策。加えて、レイキャスティングの実装内容（テクスチャマッピング・深度バッファ・スプライト描画）を説明できるようにしておく
ゲーム系4モジュール（#1/#2/#3/#5＝8pt）が
ロビー未完成で実演できない		 致命的。合格ラインを割る ここが本当の急所。F-05（ロビー）とF-03（ログイン）は最優先。フロントエンド開発工程参照
時間が余った場合 — 真っ先に戻すのは別のゲーム（FPS, 2pt）。W-13を作れば同時にゲーム統計（1pt）も復活し、W-13ひとつで3pt分になる。その時点で最もリスクの高いモジュールと差し替える
