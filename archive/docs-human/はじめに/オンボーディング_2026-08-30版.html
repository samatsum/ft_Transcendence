01 · Now

いま何を作っているか

42の課題 ft_transcendence: ブラウザで遊べるオンライン対戦（cub3D由来のエンジンをWeb化）。 Cエンジンは予定作業を完了しており、これからTypeScriptのBackend / Frontendを積み上げる段階（FPSにあった欠陥G-11（FPSの射撃で相手席を消せる）・G-12（FPSで相手の見た目が無い）はいずれも2026-08-09に修正済み）。

状態内容
完了 Cエンジン（codes/ / web/）。判定を担う sim.wasm と、描画を担う render.wasm。
これから TypeScriptのBackend / Frontend（app/）。次の関門はゲート2。
ゲート2の定義: 複数ブラウザでRSP（じゃんけん鬼ごっこ）対戦が最後まで成立すること。 これが結合デモのgo/no-go関門であり、連番の課題番号ではない。 日程の正本は⑤ バックログ §6（Gate/schedule mapping）。

要件の一次情報: ai/requirements.md（旧 01_課題/ft_トランセンデンス.md）

02 · Lanes & roles

開発レーンと管理役割

このプロジェクトの実装は5つの開発レーンに分かれる。レーンは「どこで動くか」ではなく 「何のコードで、誰が保守するか」で分けている。 誰が何を担当するかは体制によって変わるが、境界そのものは変わらない共通の地図として使える。 定義の正本はGit運用フロー §05。 2026-08-30以降、レーンはIssueに貼るラベルとしてのみ使い、「誰がそのレーンにいるか」を 固定的に管理する運用はやめた——現在のメンバー・役割は⑥ チーム体制。

Lane · E- / G-

Engine

codes/とweb/のCエンジン。native / render.wasm / sim.wasmの3ターゲット、 対戦ルール、AI、マップ。予定作業は全件完了。後から見つかったG-11・G-12も修正済み。

Lane · B-

Backend

Fastify・認証・REST・WS・GameRoom・DB。 中身は性質の違う2種類に分かれる——基盤（B-02〜B-05: 普通のWebアプリのCRUDと認証）と、 ゲームサーバー（B-08〜B-12・B-17: 30Hz tick・snapshot・再接続）。 必要な経験が違うので、着手先を選ぶときはここを見る。

Lane · I-

Infra / DevOps

リポジトリ骨格とツーリング、Docker / nginx / TLS、CI。 「空のcloneからdocker compose upだけで起動する」を成立させる担当。

Lane · F-

Frontend

一般Web画面。認証画面、共通レイアウト、ロビー、レスポンシブ。 対戦そのものではない画面を担う。

Lane · GV-

GameView

ゲーム画面。Canvasとrender.wasmの統合、HUD、試合遷移、観戦UI。 F-と分けてあるのは、WASMとWebSocketに触るかどうかで必要な知識が大きく違うため。

なぜrender.wasmがFrontendではなくEngineなのか: ブラウザで動くのにEngineなのは、レーンを実行場所ではなくコードの正体で分けているから。 同じraycast.cがnativeバイナリとrender.wasmの両方にコンパイルされるので、 実行場所で線を引くと1つのソースファイルが2レーンに割れてしまい、担当境界として機能しない。
課題書の4レーンとの対応: 課題書 II 章が想定するのは Engine / Backend・DevOps / Frontend / Gameplay の4本。 運用上のレーンと、課題書の科目としての枠は別物という点に注意。 E-とG-は運用上は1本のEngineレーン（接頭辞が2つあるのは、完了済みの作業を振り直す利益が無いから）だが、 課題書の枠に当てはめるとG-の中身がGameplayに相当する。 残りはB-＋I-＝Backend・DevOps、F-＋GV-＝Frontend。 2026-08-08まではさらに別の呼び方（「ゲームサーバーレーン」「非ゲームUIレーン」など）も並立していたが、 3種類の語彙が混在して分かりにくかったため上の1本へ統一した。 古いコミットやIssueに残るW-の読み方は Git運用フロー §05の対応表を参照。
管理役割（課題書 II.1.1）: テクニカルリード（TL）、プロジェクトマネージャー / スクラムマスター（PM/SM）、 プロダクトオーナー（PO）、開発者（専任）の4種。 全員が開発者であり、管理役割は開発と兼任できる。 評価では「自分の役割と貢献」を説明できる必要がある。

04 · Boundaries

モジュール境界（ここだけ合意すれば並行できる）

正本はこのページ（旧「⑥チーム分担計画」§4の内容を移設）。 担当者が誰であっても、この契約の境界自体は変わらない。

契約所有レーン主な消費レーン
app/shared/のzod（型の単一情報源） B- Backend（F- Frontendが必須レビュアー） 全レーン
REST API B- Backend（基盤側） F- Frontend
WSプロトコル（メッセージ形・GameRoom） B- Backend（ゲームサーバー側） GV- GameView（＋ロビーWSはF- Frontend）
sim公開API / snapshot受信・補間（C側） E- Engine（完了・原則不変） B- Backend / GV- GameView
最優先の同期: B-（ゲームサーバー側） ⇄ GV- GameView のsnapshot JSON形（②WSプロトコル設計のsnapshot節）。
次点: B-（基盤側） ⇄ F- Frontend のエラーエンベロープとCookie。

契約を変えるときは設計書を先に直してから実装する （②WSプロトコル設計自身が「実装が本書と食い違ったら、まず本書を直してから実装せよ」と明記している通り）。 元は「所有レーンの担当者に相談してから」というルールだったが、samatsum単独稼働の現状では 相談する相手が別にいないため、この原則だけが残っている。

05 · FAQ

よくある混乱

Q. Cub3D / レイキャスタの数学まで読むか？

A. ゲート2前は、B-のゲームサーバー側（エンジン駆動）以外は不要。 説明用の深いエンジン資料や、印刷用全記録のレイキャスタ章は後回しでよい。

Q. codes/（C）を直してよいか？

A. 原則凍結。変更が必要な場合は、上の「モジュール境界」にある契約表を先に更新し、 設計書を直してから実装する（②WSプロトコル設計の原則に従う）。

Q. 進捗の正本はどれか？

A. Issue受入・ゲート定義・日程（Gate/schedule mapping） → ⑤ バックログ §6。 0-全体アーキテクチャ設計.mdの14日表は日程としては無効。

Q. 説明用資料はすべて読む必要があるか？

A. いいえ。自分が今取り組んでいる分野に関係する資料から読めば十分。 説明用（説1〜説12）を通読する必要はない。
