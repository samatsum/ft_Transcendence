## 0. 結論（先に）

| 案 | 実働の核 | 提出目安（evaluation 完成度） | 納期短縮の現実性 |
|---|---|---|---|
| **A** 実働偏り4人 | 実装に寄与しうる時間 **12h/日**（4+4+3+1） | **約 5〜6 週**（〜**2026-09-19** 前後） | 三人称では最短帯。ただし **1h枠はほぼ実装戦力にならない** |
| **B** 実装1人＋学習ロボット | samatsum **4h/日**のみが実装クリティカル | **約 16 週**（〜**2026-11-28** 前後） | **納期短縮目的では非現実的**（前回6h前提の9週よりさらに長い） |
| **C** 実装2人＋PM（非実装）＋ロボット | 実装 **8h/日**＋ torinoue PM **4h/日** | **約 6〜7 週**（〜**2026-09-26** 前後） | Bより大幅短縮。**Aより短いとは限らない**（実装スループットがAより少ない） |

納期だけ見るなら **A ≳ C ≫ B**。  
「3人以上は合意コストで伸びる」は **実装者を増やすほど**当たりやすく、**PMを1人置いて実装を2人に閉じる（案C）**は通信を星型に畳める。案Cの価値は「三人目のコーダー」ではなく **調整の外部化**。

本レポートの数字に余裕はない。

## 1. この分析の名前（何と呼ばれるか）

実務・教科書で近い呼び名は次のとおり。単一の正式名称というより、**いくつかを重ねた分析**になる。

| 呼び名 | 何を見ているか |
|---|---|
| **チーム規模と調整コスト分析**（coordination cost / communication overhead） | 人数が増えると合意・同期・レビュー待ちが増える |
| **通信経路数の議論**（しばしば Brooks に紐づく） | \(n\) 人の全結合で経路は \(n(n-1)/2\)。2人=1、3人=3、4人=6、5人=10 |
| **Brooksの法則**（Brooks's Law） | 「遅れているプロジェクトに人を足すとさらに遅れる」— 学習・通信がスループットを食う、という警句 |
| **資源制約付きスケジュール**（resource-constrained scheduling / critical chain） | 人時合計だけでなく、**誰が何h/日か**とクリティカルパスで暦が決まる |
| **限界生産力の逓減**（チームへの応用） | 1h/日の追加メンバーは、オンボと合意コストの方が大きく **純増がゼロや負**になりうる |
| **ハブ＆スポーク / チームトポロジ** | PMを中心にすると「全員合意」が「PM経由の双方向」に減る（案Cの狙い） |

PMとしての一言: **「人数を増やす＝納期が縮む」ではない。増やす対象が実装スループットか、調整か、学習ロボットかで符号が逆になる。**

## 3. 調整コストの構造（なぜ3人以上で重く感じるか）

### 3.1 経路数

| 意思決定に乗る人数 \(n\) | 全結合の経路数 | 意味 |
|---|---:|---|
| 2 | 1 | 合意は一対一 |
| 3 | 3 | まだ回る。PMがハブなら実質 2本 |
| 4 | 6 | 「残りへの展開」が発生しやすい |
| 5 | 10 | 1h枠を含めても同期コストは人数分乗りやすい |

PM視点の典型パターン:

1. **二人で技術合意**する  
2. **残り n−2 人に同じ絵を配る**（再説明・Issue更新・ロールの体裁）  
3. **異議や誤解の回収**が経路数に比例して増える  

案AでメンバーBが1h/日のとき、（2）と（3）に対する貢献が小さく、**説明コストだけが残る**ことが多い。

### 3.2 実装スループット vs 調整

```text
納期 ≒ f( 実装スループット, クリティカルパス, 待ち, 調整オーバーヘッド )
```

| レバー | 効く条件 |
|---|---|
| 実装者を足す | 足した人の **日次hがレーンを持てる**（目安: 継続3h以上＋オンボ済み） |
| PMを足す（非実装） | 実装者が調整から解放され、**待ち28のうち同期・優先度分が減る** |
| 学習ロボット | 提出日は縮まない。VIII耐性だけ上がる |

## 4. 案A（再計算）— 実働 4+4+3+1

### 4.1 人時

| 区分 | 人時 |
|---|---:|
| 実装 | 172 |
| 待ち・手渡し・レビュー・オンボ・PM | 28（4交点前提。1h枠がボトルネックを増やす分は暦で見る） |
| **計** | **200** |

### 4.2 スループット

| | 値 |
|---|---|
| 名目キャパ | 4+4+3+1 = **12h/日**（週60h） |
| 実装に効きやすい時間 | おおよそ **4+4+3 = 11h/日**（1h枠はレビュー・文言・Issue補助向き） |
| 単純割り | 200 / 11 ≒ **18稼働日** ≒ 3.6週 |

### 4.3 暦（粗い）

クリティカル（Auth → 結合 → FE）と1h枠のオンボ負荷を踏まえ:

| | 目安 |
|---|---|
| ゲート2 | 約 **3〜4.5 週** |
| evaluation 完成 | 約 **5〜6 週** → **2026-09-12 〜 09-19** 前後 |

1hメンバーを「第四の実装レーン」にすると破綻しやすい。案Aを活かすなら **Bは補助専任**（Issue、文言、理解資料の追記、小さなFE）に固定する。

## 6. 案C（新）— 実装2人 + torinoue（PM/Auth・非実装）+ ロボット 3h/1h

### 6.1 役割

| 人 | 日次 | やること | やらないこと |
|---|---|---|---|
| samatsum | 4h | TL・ゲーム鯖・必要に応じFE/BE実装 | 全員合意の司会を一人で抱え込まない（torinoueへ） |
| 別実装者 | 4h | BE/FEの実装レーン（Auth実装含む） | 優先度の最終決定（PM） |
| torinoue | 4h | PM、Authの受入・設計確認、II.1.2、理解ドキュメント主導 | **コード実装しない**（前提どおり） |
| ロボットA | 3h | 担当レーン理解・説明練習 | 実装クリティカルに乗せない |
| ロボットB | 1h | 同上（浅い） | レーンオーナーにしない |

Auth「所有」と「実装しない」の両立: **受入・仕様・curlシナリオ・レビューは torinoue、実装コミットは二人の実装者**。境界を文書化しないと案Cは崩れる。

### 6.2 人時

| 区分 | 人時 | 根拠 |
|---|---:|---|
| 実装 | 172 | 変更なし |
| 待ち・手渡し | **14** | 交点は主に実装者2＋PMハブ。案Aの28より少ない |
| 理解ドキュメント | 34 | 評価耐性。torinoueが過半を書ける |
| **提出に効く合計（目安）** | **220** | ただし文書の多くはPM時間と並行消化 |

### 6.3 スループットと暦

| | 値 |
|---|---|
| 実装キャパ | 4+4 = **8h/日**（週40h） |
| PMキャパ | **4h/日**（週20h）→ II.1.2週7 + 文書・受入に充当 |
| 実装の単純割り | 172 / 8 ≒ **21.5稼働日** ≒ 4.3週 |
| 待ち14 | +約2稼働日 |
| 文書34 | PM週20のうち文書に回せば **約2週分**で消化可能（実装と並行） |

| | 目安 |
|---|---|
| ゲート2 | 約 **4〜5.5 週** |
| evaluation 完成 | 約 **6〜7 週** → **2026-09-19 〜 09-26** 前後 |

### 6.4 案CがAより短くならない理由

- 案Aの実装に効く時間 ≒ **11h/日** vs 案C **8h/日**  
- torinoue を非実装にすると **Auth実装の手が二人に寄る**（専門は増えるがスループットは減る）  
- 案Cが勝つのは、「Aの3h+1hが調整負けしている」「PM不在で待ち28が膨らんでいる」とき  

逆に、Aの3hが安定してFEレーンを持てるなら **Aの方が納期向き**。

## 7. 三点比較表

| | 案A | 案B | 案C |
|---|---|---|---|
| 実装スループット | 高（〜11h/日） | 最低（4h/日） | 中（8h/日） |
| 調整経路 | 6本（4人全結合） | 実装は1人（体裁通信は別） | 実装1本＋PMハブ |
| 待ち人時 | 28 | ≒0（実装） | ≒14 |
| 1h枠の影響 | 実装戦力にならない。説明コストは残る | 学習が浅い。VIIIリスク | ロボットB同様。レーンを持たせない |
| PM負荷 | 分散 or 兼務 | samatsumに集中（週7が実装を食う） | **torinoue 4hが吸収** |
| 提出目安 | **5〜6週** | **〜16週** | **6〜7週** |
| 目安日 | 〜09/19 | 〜11/28 | 〜09/26 |
| 失敗モード | 合意爆発・1h枠の誤配置 | 単一点障害・理解不足 | Auth「非実装PM」境界の曖昧さ |
| 納期短縮 | 相対的に最良帯 | 不適 | Bより遥かに良い。A超えは条件付き |

```text
納期:   A ≲ C ≪ B
通信:   B（実装）< C < A
評価耐性: 学習投資次第（ロボット3hは効く。1hは限定的）
```

## 8. PMとしての推奨

1. **納期が第一なら案Bは捨てる**（4h前提で約16週）。  
2. **案A vs 案C**  
   - FEを3hで継続できる人がいる → **案A**（Bは補助固定）  
   - 3hが不安定／調整がすでに重い → **案C**（実装を2人に閉じ、torinoueはPM+Auth受入）  
3. **1h枠**はどの案でも「第四実装者」にしない。学習ロボット or Issue/文言補助。  
4. 案Cを採るならキックオフで一文合意: **「Authのコードは実装者、受入のサインは torinoue」**。  
5. 理解ドキュメント34は案B/Cで必須。案Aでもレーン別が無いとVIIIが弱い（現行 `docs/` に担当別が無い問題は継続）。
