## 0. 結論（先に）

評価（evaluation）に出せる完成度までの目安。数字の前提は §2 以降。

| 案 | 誰が手を動かすか | いつ頃出せそうか | ひとことで言うと |
|---|---|---|---|
| **A** 実働4人（時間の偏りあり） | 実装に使える時間の合計 ≒ **1日12時間**（各自の「正味」） | **およそ5〜6週間後**（**2026-09-12〜09-19**ごろ） | **いちばん速い候補**。週あたりの実装の進みは三人の中で最大。ただし新人対応で samatsum の実装時間が削られる |
| **B** 実装は1人＋学習役3人 | 実装の進みを止めるのは samatsum **正味6時間/日**だけ | **およそ7週間後**（**2026-09-26**ごろ） | PMを torinoue に寄せたので、以前の「約16週間」案より短い。それでも **A・Cより遅い** |
| **C** 実装2人＋PMは実装しない＋学習役 | samatsum は週30時間。もう1人は **週末にまとめて週14時間** | **およそ5.5〜6.5週間後**（**2026-09-19〜09-26**ごろ） | Bより速い。週末に作業が寄るので **週をまたぐ待ち**に注意。Aより速いとは限らない |

```text
納期の早さ（本前提）:  A が最速寄り  ≦  C  <  B が最遅寄り
```

- 週あたりの実装の進み（後述のスループット）: **A（週おおよそ60時間）> C（週44時間）> B（週30時間）**
- このレポートの数字に余裕はない（「多めに見ている」つもりで読まないこと）

## 1. この分析は何をやっているか（用語の説明）

ひとつの決まった科目名ではない。納期を決めるときに、次の見方を**重ねて**使う、という話。

### 1.1 スループット（throughput）＝作業の進む速さ

| | 内容 |
|---|---|
| カタカナ | **スループット** |
| 英語 | **throughput** |
| 意味 | **決まった時間のなかで、どれだけ仕事を進められるか**。ここでは「1日または1週間に消化できる実装の人時」 |
| 日本の現場・CSの授業 | だいたいこのカタカナ（または「処理能力」）。漢字の「吞吐」は日本ではほぼ使わない（中国語圏の訳語） |
| この文書での例 | 案Aは実装に使える時間が合計おおよそ1日12時間。案Cは平日の samatsum 6時間に加え、別実装者が週末に週14時間、など |

注意: チーム全体のスループットが上がっても、**一番細い一本道（クリティカルパス）上の人が忙しい／遅い**と、納期は伸びる。

### 1.2 調整コスト（人と人が合意するのにかかる時間）

| 呼び名 | 英語（参考） | 見ていること |
|---|---|---|
| チーム規模と調整コスト | coordination cost / communication overhead | 人数が増えると、相談・同期・レビュー待ちが増える |
| 通信の経路の数 | communication paths | \(n\) 人が全員つながると、経路は \(n(n-1)/2\) 本 |

| 人数 \(n\) | 経路の数 | 感覚 |
|---:|---:|---|
| 2 | 1 | 二人だけなら一本 |
| 3 | 3 | まだ回しやすい。PMが窓口なら実質もっと少ないことも |
| 4 | 6 | 「二人で決めたことを残りに説明する」が増えやすい |
| 5 | 10 | 1日1時間しか働けない人がいても、説明の相手は増える |

案Aで起きていること: 新人が増えると、samatsum への **今すぐ答えてほしい質問**（DM・通話待ち・Issueの口頭説明）が増える。拘束6時間のうち **2時間**がここに消え、実装に残るのは **正味4時間/日**。

### 1.3 Brooksの法則（Brooks's Law）

> 遅れているソフトのプロジェクトに人を足すと、かえって遅れることがある。

よく言われる理由は次の二つ。

1. **慣れの期間**: 新人が質問し、既に詳しい人の時間が削られる  
2. **連絡の増え方**: 上の表どおり、人数が増えると「誰と誰が話すか」の組み合わせが増える  

このリポジトリはこれまで **samatsum 一人**で進んできた。案Aはまさに「人を足す局面」で、その代償が **正味4時間（6−2）** として数字に入っている。

### 1.4 「合計何時間」だけでは足りない（誰が何時間か）

| 呼び名 | 英語（参考） | 見ていること |
|---|---|---|
| 資源を考えた日程の立て方 | resource-constrained scheduling | 「合計200人時」だけでは足りない。**誰が、1日何時間か** |
| クリティカルパス／クリティカルチェーン | critical path / critical chain | 遅れが全体を止める一本道と、その上の人の細さ |

例: 仕事の合計時間が同じでも、認証（Auth）を「週末だけ働く人」だけに任せると、平日は認証が進まない。

### 1.5 ほかに知っておくとよい言い方

| 呼び名 | 見ていること |
|---|---|
| 人が増えても効果が弱くなること | 1日1時間の追加メンバーは、教わる時間と質問の方が大きく、得がゼロやマイナスになりうる |
| PMを窓口にする（ハブ型） | 「全員で毎回合意」より「まずPMに集約」の方が連絡が減ることがある（本版で PM＝torinoue にした理由） |

### 1.6 一文でまとめると

**人数を増やせば納期が縮む、とは限らない。**  
増やすのが (1) 実装のスループット（throughput）か (2) 調整係か (3) 評価のための学習係か、で効果が変わる。  
本版では **PMを torinoue に固定**し、samatsum には課題書 II.1.2 の運用工数を載せない。

## 3. 案A — 実働4人（通信込み）

### 3.1 なぜ samatsum は正味4hか

一人開発から複数人へ移る局面では、Issue の意味や境界を **同期的に**伝える必要が出る。  
名目6hのうち2hをその待ち・説明に充て、**実装正味4h/日**とする。

### 3.2 人時とスループット

| 区分 | 人時 |
|---|---:|
| 実装 | 172 |
| 待ち・手渡し・レビュー・オンボ等 | 28 |
| **計** | **200** |

| 人 | 実装寄与/日 |
|---|---:|
| samatsum | 4 |
| torinoue（Auth実装。PMは別途伸長） | 4 |
| A | 3 |
| B | 1 |
| **合計** | **12h/日**（週60h） |

単純割り: 200 ÷ 60h/週 ≒ **3.3週**（理想）。  
クリティカルパスと1h枠の制限を踏まえ、evaluation は **約5〜6週**。

| | 目安 |
|---|---|
| ゲート2 | 約 **3.5〜4.5 週** |
| evaluation 完成 | 約 **5〜6 週** → **2026-09-12〜09-19** |

1h枠（B）はレーンオーナーにしない。

## 5. 案C — 実装2人＋PM非実装＋ロボット

### 5.1 役割

| 人 | 稼働 | 内容 |
|---|---|---|
| samatsum | 正味 **6h/日×平日**（週30h） | TL・実装。PMしない |
| 別実装者 | **週14hを週末3日に集約**。平日原則ゼロ | 実装のみ（別プロジェクトあり） |
| torinoue | 日次伸長可 | PM、Auth受入、II.1.2、理解ドキュメント主導。**コード実装しない** |
| ロボットA/B | 3h / 1h | 学習のみ |

Auth: **受入は torinoue、実装は二人のどちらか**。クリティカルな Auth を週末専用の人だけに載せると、平日が進まない。**Auth/結合は samatsum 平日側に載せる**のが安全。

### 5.2 人時

| 区分 | 人時 |
|---|---:|
| 実装 | 172 |
| 待ち・手渡し | **14**（交点が少ない。週末バッチ分の週境界待ちを暦で加算） |
| 理解ドキュメント | 34（torinoue 並行） |

### 5.3 スループットと暦

| | 値 |
|---|---|
| 週次実装キャパ | 30 + 14 = **44h/週** |
| 実装172の単純割り | 172 ÷ 44 ≒ **3.9週** |
| 待ち14 | ≒ **+0.3週** |
| 週末バッチの週境界 | 手渡しが週1に寄る → **+0.5〜1週** みておく |
| 文書34 | torinoue が並行消化 |

| | 目安 |
|---|---|
| ゲート2 | 約 **4.5〜5.5 週**（Authを平日側に置いた場合） |
| evaluation 完成 | 約 **5.5〜6.5 週** → **2026-09-19〜09-26** |

週末14hは、平日2h×5＝10hより **週あたりの実装量は多い**。一方で「毎日少し進む」のではなく「週に一度まとめて進む」ため、レビューや結合のリズムが週次になる。

| | 案A | 案B | 案C |

```text
週次の実装スループット（throughput）:  A (60) > C (44) > B (30)
納期目安:                              A ≲ C < B
```

## 7. PMとしての推奨

1. **納期第一なら案Bは本線にしない**（改善後も約7週で三人の中ではいちばん遅い）。  
2. **案A**: 新人流入時の samatsum 正味4hを守り切れるか（通信2hが3hに膨らまないか）が鍵。  
3. **案C**: 別実装者の週末14hは週次スループットを上げる。ただし **クリティカルパスを週末専用にしない**。  
4. 1h枠は全案でレーンオーナーにしない。  
5. 旧三点比較ファイルの数字と混ぜない（PM負担の前提が違う）。
