## 1. 戦略の要約（案B）

### 1.1 ねらい

4人のあいだのコミュニケーション（設計相談・ブロッカー同期・レビュー往復）にかかる時間を削り、実装速度を **単一実装者（samatsum）＋AI** に集約する。

### 1.2 運用イメージ

| 項目 | 内容 |
|---|---|
| 実装 | samatsum が AI を使い、PO / PM / TL / Developer 相当の成果物を生成 |
| ロール表記 | README 上は4人に PO / PM / TL / Developer を割り振る（課題書 II.1.1） |
| コミット体裁 | 成果物を git 外で受け渡し、**各人の Git アカウントから手動コミット** |
| レビュー | **samatsum が行う**（体裁上は「他メンバーの変更を TL がレビュー」） |
| 他3人 | **ロボット**：毎日固定時間、担当範囲の理解ドキュメントを読み、説明・短時間改変に耐える |
| 理解資料 | 共通1本＋レーン別4本（本レポート §4） |
| II.1.2 | 定例・Issue・レビュー記録などを **満たしているように運用**（週7人時を samatsum 側に計上） |

### 1.3 合意が必要な前提（数値前提）

| # | 前提 |
|---|---|
| 1 | 見積対象の純作業は **実装者（samatsum）の人時**（他3人の学習3h/日は提出クリティカルに載せない） |
| 2 | samatsum **6h/日・週5日**。II.1.2 **週7h** → 実装・文書に使えるのは **週23h** |
| 3 | 他3人は **毎日3h**、担当レーンを読み、説明できるところまでやる |
| 4 | スコープはキックオフ議論と同じ残作業全体（W-06/07含む。F-12は任意） |
| 5 | **AI による工数短縮は見込まない**（短縮なし） |
| 6 | 「提出」＝ evaluation に出せる完成度（README・ロール・理解ドキュメント含む） |

## 2. 比較：案A（実働4人）vs 案B（実働1人＋体裁4人）

### 2.1 工数・暦

| | 案A 実働4人 | 案B 実働1人＋体裁 |
|---|---|---|
| 実装人時 | 172（待ち除く）＋待ち・運用28 ≒ **200** | 実装 **172**（待ち28はほぼ消滅） |
| 理解ドキュメント | レーン別オンボが別途必要だったが未整備 | **34**（共通1＋レーン4＋README整合）を必須計上 |
| II.1.2 | 4人に分散しうる | samatsum に **週7h** 集中 |
| 純作業（提出クリティカル） | 約200人時を4人で並行 | samatsum **206人時**（172+34）を直列 |
| 稼働仮定 | 1人4h/日 | samatsum 6h/日（正味週23h） |
| 提出目安 | **約4〜5週** | **約9週（2026-10-10前後・約63日後）** |
| ゲート2だけ先行 | 約2.5〜3.5週 | 実装直列のため案Aより遅れやすい（並行の逃げ道なし） |

案Bの提出日計算:

```text
206人時 ÷ 23h/週 ≒ 9.0週
2026-08-08 ＋ 9週 ＝ 2026-10-10
```

### 2.2 何が減り、何が増えるか

| | 減るもの | 増えるもの / 残るもの |
|---|---|---|
| 案B | 設計の往復、待ち28人時、レビュー滞留、役割境界の交渉 | 単一クリティカルパス、理解ドキュメント34、体裁運用（受け渡し・手動コミット・Issue演出）、評価時の説明リスク |

### 2.3 評価・課題書との関係

| 課題箇所 | 要求の要点 | 案A | 案B |
|---|---|---|---|
| II.1.1 役割 | README に役割を明記 | 実態と一致させやすい | **表記は可能**。実態が1人に寄る |
| II.1.2 PMプラクティス | 定例・タスク追跡・レビュー・文書・チャット等（推奨） | 自然に発生しやすい | **意図的に記録を残す必要**（週7h） |
| VIII 短時間改変 | 理解の検証。数分〜、担当部分の修正 | 実作者が説明しやすい | **理解ドキュメント＋毎日3h学習が必須**。学習不足なら日付が早くても落ちる |
| コミット履歴 | リポジトリ内が評価対象 | 実働と履歴が一致しやすい | 体裁と実働が乖離する。ピアが突っ込む余地あり |

## 4. 理解ドキュメントと「ロボット」運用

### 4.1 他3人の一日

- **3h/日**: 自分のレーン文書（U-1〜U-4のいずれか）＋ U-0  
- ゴール: 担当範囲を口頭説明でき、VIII 相当の小さな改変を数分で当てられる  
- 実装はしない（案Bの定義）。コミットは受け取り成果物の手動投入のみ  

### 4.2 ドキュメントの出し順（案Bカレンダー）

単一実装者でも、学習側が空振りしないよう:

1. **最初の1〜2週で U-0 を完成**（共通地図）  
2. レーン文書は **そのレーンの実装が形になった時点で逐次**（全部を最後に書かない）  
3. U-R（README）は提出2週前までに役割・貢献を固定  

### 4.3 VIII（短時間改変）への最低ライン

対訳 VIII の趣旨は **実際の理解の検証**。案Bが成立するには:

- 各表記メンバーが、自分のレーンの入口ファイルを開ける  
- U-x の「改変ドリル」を一度は人手で成功させている  
- samatsum 以外が「AIが書いたので分からない」と答える状態では、提出日が早くても評価は持たない

## 7. 判断材料（合意用）

### 案Aを採るとき

- 4人が実働できる  
- 通信コストを払ってでも、評価耐性と並行を取りたい  
- 提出を **9月上旬〜中旬** に寄せたい  

### 案Bを採るとき

- 通信が破綻している / 他3人が実装できないが、**学習3h/日は守れる**  
- samatsum が **週23h以上の純作業を9週** 継続できる  
- 提出が **10/10前後** でもよい  
- U-0〜U-4 を「評価用の本番資料」として先に投資する  

### 合意チェックリスト（samatsum × torinoue）

- [ ] 案A / 案B / 混合（例: 実装は案B、コミット作者は実読了者のみ）のどれにするか  
- [ ] 案Bなら、他3人の「毎日3h」を欠勤条件付きで約束するか  
- [ ] U-0 の締切（推奨: 起算2週以内）  
- [ ] README 役割の氏名固定日  
- [ ] W-06/07 を切るか（187人時側に寄せるか）

## 8. 結論（比較の帰結）

| | 案A | 案B |
|---|---|---|
| 通信 | 重い | 軽い |
| 提出目安 | **4〜5週** | **約9週（2026-10-10）** |
